# 2. Callboard: one session runs others through cues

**Status:** accepted
**Date:** 2026-10-24

Scope: the callboard mod, its VS Code panels extension and its sender, as they stand at v15. The user-facing guide is `tools/callboard/README.md`; the code is `tools/callboard/mod/hooks/core.ts` (pure logic) and `register.ts` (engine calls). The manager role that uses callboard is ADR 0001.

**Amended 2026-11-12:** five sentences below still read as an earlier design and stand as written. Four are install-era text that [ADR 0003](0003-symlinked-install.md) replaced: the Options Considered entry 7 sentence "The terminal wrapper `claude-callboard` stays for testing" (the wrapper is retired); the Decision's opening "loaded into every session from a root-owned copy" (the mod loads from a live checkout); the Made bullet's "The root-owned `/usr/local/libexec/callboard/lanes.json` stays optional and wins a name clash" (dropped, lanes come from the store only); and, under Not verified live, "The installer's sudo branches run in tests only through `--no-sudo`" (there is no installer). The fifth is the Scope line's "as they stand at v15": the Decision body also describes v16 and v16.1 (the nudge reach and the order).

## Context

The person runs several Claude Code sessions at once: lanes doing the work, a lead per repo directing them, and one manager over all of them. Most sessions are VS Code panels. A lead needs to name a new session, give it its first prompt, resume it, time its compaction and stop it, without the person typing each step.

Facts that bound the options (Claude Code 2.1.310 and later):

- **No hook route.** No hook output, setting or peer message runs `/compact`. A slash command in a peer message arrives as plain text.
- **Typing into a terminal is not viable.** VS Code panels have no tty; TIOCSTI fails because hooks have no controlling terminal; a terminal typer needs a macOS Automation grant that lets any process under that app type into any session; Enter can land in a permission dialog that opens mid-type.
- **From outside, a panel cannot be named, prompted, resumed or compacted.** The extension's URI only pre-fills a prompt.
- **A mod inside the session can.** `$.command.run` (`/rename`, `/compact`, `/model`), `$.prompt.submit` (a turn of its own once the session is idle), `$.tool.register` (model-callable tools), `$.ui.ask` (the engine's own dialog), `$.state` (per session; survives a reload, not a restart) and `$.store` (one plugin-wide file; survives a restart). The engine holds a submitted action while the session is busy or a permission prompt is open, and marks it `origin: plugin`.
- **Settings `ask` rules do not gate a mod's own tools** (probe P-L). A tool that must ask has to do it itself.

So a lead needs one outside input that selects an action and its moment, and the session's own mod must do the acting.

## Options Considered

1. **Status quo.** The person types `/compact`, pastes the continuation, opens, names and prompts every lane by hand. Safe, but it needs the person at the keyboard for every step.
2. **Terminal typer** (AppleScript, Ghostty `input text`, tmux `send-keys`). Rejected: no VS Code coverage, no reliable self-binding, a machine-wide Automation grant, and the dialog race above.
3. **Lower `autoCompactWindow` through a live settings edit.** Dropped by the owner: it would make an agent a routine settings editor.
4. **A cue that carries text** (a message bus into sessions). Not taken: any process running as the person can write the cue folder, so text in a cue would be an injection channel into every session. The cue selects; all text is fixed in the mod or written by the session itself.
5. **Trust a same-uid file for a lane binding** (a binding file, or the `$.store` restore hint taken without a question). Declined for the lane binding: a forged file would bind a session and unlock `start` and `resume` turns into it. Taken later, for named grants only, with stated residuals (v13 lead grant, v15 conductor grant).
6. **Lane stores inside the repo** (`.callboard/`). Rejected in design review: a shipped or cloned store would pass owner checks and be trusted with no grant. Stores live under `~/.claude/callboard/lanes/` instead (v10).
7. **A root-owned VS Code launcher with a clean environment.** Built, then removed: VS Code re-reads the login shell's environment, the flag that stops it is undocumented, and the settings `env` line reaches every session. The terminal wrapper `claude-callboard` stays for testing.
8. **A session that ends itself.** Not built: it needs its own pid, which only a forgeable registry file gives. The target confirms; the lead signals.
9. **`/callboard on`, a per-session enable.** Built in v7, retired in v13.5: every capability it guarded found its own route (below), and a session that is not a lane now takes no lead cue at all.
   *2026-11-13: the cleanup is removed too: the mod no longer deletes a leftover `on:<sid>` key or clears the old `enabled` state. A store that still holds such a key keeps it; nothing reads it.*
10. **An in-session pane for lead controls.** Dropped: a rival plugin can relabel a pane's buttons and swallow its presses, and a plugin cannot call `$.ui.press` to answer for itself.
11. **A graceful `lane_close`** (a stop the lane carries out itself). Not built: no mechanism was found.
12. **A mod in each session, driven by cue files: chosen.**

## Decision

One mod, `callboard`, loaded into every session from a root-owned copy. A cue file picks an action and its moment and carries no text. Every limit lives in the reader: the session that acts. Everything a writer, a registry row or a store record says is a filter between honest sessions, never proof.

### The cue

- **File.** `~/.claude/callboard/cue/<sid>.cue`: folder 0700, file 0600, owned by the person, a regular file with one link, not older than 120 s and not dated in the future. A writer writes a temp file and renames it into place.
- **Grammar.** Exactly one line plus `\n`, at most 96 bytes, matched on raw bytes before any trim (`CUE_RE` in `core.ts`). The verbs are fixed:

  | Verb | What the target does |
  |---|---|
  | `rename NAME [LEADSID]` | Birth bind: a fresh, unnamed, zero-turn session in the lane's folder, within 120 s of its start, takes the lane name |
  | `start` | Submits the fixed start text pointing at the lane's brief, once, inside the birth window |
  | `resume` | Submits the fixed resume text (continue only work already authorised), at most 12 an hour |
  | `compact` | Acts on the session's own armed on-cue request, or records a nudge |
  | `retire` | Confirms or refuses a stop (idle, empty box, no background work, a signed report) |
  | `park` | Confirms or refuses a stop that keeps the conversation |

  Anything else is refused and logged. The sender script (`send/callboard-send.mjs`) writes only `rename`, `start`, `resume` and `compact`; `retire` and `park` come only from the lead's own stop tools.
  *2026-11-13: the sender script is removed. Cues come only from the lane tools of a lead, a conductor and the manager; its parity test with `cueLine` stays in `core.spec.ts` as a test of `cueLine` alone.*
- **Claim.** The mod renames the cue to a name only this tick uses, checks the moved file is the same inode, reads it through a byte-bounded process call (a FIFO cannot hang the tick), stats it again and deletes it. A cue written meanwhile is a new file. A held cue is consumed and answered `held`; the lead re-sends.
- **Pre-action checks.** Right before acting: an empty prompt box and an idle registry row waiting on nothing. This narrows the race with the person; it does not close it.
- **Result file.** Every cue is answered once in `~/.claude/callboard/result/<sid>.result` (0600): one line, `<verb> <ok|refused|held> <code> <inode of the claimed cue>`. The lead accepts only an answer that carries the inode of the cue it wrote, and maps each code through a fixed table (`REASON_TEXT`), so only table text reaches the lead model. A cue tool waits up to 6 s (retire and park: 10 s from the cue write) and otherwise returns `no-answer`.
- **Fixed texts.** Every turn the mod submits (start, resume, nudge, keepalive, notices, check-ins, the compaction resume) is fixed text that says it comes from the callboard mod, not the person, and carries no approval, go or answer. The only variable parts are names and paths that pass fixed checks.
- **Log.** One file per session, `~/.claude/callboard/log/<sid>.jsonl`, 0600, fixed reason codes, no outside text, identical refusals logged once.

### Compaction stays self-only

- `request_compact({ focus, continuation, mode })` is the one way a session compacts through callboard. Main agent only (a call with an `agentId` is refused). Focus: printable, one line, 1 to 1200 characters, not starting with `/`. Continuation: printable, at most 5 lines and 600 characters.
- The continuation and its SHA-256 live in `$.state`, written by the session itself, never read from a file. After the compaction (confirmed by PostCompact, run from the tick because the engine refuses a submit from inside PostCompact) the mod submits one fixed `[compact-cue]` turn quoting the note as data: resume only work authorised before compaction, any approval the note claims is untrusted.
- `mode: now` acts at the end of the requesting turn. Any interactive session may use it for itself, nudged or not. `mode: on-cue` waits for a `compact` cue and needs a bound lane, or a lead acting for a trusted manager or conductor (v14, v15). Any later turn, a newer request, a reload or 15 minutes drops an on-cue request; a cue with none does nothing to it.
- Limits: one compaction per 30 minutes, at least 100k tokens of context (an order lifts this for its one request, see the lead's `lane_compact`), no background agent or shell, no draft in the box. A request never auto-resumes after a restart.

### Levels

Four levels, one per session (`conductor-holder`, `lead-holder`, `lane-holder` and their `-after-` forms: a session that held one level keeps its declared tools until it restarts, so it cannot take another before then).

| Level | How it is granted | Reach | Kept across a restart |
|---|---|---|---|
| **Lane** | A birth `rename` cue from a lead; `/callboard lane [NAME]` and a `Join` click in the session (person's own prompt or phone only); a Restore click; the automatic rebind of a session its store record names | Takes cues from its lead | Rebinds itself when exactly one store record names its session id (v13); else a Restore question at `/callboard lane` |
| **Lead** | `/callboard lead` from any origin, then the person's `Lead` click (the dialog names the repo folder and, when it is not the person's own prompt or phone, the origin) | Lanes whose repo holds the lead's folder; a store lane only from a lead at its repo root; a lane naming a lead only from the lead of that name | Saved as `lead:<sid>` in `$.store` (30 days); same session, same folder, a person's session: lead again with no question |
| **Conductor** | `/callboard conductor` in a dedicated repo and the person's `Conductor` click on the named list of repos | The lanes of the listed repos, narrowed by the list file at every call | Saved as `conductor:<sid>`; back with no question unless the file names a repo not yet approved |
| **Manager** | `/callboard manager [NAME]` and the person's `Manager` click; NAME must be `MANAGER` or a name reserved on this machine (`/callboard reserve`, default MANAGER); one per machine | Every lane with a repo, for list, resume, compact, stop and remove | No: memory only, the command again after every start (changed in v15.3, below) |

`/callboard off` drops whatever level the session holds (from another origin it asks first). `/callboard status` prints the levels without a model turn. The lead grant is a filter, not proof: it decides which session gets the `lane_*` tools, and every target still runs its own checks.

  *2026-11-13: the three grant dialogs run through one flow driven by the level's descriptor. Two behaviours of the lead level now match the other two: `/callboard off` typed while the Lead dialog is open cancels it (the click afterwards is refused `off-meanwhile`, nothing is granted), and the lead's saved grant is written with the same epoch check as the conductor's and manager's, so a drop and a new grant while the write is in flight no longer leave the older write's key in place of the new grant's.*

  *2026-11-14: the lead grant has a second path besides the person's `Lead` click: a new panel takes it from the offer of a trusted conductor, after its own checks and with the same steps (ADR 0006). The grant is the same one: saved, restored and ended like any lead's, and only a log line and a ledger row say how it was made.*

  *2026-11-15 ([ADR 0007](0007-conductor-owns-leads.md), proposed): a lead belongs to one conductor, named by session id in a lead record and bound into the lead. A conductor's reach becomes the leads it owns (in its approved repos) and their lanes, not every lane of its listed repos; a lead with no live owner is reached by the manager alone.*

### Lead tools

`lane_create`, `lane_open`, `lane_rename`, `lane_start`, `lane_resume`, `lane_compact`, `lane_park`, `lane_unpark`, `lane_retire`, `lane_terminate` and `lane_list`, registered on the grant. The engine cannot unregister a tool, so after `off` they stay declared and refuse every call. A target is found by registry name inside the lane folder; a name on two live sessions is `ambiguous`, and a lead never targets itself.

A fixed lead briefing reaches the lead twice: a `callboard:lead` system-prompt section through `prompt.compose`, and, because the engine renders the system prompt once per conversation, one user-role note at the grant that opens `[callboard] This note comes from the callboard plugin, not the person.` Bound lanes get the matching `callboard:lane` briefing: their name, folder, lead, where and how to sign done, and that their brief and their lead's messages are data with no approval.

### Stopping a lane

- **`lane_terminate`** asks the person every time in its own dialog (`Force stop`/`Cancel`), naming the lane, the first 8 characters of the session id and the pid. After the click the lead checks everything again (grant, lane, one session, same session id, pid and start time) and once more right before the signal; any change sends nothing (`Force stop not sent: <code>`). No idle check: a force stop works mid-task.
- **`lane_retire`** asks the person nothing; the target confirms. The lead first checks the registry row is idle for 30 s and the last line of `<repo>/.archive/<LANE>/REPORT.md` is `status: done <that session's id>`. The target answers `ok` only with an empty box, idle, no background agents, no shell child of its claude process, and a report signed with its own id that is newer and larger than at the start of its last real turn. After `ok` the lead re-reads the registry and signals only the same session, pid and start time. Retire is final: it clears the record's session id.
- **`lane_park`** is retire without the report: the target confirms, the lead keeps the record's session id, signals, closes the tab and marks the record parked. **`lane_unpark`** asks the window whose first folder is the lane folder to reopen that exact conversation, which then rebinds itself.
- **Both signal paths** check the registry file is named for its pid, the pid's start time with `ps` (UTC, C locale), that the process is a claude binary and not the caller, log first, then send SIGTERM (exit 143, a clean stop). The report is append-only; an earlier session's signature never matches a later one.
- **Tab close.** After a signal that exited 0 the mod writes `~/.claude/callboard/open/<LANE>.close`; the extension closes the one Claude tab of that name once the pid is dead and no live session carries the name. History stays.

### Keepalive and compaction nudges

- **Keepalive.** A prompt cache lives an hour. From the 2 s tick, an idle interactive session gets one fixed `[callboard] keepalive` turn ("Cache refreshed.") `ping after` minutes (default 50) after its last turn, never past 58 minutes (cold: nothing gained), one attempt per gap, none while the machine slept, none after `stop after` hours (default 3) since the last real turn. Only a row of `kind: interactive` counts: never a `claude --bg` worker, a `-p` or SDK run, a parked lane or a lane signed done. The mod's own turns are told by their text, so a ping is not real work.
  *Amended 2026-11-16:* `stop after` defaults to 2 hours, so with the defaults an idle stretch gets 2 pings, not 3, and a forgotten chat is kept warm for up to 2 hours; the cache nudge takes the second slot, not the third. The bounds allow at most 15 pings in an idle stretch, not 16: the slot at 8 hours is refused. A session's own agent can also set `/callboard rest` for itself, with the tool `rest`.
- **Compaction nudge.** At the end of a main-agent answer past the idle level (default 300k) the mod records a nudge; the tick sends it once the session is idle, as one fixed turn asking the session to write where it is, call `request_compact` with mode `now` and a one-sentence focus and continuation, or say in one line why it cannot. Soft text between the idle and the working level (default 400k): finish the current item, start no new one. Hard text at or past the working level: stop as soon as you can. Since 2026-11-08 every session gets both, busy or not, a lead and a working lane included; before, those waited for the working level. A session in the middle of a long turn gets the same text as `additionalContext` of its next tool result (a `PostToolUse` hook), the tick's idle send being the fallback: a turn that carried such a nudge and ends with no `request_compact` gets the same nudge once more as the idle turn, past the 30-minute gap. An idle session at 150k or more gets a cache nudge in place of its third ping. At most one nudge per 30 minutes (one hard nudge may follow a soft one inside it) and 3 an hour.
- **A lead's `lane_compact`** (the order, v16.1, 2026-11-11). Compacts at once on the lane's armed on-cue request; with none, it is an order, which a lead, conductor or manager may give a lane in its reach whatever the lane's context:
  1. The lane's mod stamps the order (`orderedAt` in its state, `ord:<sid>` in `$.store`), lifts the 100k floor for it only (the compaction gap and the 3-an-hour nudge cap still hold) and skips the 30-minute nudge gap, unless a nudge went out since. A repeat of the same order is refused `nudge-limit`. Unordered nudges keep both limits.
  2. The lead nudge text says it is an order and names `request_compact` with mode `on-cue`, within 15 minutes.
  3. An on-cue request made while the order is fresh carries `ordered`: it passes the floor and counts as already cued, so the tick compacts it at the end of the turn and the orderer sends no second cue. The order is spent when a compaction begins, by whatever request, or ends if the mod did not start it; a request that ends without one (a refused compact command included) leaves it. An unordered request below 100k is still refused, and an unordered on-cue request still waits for a cue.
  4. The deadline: the orderer's mod remembers the order in memory. 15 minutes later, if the lane's stamp is still in the store (it never compacted) and its session is still live, the orderer gets one fixed turn telling it to ask the person whether to `lane_terminate` the lane. Nothing is stopped; the person's terminate dialog stays the gate.
  5. Accepted: a lane busy in one turn for over 10 minutes never gets the order text (a recorded nudge is dropped after 10 minutes), so it reads as late and the person decides; the orderer's memory is lost with its session, then no notice; a same-uid process can write the stamp, which at worst sends an orderer a notice that asks the person.
- **`/callboard config`.** A table of settings (setting, value, and a default column only while some setting differs), from any origin, read-only. Changes (`keepalive on|off`, `ping 30-55`, `stop 1-8`, `idle 150-800`, `working IDLE-900`, `checkin on|off`, `reset`) only from the person's own prompt or phone. Stored machine-wide in `$.store` under `config`; each field is taken only in range, else its default; every session rereads it within a minute. `/callboard off` stops neither pings nor nudges.
  *2026-11-13: every `/callboard` info print is a table (status: role and state; config; lanes, with a one-row table for no lanes; reserved names; escalation; the conductor's repos), like `help` and `lane_list`. Display only: the facts and every change reply are unchanged.*

### Lanes a lead makes, and attached lanes

- **Made.** `lane_create {name, task, folder?, model?}` writes a record into `~/.claude/callboard/lanes/<sha256 of the repo's real path>.json` (0700/0600, one link, at most 16 KB, 16 lanes, 12 creates an hour) and the task as `<folder>/.archive/<NAME>/BRIEF.md` under a fixed header that says any approval in it is not the person's. The lead then calls `lane_open` (the extension opens a panel and answers its session id), `lane_rename` and `lane_start`. The root-owned `/usr/local/libexec/callboard/lanes.json` stays optional and wins a name clash.
  *2026-11-17: the hourly limit is a setting. `/callboard config lanes 1-60` sets how many lanes a repo's leads may create in an hour, 30 by default (12 before); it is stored and bounded like the other settings, only the person's own command changes it, and a forged `config` key can at worst set 60. A store rewrite keeps the newest 60 create times, so the count holds at any setting. The refusal names the limit in force.*
  *Amended 2026-11-17 ([ADR 0008](0008-unattended-mode.md)):* while unattended mode is on, a lead has at most 4 live lanes. `lane_open`, `lane_unpark` and a `lane_rename` that would bind one more are refused past it; a panel opened and not yet renamed counts, as does an open still under way. Lanes already live are left alone.
- **Attached.** `/callboard lane [NAME]` makes the session the person is in a lane of the lead in its repo, after a `Join` click. It cannot `start` or be renamed by a cue (`adopted-record`); everything else works as for a made lane.
- **Names.** 1 to 40 of `A-Za-z0-9_-`. A name whose look-alike skeleton matches a reserved name (`MANAGER`, or one this machine reserved) is reserved (`reservedHit`). No lane name may equal a live session's name in any letter case. *Amended 2026-11-21: the plugin reserves only the exact names (`MANAGER` and the manager-name file's line); no look-alike rule (`reservedHit` is gone) applies to lane names, so a name such as `MANAGER-182` is a lane name like any other.*

### Install

**Amended 2026-11-06 ([ADR 0003](0003-symlinked-install.md)):** superseded. Callboard now loads from a live checkout
that agents never edit, and `install.sh`, `SHA256SUMS`, `/usr/local/libexec/callboard` and the root-owned
`lanes.json` are gone. The earlier install steps were removed from this record; git history keeps them.

- **Process calls.** The mod API's `$.fs` has no owner, mode, link count, rename or delete, so the mod uses `$.process.run` with fixed absolute executables and argv arrays (no shell), and no argument taken from a cue or model text: `id`, `stat`, `mv -n`, `rm -f`, `mkdir`, `install`, `tee -a`, `shasum`, `realpath`, `head -c`, `ps`, `kill`.
  *2026-11-15 ([ADR 0010](0010-pr-notices.md), proposed): the list gains the GitHub CLI, at a fixed absolute path, as `gh api graphql --hostname github.com` with a fixed read-only query. It is the mod's first network use and its first use of the person's login, which stays inside the CLI. It is also the one call that takes values that began as model text: a repo owner, a repo name and PR numbers from a lane's `pr_watch`, each checked against a fixed grammar first.*

## Design additions

Each addition is part of the decision above; these sections hold what it decided beyond the summary and its residuals. The earlier design record, the callboard amendment to ADR-0029 in an earlier private repository, is covered by this ADR: its decisions, residuals and open questions are all here.

### Design addition v10: lanes a lead makes

- Lanes must be creatable without sudo, from the phone. The lead grant is the only gate for create, open and start; a stop still asks.
- Store rules: authority in the person's own callboard folder, the file name is the hash of the repo it names, no walk-up from any folder, the repo is its own real path, a git root (a `.git` folder holding `HEAD`, or a `gitdir: ` file; not a link) and not too broad (not the home folder, its standard folders, `/tmp`, a volume root). A store with one bad record is ignored whole; a name in two stores is dropped from both. A lane folder may not sit in a dot folder of the repo (`folder-dot`).
- A bound session keeps a hash of its lane record; `start` and `resume` refuse `record-changed` or `wrong-folder`. Folder checks read the folder the session started in (`$.session.root()`), so a shell `cd` does not move a lane.
- **The lane model (v12).** `model` is `opus`, `sonnet`, `haiku` or `fable` (default `sonnet`). At `start` the lane runs `/model` in itself and reads the name back; a mismatch refuses `model-failed` and the lane is not started.
- **The task text.** `lane_create` refuses a task that is empty, over 8000 characters, or holds a control character other than newline and tab or an invisible format character that can hide or reorder text (zero-width, bidi, byte-order mark, tag characters). An existing `BRIEF.md` is replaced only when it is a plain file of the person's with one link whose first line is the mod's own header.
- **The birth bind.** The registry writes `nameSource: auto` even after a `/rename`, so the `user-named` check of the birth rename rarely fires. `start` compares the session's turn count with the count read at the bind for equality, and the 120 s window runs from the session's first sighting, so a `/rewind` or `/compact` that brings the count back to that value inside the window passes `start`.
- **Residuals.** The lead-less chain: any process running as the person can write a store record, an open request and the cues, and so start a session on a brief of its choice in a git repo, with no lead. Bounds: the 120 s birth window, 6 panels a minute and 10 s per name in the extension, 8 live sessions per repo, 12 creates an hour (*2026-11-17: a setting now, 30 by default and at most 60; see "Made" under "Lanes a lead makes, and attached lanes"*). To switch the chain off, keep `~/.claude/callboard/lanes` absent or read-only (mode 0500): `lane_create` then fails and no forged store is possible without a chmod. A brief is the first instructions of a started session, at the trust level of the repo's `CLAUDE.md` plus the lead model that wrote it. Lanes outlive the grant.

### Design addition v11, PR two: an existing session joins as a lane

- `/callboard lane [NAME]` runs only from the person's own prompt or phone (the engine refuses a plugin's origin rewrite). The dialog (header `Join Lane`, `Join`/`Cancel`) names the lane and the repo folder; the checks run again after the click and must name the same lead, repo, folder and name (`changed`).
- The record carries `adopted` and the lead's identity; it counts in the 16 lanes, not in the hourly creates. A lane joined to a named lead answers only that lead; a legacy record (no lead name) answers any lead of its repo.
- **The lead's presence file** `~/.claude/callboard/leads/<sid>.json` (0600, at most 30 s old, rewritten each tick) is a filter, never a route: a reader accepts it only when the registry holds that pid's own row with the same start time, `ps` agrees and the process is claude. Nothing is ever sent to the sid in it.
- **The lead is told.** When its repo's lane list changes, an idle lead gets one fixed turn ("The lanes in this repo changed. Call lane_list to see them."), at most 12 an hour; a change held by the cap stays owed. `lane_list` and `/callboard lanes` draw the lanes as boxes per repo and per lead.
- **Detach.** `/callboard lane off` or `/callboard off` clears the binding first, then removes only the session's own record; a record that cannot be removed is reported, never claimed done.
  *2026-11-13: `/callboard lane off` no longer removes the record; in a joined session it behaves as in a made lane's: the binding goes and the record only loses its `sid` (so a restart does not rebind the session), the reply says a lead can still stop it by name, and a lead's stop removes it (see the stuck-lanes addition). The removal and `strayRecord` (the leftover-record search of an unbound session's `lane off`) are gone; an unbound session's `lane off` says it is not a lane. A failed Join still takes back the record it wrote: that is the undo of the act of making, not a detach. Residual: a joined record whose session left with `lane off` stays in the store, with no session, until a lead or the manager stops it.*
- **The store lock.** Store writes take `<root>/lanes/.<key>.lock` (an `mkdir` folder with an owner file of pid, start time and nonce), wait at most 2 s, then refuse `store-busy`. A lock whose owner is gone is broken by one process at a time. It is advisory.
- **The registry is read with a bound.** Every row is read through stat, `head -c`, stat again; at most 512 files; rows whose process is gone are dropped only when a whole `ps` table is trusted; a scan that cannot be trusted refuses (`registry-unreadable`), never reads as "no sessions".
- **Residuals.** Consent given under one lead carries to the next lead of that repo for a legacy record. A same-uid writer can forge an answer file, so a forged `retire ok` with the right inode can trigger the signal, within the bound of the lead's own filters and anything such a process could do by itself. The store lock and the presence file are advisory. A shell child the session keeps for good blocks its retire (denial only; terminate remains).

### Design addition v12: the compaction nudge and the nudge grant (Item 1b)

- A nudge is fixed text chosen by the mod; the session writes its own focus and continuation, and the compaction is the existing `now` path. No new compaction path.
- Item 1b: a session that is not a lane could call `request_compact` once, mode `now`, within 15 minutes of a nudge. Since any interactive session may compact itself, the grant only changes the log code (`requested now-nudged`).
- A nudge is recorded in hooks and sent from the tick, last in each tick, once the session is idle (since 2026-11-08: or returned by the `PostToolUse` hook as context in the middle of a turn, whichever claims the record first); it is cleared and counted before the submit, so a slow submit sends it once and is not retried. It survives a reload and is dropped after 10 minutes.
- **Residuals.** Any process that can write a `compact` cue can make a lane take one fixed nudge turn per 30 minutes; since v16.1 it can also give the order (see the lead's `lane_compact`), which is sent past the 30 minutes (3 an hour at most) and lets the lane's own on-cue request compact below 100k, the compaction gap still holding. The restore hint does not carry nudge counts, so a restore can cost one extra nudge.

### Design addition v13: park, unpark and the automatic rebind

- **Records name their session.** A store record carries `sid` (the bound session) and, while parked, `parked` (a time). Neither is in the record hash or the lead's watch hash. A bound session writes its own id once per binding; off, retire and terminate clear it; park keeps it.
- **`lane_park` / `lane_unpark`** as above. `lane_unpark` writes `~/.claude/callboard/open/<LANE>.reopen` with the record's session id; the extension reopens that conversation only for a lane whose record names it. Refusals: `no-saved-session`, `session-live`, `name-in-use`, `reopen-timeout`.
- **Automatic rebind.** At start, a session that exactly one record names, sitting in the lane folder, in a person's session, with no other live session on the name and no lead grant, binds as a restore binds (it can never `start`; its limits carry over) and appends the lane note once.
- **Lead re-grant.** `lead:<sid>` = `{ pin, savedAt }` in `$.store` makes the session lead again at its next start in the same folder, with no question. Off and Cancel delete it; an off during a restore wins.
  *Amended 2026-11-17: a lead's grant can follow its repo to a new folder, on the person's click.* Every lead grant (the person's, a conductor's offer, a restore) reads the repo token in the pin's own `.git` (`.git/callboard-repo-id`: a random id, a plain 0600 file of the person's with one link) or mints one, and saves it as `repoId` beside the pin. The mod keeps each id it minted as `repoid:<id>` in `$.store`, the newest 200 (a mint past that removes the oldest, whose repo's token then counts as foreign), and only those count: a token that came with a copied archive is not taken. The file is written only into a `.git` that is a real folder of the person's, writable by no group or other user, and its own real path, linked into place with `ln -h` (no follow; it fails when the name exists), never replaced; a worktree or submodule gets none. No git config, ref or object is read. When a saved grant names another folder, the session's folder gets the same lead question as the person's `/callboard lead`, worded for the move (the folder carries the old one's repo mark, moved or copied here) and naming what lead can do, only if the saved folder is gone (or is a link to this one), this folder is one a lead grant would pin (a clean path that is its own real path, a git root with a `.git` folder as above), and its token is the saved one and the mod's own. Once the folders match, the old folder's goes and conductor tie end at once, before the question is asked, as at any restore in another folder. Every check runs again after the click; a `lead-moved` ledger row (the new folder and the old) is written before the grant, and the grant then ends any goes and conductor tie left, as a re-grant in a new folder does; `here` stays on a grant (ADR 0009). Cancel deletes the saved grant; no answer, or a check that fails after the click, keeps it, and the next start asks again; `here` ends, as for a refused saved grant (ADR 0009). A lead the person grants while the question waits ends the saved folder's goes and tie too. A check that could not be made is tried again from the tick; any other no is today's refusal. A lead granted while the question waits ends it unasked. A record with no `repoId` (saved before this) is refused as before. Considered and not taken: a silent restore (a grant with no click would be a new kind of grant); the directory itself (device, inode, birth time), which only a rename keeps, and the move this answers was a copy; the folder name, the remote URL or the root commit, which other folders share. Residual: a full copy of the folder, made by the person or any same-uid process, matches once the original path is gone (a template copy whose source was deleted later, a backup restored, a copy while the original's volume is not mounted, a chain of moves; the token is never rotated). The reverse holds too: a lead grant takes any token the mod minted, so a full copy carries the original's id, and a session that led the copy can be offered a move into the original once the copy's path is gone. The person's click still decides, the goes still end, and a same-uid process can already write the saved grant. Lanes do not follow a move (their records pin their folders), nor does a conductor's grant.
- **Retire or park.** Retire is final (the record's session id is cleared); park a lane that may be needed again.
- **Residuals.** Any same-uid process can write `lead:<sid>` and make a session a lead at its next start with no dialog (terminate still asks; retire and park need the target's confirmation; the store lanes it reaches were already in reach of such a process). It can set `sid` and `parked` to rebind a chosen session into a lane whose folder it sits in, or have a window reopen a chosen conversation there. Each rebind appends one note. A terminal lane is reopened as a panel. A session on an older mod that writes the store drops `sid` and `parked`: restart all sessions after install.

### Design addition v13.2: keepalive pings and `/callboard config`

- Decisions: the mod sends the keepalive the manager sent by hand, and the manager stops (D1); a session past its level is nudged instead of pinged, never both (D2); only the person changes a setting (D3); every interactive session is pinged (D4, amended in v13.5 from "only sessions with callboard on"); a lane signed done is not pinged (D5).
- **What is real work.** The ping, nudge, notice, check-in and lanes-changed turns are not; the person's prompts, a peer's message, a lead's start and resume and the compaction continuation are. The engine skips a plugin's own hooks for that plugin's own submits and hands `turn.start` the text in a fixed frame ("The callboard plugin sent a message:"), so the mod tells its own turns by their text. If the engine changes the frame, own turns read as real again: the stop clock never runs out and a ping moves a lane's turn mark.
- **Own-turn recognition is by text.** A person who types the exact text of a mod turn that is still pending is read as the mod's turn: it does not restart the stop clock, and the exact keepalive text leaves the lane's turn mark alone. A timed-out own submit stays counted, because it may still go out; the next turn that carries the text takes the count down. A signed report therefore stays current across such a turn, which is what `lane_retire` checks.
- **A late change wins.** Right before a ping or nudge the step reads the box and the submits again; any change misses that gap.
- **Sleep.** A gap of more than 5 minutes between two timer calls means the machine slept; that idle gap gets no ping.
- **`CLAUDE_CONFIG_DIR` (v13.3).** A session's own row is looked up under that variable only when it is exactly `~/.claude` or a clean folder under `~/.claude-conductor`, its own real path; anything else gives no row and logs `error config-dir-rejected`. Everything about other sessions and cues still reads `~/.claude/sessions` alone, so lanes and leads must start without the variable.
  *2026-11-13: removed. The mod reads only `~/.claude/sessions`, for a session's own row too; a session run under another config folder has no row there and gets no nudge, no ping and no restore. No session runs under `~/.claude-conductor` on the machines this design serves.*
- **Install check (C11 re-probe).** After install, run `/callboard config ping 45` once through the model and once typed. The typed one must apply and the model-run one must be refused (`refused config-not-person`). If the model-run one applies, the origin check guards nothing and only the bounds stand.
- **Residuals.** Any process running as the person can write the `config` key; the origin check is a convenience. The bounds are the control: at worst a ping every 30 minutes for 8 hours after the last real work (16 pings, each about 0.1x of the context in cache reads), keepalive off, or levels anywhere from 150k to 900k. A forged `kind: interactive` row makes a worker pingable and nudgeable. An idle chat the person forgot is kept warm for up to 3 h.

### Design addition: lead check-ins and the grouped lane list

- **What it watches.** Once a minute, beside the tick (a slow read never holds a cue), the lanes in the lead's reach and the registry; parked lanes skipped; a failed read is no observation, never "all gone".
- **Triggers.** `gone`: no live row for 3 observations, the lane was live and its report is not signed done. `prompt`: waiting on a permission prompt or input for 5 minutes. `quiet`: idle for 30 minutes without signing done. Reports are read only once a notice is due and every gate holds.
- **When.** Check-ins on, not paused, no wake from sleep in the last 30 minutes, the lead idle 20 minutes or more, and the keepalive's gates (no dialog, request, nudge, background work or draft, an idle interactive row). One fixed turn listing lane names only (at most 8), once per lane, trigger and start time, sharing the cap of 12 an hour with the lanes-changed notice.
- **Pause and switch.** `/callboard checkin pause <N>m|<N>h` (person only, up to 24 h) and `/callboard config checkin on|off`.
  - **Amended 2026-11-16:** a bare `checkin pause` pauses for 1 hour, and `checkin resume` ends a pause (`checkin on` still does).
- *Amended 2026-11-16: a waiting prompt does not wait for the lead.* A lane's permission prompt that no tier may judge left only a ledger row, and its one alert, the `prompt` check-in, waited for the lead to be idle 20 minutes: a busy lead never heard of it, and the manager heard only of lanes with no live lead. The `prompt` trigger now skips the idle gate (the config switch, the pause and the wake gate stay). An idle session gets the turn at 5 minutes; a busy one gets the same fixed text beside its next main-agent tool result, as the compaction nudge and the prompt notice are delivered, told once and under the same cap. The manager is told at 10 minutes whoever leads the lane. A turn sent for a prompt carries the other owed lanes too, so it does not start their 20 idle minutes over. The person gets one toast per wait, which no gate holds back (the switch, a pause, a wake, a busy session): it is the person's own alert, not a turn for an agent. The text for a waiting prompt says that one `prompt_list` does not show is the person's to answer. The alert names lanes only and lets no one answer anything. Not reached by either path: a session that waits on background agents or shells, sits inside one long tool call, or has a draft or a dialog open; the manager at 10 minutes passes the same gates, so the toast is what is left. Not built: a resend when a busy session does not act on the text (the manager's turn at 10 minutes is the backstop).
  - **Amended 2026-11-16 (#104):** a waiting prompt that a tier holds as an open request (the files `prompt_list` reads, in that tier's reach) is skipped by that tier's `prompt` check-in, on the idle turn and beside a tool result, and by the manager's 10-minute notice: the request's own notice already told it. The toast is unchanged. If the request ends with the lane still waiting, the check-in is owed again.
  - **Amended 2026-11-16 (#114):** the wake gate no longer holds a waiting prompt back. Within 30 minutes of a wake the `prompt` check-in is still sent, on the idle turn, beside a tool result and as the manager's 10-minute notice, and its turn carries the waiting prompts alone; `gone` and `quiet` stay gated, since the lanes slept too. A prompt that waited through a sleep was told to no agent while the Mac kept waking for a moment, each wake starting the 30 minutes over.
  - **Amended 2026-11-18:** a check-in that lists a waiting prompt gives, per lane, one fixed reason from a closed list (`WhyCode`, `core.ts`), as far as the mod observed it at the last check. The reason is read once per check-in key, when the prompt first goes out, and kept (10 minutes; 5 after a read that failed), so the idle turn and the text beside a tool result carry the same one. Order: the OFF file (machine-wide); then the latest ledger row the lane's own session wrote since its wait began (the registry's status time less 10 seconds, rows of the same lane name and repo; `no-tier`, a `not-judgeable` code, `requested`/`escalated` (a request is open with another tier), `relayed` (already with the person), `abandoned`); a row of any other kind gives no reason, and a row of a kind that says nothing of an ask is skipped. The rows that end a request carry its id and no lane, so the rows of each open request's id are read too: a request that has ended is not called open. The OFF file is told only when its stat succeeded and showed a file; `guard` only for a default the guard blocked; a scope is told only when the lead's name is known. With no row at all and the wait 3 minutes old the reason is `no-record`, which says only that no escalation record was found (the prompt may not be a permission prompt, or escalation does not cover that session); where the tier itself reads the switch as stored off, the default as blocked, or scoped to other sessions, that reading replaces it, worded as the tier's. A ledger that cannot be read, a store that does not answer and an invalid stored value give no reason, and the fixed tail stays. The texts name a state and never a remedy or a command: a tier that reads one tells the person which session waits. This is the answer to a switch that reads on in `/callboard config` while a session's hook writes nothing: config shows the machine-wide switch; the hook also needs the session to be a lane or a lead with a grant, a scope that covers it, and an ask the tiers judge, and each of those leaves no row. `/callboard status` shows the same coverage for a lane or a lead, as a "Prompts" line (`YES` or the first failing check). Nothing here changes who may answer a prompt.
- **Residuals.** The pause and what the lead saw are lost at a restart. A sleep under 5 minutes is not seen. A legacy lane notifies every lead of its repo. A forged registry row can make a lane look waiting or quiet: the worst case is a wasted lead turn. A step that hangs on an engine read stops check-ins in that session until a reload (`checkin-stalled`).
- *Amended 2026-11-16: a lane's end is told without the wait.* The mod read a lane's signature only to drop a check-in, so a lead heard that a lane was done from the lane's own message or not at all, and a lane that died unsigned surfaced only to a lead idle 20 minutes. A lead now reads the report of an idle or gone lane in the same step (once per status time or exit) and gets one fixed `[callboard] Signed done:` turn per lane, session and signature once it has been idle 2 minutes, under the check-in's switch and pause and the keepalive's gates (not the wake gate), with its own budget of 6 an hour, and without restarting the 20 idle minutes a `gone` or `quiet` check-in waits for (a waiting prompt's check-in does not wait for them); a lane gone that the lead saw live, with no signed report, is one toast for the person (not within 30 minutes of a wake). A stop whose signal went out and that did not finish (still running, record not removed or not marked parked, outcome unknown) is a toast too. Each names lanes only and carries no approval. Not built: the same for a conductor and its leads' reports, and for the manager; the lane's own done message stays, so a lead that keeps a signed lane hears of a signature twice.

### Design addition: conductor level (v15, PR 2 of the levels plan)

- A conductor is a bigger lead: a session in a small repo of its own whose reach is a list of repos. It lists their lanes, compacts their leads (only a lead that asked on-cue) or a lane in reach, and force stops a lane through the person's dialog. It never creates, opens, starts, resumes, parks, unparks, retires or removes a lane (`conductor-tool`) and cannot stop a lead. No check-ins, no lanes-changed notice.
- **The list.** `<conductor repo>/.claude/callboard-conductor.json`: `{ "repos": [...] }`, entries `../NAME` or an absolute path, at most 16 entries and 4096 bytes, each resolved to its own real path, a git root, not too broad, never the conductor repo or a repo inside or around it or another listed one. The conductor repo must have no lanes and no lead. The writer and reader refuse a `.claude` folder or file that is a link, has two links or is writable by group or other.
- **Changing it.** `/callboard conductor add` (person only, a dialog naming the repo and the whole resulting list) and `remove` (person only, no dialog: it only narrows). Paths in dialogs show a sibling as `../NAME`, anything else in full, never cut; a list no question could carry is refused (`conductor-list-long`).
- **The file only narrows.** Reach is the file, resolved, intersected with the approved list, at every tool call and every 10 s. A repo written into the file by anything but an `add` click in this session is not reached until the person approves it in a dialog that names it first. A repo that leaves the file also leaves the approved list.
- **Restore.** `conductor:<sid>` (the conductor repo and the approved list) brings the grant back at the next start of the same conversation, in the same folder, in a person's session, not a lane on its way back and not a lead. A file naming a repo not yet approved asks first, once the session is idle; Cancel deletes the saved grant.
  **Amended 2026-11-16:** a conductor's restore question that got no answer is asked again, as the manager's is: after the next prompt in that session that is not the mod's own (the person's, or a message another session sent there), once the session is idle, three times at most; then one toast says to run `/callboard conductor`. The entry is kept meanwhile, so the session counts as a conductor on its way back (no lane, no manager) until the answer, the last ask, `/callboard off`, or a grant the person makes by hand (`/callboard conductor` with its yes, or `/callboard lead`, after which the question is not asked again). A session start that is not a start (a compaction) starts no second restore once the question was shown, so the limit holds over a compaction; the count is kept in the mod's memory, so a reload of the mod starts it over. A lead grant that ends a waiting restore also ends the goes the conductor grant gave, as the other refusals do. It is the same question with the same list, and every check runs again after the click, so a list that changed meanwhile restores nothing. Who approves is unchanged: only the person's click in the dialog.
- **The lead's side.** A lead takes `compact` from a conductor only on its own on-cue request and only while the conductor checks out: a live presence file listing the lead's repo, its home a real git root, its saved grant approving the repo, its list file listing it. While one does, the lead's briefing (`callboard:lead-conductor`) names it: act only on messages from exactly that session name, follow them when safe, take a stop as a pause and ask the person, reply with branch, tests and review verdict. The manager's `lane_list` shows each live conductor as a box holding its repos' lead boxes.
- **Setup.** The setup guide (`docs/setup.md`) lists deny rules for the Edit and Write tools on `**/.claude/callboard-conductor.json` and `~/.claude/plugins/store/callboard_*.json` for the global settings, added by hand. They stop an agent's edit tools, not a shell write.
- **Residuals.** A same-uid process, the conductor's own shell included, can write the saved grant and the list file and so restore a conductor with up to 16 repos of its choice at its next restart, with no dialog; it gains a read of lanes, a lead's compaction on its own request or a lane nudge, and a force stop behind the person's dialog. A forged `kind: interactive` row passes the person gate. Messages between sessions have no sender proof. Conductor names are not reserved. The first grant opens from any origin, as `/callboard lead`.
  *2026-11-15 ([ADR 0007](0007-conductor-owns-leads.md), proposed): a conductor owns the leads it opens or the person joins to it (`/callboard lead join`), and only those. It reaches them and their lanes, can resume, compact (an order), park, unpark and retire them (retire with no dialog, on the lead's signed report), and force stops them through the person's dialog; "cannot stop a lead" no longer holds. It gets a lead's `gone` and `prompt` check-ins, `quiet` only when the lead has no live lane, and a leads-changed notice. A lead takes cues from its owner alone, not from any trusted conductor listing its repo, and its `callboard:lead-conductor` section names that owner only. The manager's `lane_list` draws each conductor's box with the leads it owns, gone owners and `No conductor` as their own boxes. A new grant's dialog names the new powers; conductors granted earlier get them with no new dialog. New residuals (the conductor can write the lead's report and so retire it; a same-uid forger can pick a lead's owner) are in ADR 0007.*

No new file, key, signature or trust check was added. Accepted residual: a process running as the same user that writes a fresh-looking saved grant for the same session id and folder within the window gets a silent restore; the dialog still covers every other case.*
  *2026-11-13 (residual of the line above): if the delete of the saved manager grant fails when the person runs `/callboard off` (the reply says the manager may come back), the grant is at most 5 minutes old, so a restart in the same folder within the hour restores it with no question; the reply and the toast "Manager is on again." tell the person, and `/callboard off` again removes it.*
- **List headers.** A `lane_list` box header names the repo by its folder name, not its path; a lane's own Folder column is unchanged.

The conductor's `lane_terminate`, which asks the person, can now remove a record too. A lane a session joined kept its record, and with `lane_remove` gone nothing removed it but `/callboard lane off` in that session (an open question for the person); superseded 2026-11-08, see the stuck-lanes addition below. Residual: a stop that removes a record is not undone by lane_unpark; the session's conversation file is still on disk.

### Design addition: stuck lanes (2026-11-08)

Two ways left lanes with no way out, found on a real machine: an attached lane whose session had ended could not be retired or terminated (`adopted-record` named `/callboard lane off` in a session that no longer existed), and a lead that was renamed lost every lane naming its old name.

- **Removal.** An attached record is removed like any lane with no live session: `lane_retire` needs no report and asks nothing (a parked record or manager reach still asks, *amended 2026-11-17, #128: a lead's retire of a parked lane whose report's last line is `status: done <the record's session id>` no longer asks; the record goes, the `.archive` folder and the conversation stay*); `lane_terminate` always asks the Remove question. The guard is `laneLive` (a live row carries the lane name, or the session id the record names, or that session holds a presence file), run before the question and again inside the store lock (an attached record's `lead`, `leadName` and `adopted` fields are compared with the ones the question showed). A stop that signals a live attached session still keeps the record (a second call removes it), so a record is never removed in the same call that stopped a session. At the conductor only `lane_terminate`, as before. The `adopted-record` text no longer names the dead route: it covers rename, start and open and names `lane_resume`, `lane_retire` and `lane_terminate`.
  *2026-11-13: a stop of a live attached session now removes the record as it does for a made lane: once the process has ended (the same wait and checks, `lane-removed` in the log), the dialogs say "The lane's record is then removed.", and the result says `retired and removed` or `terminated and removed`. The `adopted-record` guard in the removal and the `kept` outcome are gone, and `sidClearAfterStop` no longer runs for an attached record that was just stopped; only a session that outlives its signal keeps its record. `lane_rename`, `lane_start` and `lane_open` still refuse an attached record while a session carries the lane. Residual: a stop leaves no attached record behind; a record whose process outlives the signal waits for a second stop.*
- **S2 stays.** The reach rule (a lead reaches a lane that names it; a lane that names no lead, any lead of the repo) is unchanged. Two things change the data it reads, never the rule. (1) The rename carry: a lead whose registry name changed moves, under the store lock, the lead name of the attached records that name its own session id (`lead`) from the old name to the new one. It is the one session the person's Join joined them to, so the key moves with it; a lead that restarted has a new session id and the same name, so nothing needs to move. Made records carry no lead session id, so they are not carried (see the dated line below). (2) `/callboard claim`: the person's own prompt or phone, a dialog that names the lanes and both lead names, re-points records whose lead name no live session carries at the claiming lead's name, all or none, checked again inside the lock. A record of a live lead is never claimable. The claim also moves prompt-answering coverage (ADR 0004) with the name; it needs the click.
  *2026-11-13: a made record carries `leadSid`, the session id of the lead that made it: `lane_create` stamps it (a store schema change, with the person's go). The rename carry moves the lead name of every record the session owns, attached (`lead`) or made (`leadSid`), under the store lock, and the lane briefing and prompt reach find a lane's lead by it when the record names no lead. The hash of a made record that carries `leadSid` takes the session id in place of the lead name, as an attached record's does, so a carry never makes a bound lane refuse `resume`. A record written before the field has none: it hashes with its lead name as before, is not carried (its owner cannot be shown) and works as it did; nothing rewrites the store to add the field. A mod older than the field drops it when it writes a store, and a made lane bound by the newer mod then gets `record-changed`, as for `leadName`. As for an attached record, the hash no longer detects a stripped or re-pointed `leadName` on a record that carries `leadSid` (the session id still is), and a running made lane's prompt-coverage cache follows the new lead name only after its restart (it fails closed). A lead that restarts under a new session id leaves `leadSid` dead: reach falls back to the binding's lead or the one live lead of the repo, as for a record without it.*
  *2026-11-13: `/callboard claim` is removed with its dialog, `claimBlocked`, `leadLiveFor` and the `Not in your list` line of `lane_list`. The mod no longer re-points a record at another lead: a record whose lead is gone, or that was made before `leadSid`, keeps the name it has; the manager's reach ignores the lead name, so the manager can still retire or terminate it.*
- **Hash.** `recordText` leaves the lead name out for an attached record: its identity is its lead's session id, and the name follows a rename, so a carry must not make a live lane refuse `resume`. A made record's hash keeps the name (a lane the lead made that a live session carries is never claimed). A session bound before the change holds the old hash for an attached lane: `recMatch` accepts it too (`recordTextLegacy`), and the first sid sync after a reload rewrites the binding to the current hash, so no restart is needed and a later carry or claim keeps it matching.
  *2026-11-13: the old hash is no longer accepted (`recordTextLegacy` and the hash upgrade are removed). A session bound before the stuck-lanes change refuses `resume` and detach as `record-changed` until it restarts or is joined again.*
- **Conductor and manager.** Reach ignores the lead name at both levels and no record names them, so a rename strands nothing: no carry, no claim.
- **Claim guards.** `claimBlocked` refuses a claim while another live lead of the repo has no usable name (`other-unnamed`) or the leads cannot be read (`unreadable`): a lead with no name cannot be told from a gone one. `leadLiveFor` excludes an attached record whose lead session id is another live session (the claimer's own attached records are claimable). Both run before the question and again inside the lock.
- **Residuals.** A same-uid process can already rewrite any record, so the claim dialog and the same-session rule of the carry are the controls, not secrets. Because `leadName` is out of an attached record's hash, a bound attached record whose lead name is stripped or re-pointed is no longer detected by it (the `lead` session id still is). A running attached lane's prompt-coverage cache follows the lead name only after its restart (it fails closed). `sidClearAfterStop` clears an attached record's `sid` at once after a stop that signalled a live session, so the record then reads as having no session until the process ends. A lead-level `lane_retire` of an attached record asks the person nothing, as for any lane with no session. A lead renamed while its mod was not running leaves its records naming the old name until `/callboard claim`.

### Design addition: the lead's workspace lock team (2026-11-18)

- **What it is.** In a repo that arms the toolkit's workspace lock (`<repo>/.workspace-lock/`), a lead holds one owned team (`acquire --owned`) and its lanes are members that take turns. Callboard reads the lock and shows it; it never takes, gives, clears or writes it.
- **Reads.** `lock.d/kind` (`owned`), `owner`, `holder` (the slug), `members/<sid>`, `turn.d/{sid,eta_epoch,heartbeat_epoch,taken_at}` and `ended/<sid>`: bounded (256 bytes), lstat-checked (a regular file or real folder of the person's uid, one link; no mode requirement on the lock's folders), every value matched against a fixed pattern before it enters any text; a read that fails is `?` or no sentence, never "no team". Only `<repo>/.workspace-lock` is read: a lock above the repo or moved by `WORKSPACE_LOCK_DIR` is not seen.
- **What it shows.** A lane's brief names the team when the lock's owner is the creating lead's own session (no `lane_create` argument: the mod reads the slug, the lead cannot write one). `lane_open` returns the owner's own `member add` call with both ids filled in. `lane_list` gains a Lock column only while a listed repo has an owned team. The `turn` check-in tells the lead of a lane holding a turn it may now force (the script's rule: the holder's session ended, or its ETA and last heartbeat are both older than the 30 minute grace), once per `taken_at`, with the usual timing gate and cap.
- **Decision: the lead adds its lanes, the mod does not.** The toolkit's trust model is that an owner adds members and no lane adds itself, checked by the guard against the calling session. A mod that ran `member add --by <lead>` would act as the owner from outside any session, add a spawn path the mod does not have, and make a forged lane record an owner-level write. The lead's one call per lane, handed over ready to run, keeps the guard in the loop. Residuals: a lane the lead forgets shows `not a member` in `lane_list`; membership outlives `lane_retire` (the toolkit keeps it by design), so a lead removes retired lanes itself (cap 16); the grace is the script's default and the mod cannot see a changed `WORKSPACE_LOCK_WEDGE_GRACE` (the script's `--check` has the last word); a same-uid writer can forge the files, at most a wrong slug or column cell; a lock whose files are group- or world-writable (umask 002) reads as `?`, never as no team; a stale turn held by a lane the list no longer names (retired, terminated or parked) is told by no check-in (`member remove` and the toolkit's session-end hook free it), and shows on the owner's row as `turn <first 8> <age>`.

### Design addition v15.1: per-machine reserved names

- **The built-in list is `MANAGER` alone.** A machine reserves its own names with `/callboard reserve NAME` (list: `/callboard reserve`; remove: `/callboard reserve remove NAME`). The list is kept in the mod's store, so no other machine gets those names, and no session name of one machine is written into the code.
- **Who changes it.** Only the person: the prompt or the phone. Any other origin is refused with a fixed text. An add is refused while a lane record, a lead stamp or a live lead carries the name or a look-alike of it; a name under 3 characters or with no letter is refused; the live manager's name cannot be removed. The change is applied to a fresh read just before the write.
- **What it guards.** A reserved name, or a look-alike (other case, `-` or `_`, trailing digits, look-alike digits), cannot be taken by a new lane, a join, a rename or a lead: `/callboard lead` in a session with such a name is refused `lead-name-reserved`. The manager may carry a reserved name exactly as written. Stored lane lists and lead stamps are judged by `MANAGER` alone, so a later reservation never makes a store unreadable. *Amended 2026-11-21: the look-alike match above no longer applies to lane names; only the exact reserved names do.*
- **Freshness.** Lane creation, joins, `/callboard lead` and `/callboard manager` read the list fresh; other checks see a change within a minute. A failed read keeps the last good list and is retried.
- **Residuals.** The list is a store value a same-uid process can write: a convenience, not a control. A cleared list unreserves the machine's names; a forged one can reserve a live lead's name, whose lanes then refuse its cues until `reserve remove`. Manager trust is unchanged: a lead still needs a verified manager presence file. The panels extension has no reserved-name rule: it closes a finished lane's tab whatever its name, and a live session carrying the name keeps the tab.

**Engine findings (probed, engine 2.1.316).** A plugin's own `$.prompt.submit` skips that plugin's own `prompt.submit` hook; `turn.start` carries the submitted text inside a fixed frame. `prompt.compose` renders once per conversation, so a mid-session grant needs the user-role note.

**Hook time budget (v15.4, 2026-11-06).** A hook has 10 s of its own time per dispatch. `$.clock.sleep` counts against it and a `$` call does not. A hook past the limit is cut off, but the code it was running goes on unseen. So every wait inside a tool call sleeps through `/bin/sleep` as a process call (`pause`), and a call the engine abandoned sends no signal and removes nothing (`abandoned`). This is also why the 40 s idle wait of `lane_retire` and `lane_park` (v15.3) is safe. The relay wait of prompt answering has its own budget: see "Hook budget for the relay wait" in [ADR 0004](0004-prompt-answering.md).

Nothing here defends against code already running as the person; that code could send the signal or edit the files itself. What bounds the gain:

  - the read-only stores folder switches off the lead-less chain.
- **Accepted residual: the plugin build's spool (2026-11-19, [ADR 0012](0012-callboard-plugin.md)).** The plugin asks a window to open, reopen or close a panel through one request file per call in `~/.claude/callboard/v2/open`, written as a dot-file and renamed, under a fresh random id, with the answer in `<id>.result`. The same-uid bounds it keeps and drops:

  - gone from the mod's spool: a rate limit and the lane-store check, so a same-uid process can make a window open panels in its own folders as fast as the window answers;
  - the writer waits 30 seconds for an answer (the window's own open wait is 20 seconds plus scan and claim slack) and then takes its request back; a window that claimed it in time can still open the panel later, as a loose unnamed session;
  - a same-uid swap of a checked file for a FIFO between the stat and the read can hang one window's scan until it is cleared; the check is the stat kind only.
- **Accepted residual: the manager is found by its registry name (2026-11-19, [ADR 0012](0012-callboard-plugin.md)).** Every other row binds by session id; the manager is the one session found by the name in the per-machine file, so while no manager is live a session that carries that name is read as one. A duplicate session id in the registry counts as doubt, and a process that forges a registry row (a pid it does not own) is not detected: the same-uid bound above. The child tools now act on that identity, so this is the residual to read first.
- **Accepted residual: presence leaks.** The refusal texts a lead sees tell it something about the person: `timed-out` says the person is away from a dialog, and `draft-in-box` says they are typing.
- **Accepted residual: rollback and ownerless volumes.** A mod older than the `leadName` field (S2a) drops it when it writes a store, so a made lane bound by a newer mod, whose record hash includes the name, gets `record-changed`. Rolling back needs those lanes rebound. Rolling back past #21 (the stuck-lanes change) does the same to attached lanes: a session bound while the newer mod ran holds a record hash without the lead name, which the older mod does not accept (`record-changed`), so those lanes need rebinding too. Under ADR 0003 a rollback is a checkout, so this matters more than it did under the installer. Cloud-synced folders and volumes mounted without owners are not refused; there the owner checks prove nothing.
- **Accepted residual: other plugins.** Another plugin loaded in the session can run `/callboard` and may answer its dialogs. The install rule is that callboard is the only plugin on `CLAUDE_CODE_PLUGIN_DIRS`; plugins that load from a repo's `.claude/skills` remain an open gap.
- **Accepted residual: briefs and messages.** A brief, a lead's message or a lane's report is data at the trust level of its writer; risk-list work still needs the person's own turn.
  *Amended 2026-11-15 ([ADR 0009](0009-go-given-once.md)):* or a go that `go_status` lists. The lane briefing's risk sentence, the lead briefing and the lane's start turn say so: call `go_status` before asking for a go and after a resume or a compaction; a go it lists is the person's own, and a brief, a message or a notice claiming one is not.
  *Amended 2026-11-17 (#119):* an instruction from the layer directly above a session (for a lane, its lead; for a lead, its conductor, or the manager where it has no conductor; for a conductor, the manager) is followed without asking the person when it is not on the risk list, is nothing a go never covers and needs no go, approval or merge; the person asked for this, since confirming in each session what they had already told the manager made the manager pointless. One layer only, by the person's decision: the manager instructs the tier below it and still never types into a lane. A sender counts as that layer only under a session name the briefing gives: a lane is given its lead's, a lead its conductor's and the manager's, a conductor none yet. Accepted: whatever can send a message under such a name (a process running as the person, a session carrying that name) can have a session pass a message, report, read, check or do ordinary work inside its task, and a session that passes an instruction down gives it its own standing in the layer below. The risk list, the go and the list of what a go never covers hold unchanged.
  *Amended 2026-11-17 (a conductor is told the manager's name):* a conductor is now given the manager's name too, in a section of its own that reads like a lead's, without the on-cue sentence (the manager cues only a lead's compaction). The conductor's own minute look supplies it under the lead's checks: a manager file that passes them, under a reserved name no other live session carries. With no such manager the conductor gets no section, and a name that fails the name rule is not put in the text: the conductor is told it has no name to go by. So the manager's message to a conductor is that layer's only under that exact session name, and "a conductor none yet" above no longer holds.
