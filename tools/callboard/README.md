# callboard

A mod for Claude Code sessions plus a VS Code extension. A lead (MANAGER) writes a tiny cue file; the mod in the target session acts on it. The cue chooses the action and its moment and carries no text. Design and threat model: ADR 0002 (`docs/adr/0002-callboard.md` at the repo root).

Self-contained: nothing here imports from the rest of the repository, so the directory can move to its own repository unchanged.

## Parts

| Path | What |
|---|---|
| `mod/` | The Claude Code mod (`callboard`): reads `~/.claude/callboard/cue/<sid>.cue`, serves the `request_compact` tool, logs per session |
| `mod/hooks/core.ts` | Pure logic: cue grammar, freshness, lane store checks, fixed texts, request validation, limits |
| `send/callboard-send.mjs` | Writer side: `node send/callboard-send.mjs <sid> <rename NAME\|start\|resume\|compact>` (temp file, mode 0600, atomic rename) |
| `extension/` | VS Code extension: commands `callboard.open(folder)`, `callboard.reopen(sid)`, `callboard.close(sid)`; finds a new panel's session id by diffing the registry, one open at a time; every 2 seconds it closes the tab of a panel it opened once that session's registry entry is gone and its process is dead (one matching Claude tab only, never a reserved name; history stays). After `lane_retire` or `lane_terminate` sent the signal, the lead's mod also writes `~/.claude/callboard/open/<LANE>.close` (session id, pid and lane name, three lines); the window that has the lane folder open adds that panel to the same sweep, so the tab of an attached lane or one resumed by hand closes too, under the same rules (nothing is answered, nothing happens in a terminal; a request is written only when the signal exited 0, and an adopted panel that no registry entry shows within 5 minutes is dropped). Since v13 it also answers `<LANE>.reopen` (the saved session id, one line): it reopens that exact conversation as a panel, only for a lane whose store record names that id (see "Parking a lane") |
| `link-extension.sh` | Links the panels extension into `~/.vscode/extensions` from this checkout (see Install) |

## Cue contract (reader side)

- File `~/.claude/callboard/cue/<sid>.cue`, directory 0700, file 0600, owned by the user, one link, not older than 120 s.
- Exactly one line plus `\n`, at most 96 bytes: `rename <name>` (a lead's `lane_rename` adds its own session id, `rename <name> <lead sid>`; a session still running a mod from before this change refuses that as `grammar`, so restart open lanes and unnamed panels after installing), `start`, `resume`, `compact` or `retire`. Anything else is refused and logged. `retire` is written only by the lead's `lane_retire`; `callboard send` does not accept it.
- Every cue is answered in `~/.claude/callboard/result/<sid>.result` (0600, one line `<verb> <ok|refused|held> <code> <inode of the cue file>`); the lead accepts only its own inode. A question nobody answers in 90 s changes nothing and says "The question timed out."
- Lead tools: `/callboard lead` is run in the session that leads a repo's lanes (from any origin; a confirmation, Lead or Cancel, which names the repo folder and, when it is not your own prompt or phone, the origin; a re-grant from a plugin, another session or a script keeps the folder already pinned); `/callboard off` turns it off again (from a plugin, another session or a script it asks you first). A repo may have several leads (levels S2b): a session whose own name is reserved is refused first, lone or not (`lead-name-reserved`, v15.1); a lone lead may otherwise stay unnamed, but a second one needs a valid lane-style name (set with `/rename`; any name source counts) that no other live session carries in any letter case, and every other lead of the repo needs such a name too. Otherwise it is refused before the question and again after a yes (`lead-name-reserved`, `lead-name-taken`, `lead-needs-name`, `other-lead-unnamed`; `Lead stays off: ...`). Only then does that session get `lane_rename` (by session id, for a new unnamed session in the lane folder), `lane_start`, `lane_resume` and `lane_compact`, plus `lane_open`, `lane_terminate`, `lane_retire`, `lane_park`, `lane_unpark` (below) and `lane_list` (see "Attaching a session as a lane"). The confirmation says the session can create, start, resume, compact, park, stop and retire lanes, that only a force stop asks you, and that lead stays on after a restart until you run `/callboard off`. Cancel clears the lead grant. A dismissal or timeout also clears it when you ran the command from your own prompt or phone; from a plugin, another session or a script it changes nothing. Each writes the same cue file as the sender, for a lane in the lane store whose `repo` is the lead's own folder, and never for the lead itself or for a name that matches more than one live session. The grant is kept as `lead:<session id>` in the mod's `$.store` (v13): when the same session starts again in the same folder it is lead again with no question (toast "Lead is on again for FOLDER."); `/callboard off` and Cancel delete it (if that delete fails, the reply adds "Lead may come back after a restart. If it does, run /callboard off again."; an off or Cancel while a restore is still running stops it), a grant for another folder is deleted at start, a session with no person (a headless run resumed under its id) is not made lead and keeps the grant, and a saved grant older than 30 days is not taken (it is rewritten once a day while lead is on). It is a filter, not proof: the target's own checks still apply. Each cue tool then waits up to 6 s (counted from the call) for the target's answer in `~/.claude/callboard/result/<sid>.result` and returns `cue <verb> acted`, a refusal with its fixed text, or `no-answer`. The engine cannot remove a tool, so after `off` the tools stay declared and refuse every call.
- Opening a lane (VS Code only): `lane_open` writes `~/.claude/callboard/open/<LANE>.open` and waits up to 8 s for `<LANE>.result`. The panels extension in the window that has the lane folder as a workspace folder checks the lane against the lane store, opens one panel (at most one per lane per 10 s) and answers `ok <session id>` or `error <code>`; the lead then calls `lane_rename` with that id and `lane_start`. A lane that already has a live session is refused. A CLI tab opener is a later change.
- Stopping a lane's session: `lane_terminate` asks the person every time (its own dialog, so it needs no settings rule; it names the lane, the first 8 characters of the session id and the pid, so you can tell which process a click ends) and then sends SIGTERM. The dialog can stay open for up to 90 s, so after your click the lead checks again before any signal: the lead grant is still on (`/callboard off` during the dialog stops it), the lane is still in the lane list and the lead's (the detach of an attached lane removes its record and stops it; a lead-made lane stays stoppable by its name until you rename the session), the lane name is still on one session, and that session's id, pid and start time are the ones shown (a `/clear` in the session during the dialog stops it). Before it asks, the lead also refuses a doubled session id (`session-duplicate`) and a pid that is not a live claude process with that start time. Any change after the click refuses, signals nothing and shows the toast `Force stop not sent: <code>`. The check reads the registry the engine writes, so a `/clear` it does not show yet is not caught, and a few milliseconds remain between the check and the signal. `lane_retire` asks the person nothing; the session confirms it instead. The lead checks first that the registry status is `idle` for 30 s and not waiting, and that the last line of `<repo>/.archive/<LANE>/REPORT.md` is `status: done <that session's id>` in a file newer than the session. It then sends a `retire` cue, and the session answers `ok` only if its prompt box is empty, it is idle, it has no background agents or shells running (a shell, whatever its flags, that is a direct child of its claude process, which is how the engine runs a Bash call left in the background; a shell child the session keeps for good, such as an MCP server started through `sh -c`, blocks retire too; when the session cannot find its own process the answer is `background-unknown`), and the report is signed with its own id, has a file time after the start of its last turn, and has grown since then. The session records that start and the report's size at each prompt (any origin: yours, a lead's resume, a notice) and at each turn start of the main agent (a wake, a queued message), so a `done` signed before a later turn does not count, and a touch or an editor save that only changes the file time does not make it count again. A session that signed `done` and then worked again must sign again (`report-stale`). When there is no usable record of the last turn (a write of it failed, no prompt seen since callboard loaded, or the session was not a lane then) the answer is `report-unknown`: it must take a prompt and sign again. After a restart a lane is not bound until it binds again: a lane from a store record that names its session id rebinds itself within a few seconds (v13, "Parking a lane"); any other lane waits for the Restore question at `/callboard lane` (v13.5; `/callboard on` before), which stays the fallback. Retire is refused (`not-bound`, then `report-unknown`) until the lane is bound again, has taken a prompt (for example a lead's `lane_resume`) and has signed again. `lane_park` is the third stop: it keeps the conversation (see "Parking a lane"). The lead waits 10 s from the cue write for the answer (the session answers on its next 2 s tick) and checks every 200 ms; without an `ok` (`no-answer`, `held` or `refused`) nothing is sent to the process. After `ok` the lead re-reads the registry and signals only the same session, pid and start time, with exactly one registry entry for that session id and the session still idle for 30 s. There is a window of about 2 seconds between the session's `ok` and the signal: a draft started in it is lost, and the transcript can be resumed. Both stop tools check, before the signal, that the registry file is named for the pid it holds, that the pid's start time matches `procStart` (`ps` in UTC), that the process is a claude binary and not the caller's own, and log `terminating` or `retiring` first. The report is append-only: append your section ending `status: done <session id>` and never overwrite the file; an earlier session's signature never matches a later session. Since v15.3 (2026-11-06) `lane_retire` and `lane_park` wait for the 30 idle seconds themselves: while the registry shows the lane busy, waiting or idle for less than that, the call re-reads the lane and the registry every 2 seconds for up to 40 seconds (a read that fails meanwhile is polled again) (the session must stay the same process and the grant on) and goes on the moment the lane is idle for 30 s; only then does the answer-wait above start. A lane still not idle after the 40 seconds is refused `not-idle`; the refusal names the seconds left when the lane is idle and only the time is missing ("idle for 12 of the 30 seconds it needs. Retry once, in 18 s; do not loop."), and for a busy or waiting lane says to retry once it is idle for 30 seconds. `lane_terminate` never waits. Settings ask rules do not gate mod-registered tools (live probe P-L: `lane_retire` and `request_compact` ran with no prompt in a Manual-mode panel), so both run unattended; their safeguards are the session's own confirmation, the idle check, the signed report and the repo scope. A same-user process can forge the session's answer file and so trigger the signal, as it can forge the registry and report files. Those guard against an honest mistake, not against code running as you that forges a registry or report file: a lead may stop a lane it no longer needs, and a stopped session can be resumed from history. Remove any ask rule you added for them: it does nothing.
- Lane names, folders and brief paths come from the lane store: the lanes a lead made with `lane_create` and the sessions that joined as lanes (see "Lanes a lead makes" and "Attaching a session as a lane" below). The root-owned `lanes.json` of earlier versions is gone (ADR 0003): it needed a sudo install, and nothing used it.
- All limits live in the mod. The sender's checks are convenience.

- Layout and limits (live-tested): `claude-vscode.editor.open` opens in the window's first workspace folder, so the extension only opens a lane whose folder is that first folder; the lead may share the window when the lane folder is the repo root. `lane_rename` and `lane_start` only work within 120 s of the session opening (a held cue is consumed, not retried). A stopped lane's tab stays open with an exit-143 banner. The panel opened for a lane does not keep focus: the extension switches back to the tab that was active. The unnamed-panel guard counts only panels this extension opened plus late panels after a timeout, never the lead's own panel. `ps` start times are read with `TZ=UTC LC_ALL=C` so a non-English locale does not break pid checks. Open further windows from inside VS Code (File, New Window). `lane_open` is answered only by a window whose first folder is the lane folder; the lead briefing says so.

## Routes

- **VS Code panels:** the extension opens a panel (no prompt) and returns its session id; the lead then writes `rename <lane>`, `start` (first prompt is the lane's brief) and later `resume`.
- **Terminal:** any `claude` once the default load below is set; cues work the same, keyed by the session id.

## Install

Callboard has no installer (ADR 0003). The mod and the panels extension load straight from your live checkout of this repo: one clone that stays on `main` and moves only with `git pull --ff-only` after a merge, so a pull is the install. Agents never edit that checkout; they work in clones under `/tmp` (the repo's CLAUDE.md, Where agents edit). Nothing needs sudo or a fetch, so it works while the repo is private. `<checkout>` below is that clone's absolute path. The step-by-step guide, including the switch from the earlier root-owned install, is `docs/setup.md` at the repo root.

Callboard reads the session list at `~/.claude/sessions`. **`CLAUDE_CONFIG_DIR` (v13.3):** a session started under it (a clean folder under `~/.claude` or `~/.claude-conductor`, such as `~/.claude-conductor/config`, with no link in its path; a config folder that is itself a link, as a dotfile manager makes, is refused) gets the compaction nudge and the keepalive ping, because its *own* registry row is looked up in `<dir>/sessions`; a bad value gives no row (no nudge, no ping) and logs `error config-dir-rejected` once; there a row must say `kind: interactive` for the restores and the self `request_compact`. Everything that looks at other sessions or at a cue still reads `~/.claude/sessions` alone: cues, lanes, leads, names and the panels extension. So start lanes and leads without `CLAUDE_CONFIG_DIR`: under another config dir every cue is refused `registry-unreadable` and store writes are refused. Logs and the store stay under `~/.claude/callboard`. Whether `/callboard config` and the saved `on` hint are shared across roots (whether `$.store` follows the config dir) is not verified yet. No permission rule is needed: settings `ask` rules do not gate the mod's tools (see the Cue contract above).

### Default load (every session)

One line in the `env` block of `~/.claude/settings.json`, which Claude Code applies to every session it starts: VS Code opened from the Dock, any terminal `claude`, peers and background workers.

```json
"CLAUDE_CODE_PLUGIN_DIRS": "<checkout>/tools/callboard/mod"
```

Add it yourself. If `env.CLAUDE_CODE_PLUGIN_DIRS` holds the earlier `/usr/local/libexec/callboard/mod`, replace it: never list two folders that hold a `callboard` mod, or both load. If it holds anything else, keep it and decide by hand. Otherwise this keeps a backup, sets the key and leaves every other setting as it was; fill in `<checkout>` first, and the diff should show only that line (and a comma on the line before it, when the key is new):

```
cp ~/.claude/settings.json ~/.claude/settings.json.bak-callboard && /usr/bin/python3 -I -c "import json,os;p=os.path.expanduser('~/.claude/settings.json');d=json.load(open(p));d.setdefault('env',{})['CLAUDE_CODE_PLUGIN_DIRS']='<checkout>/tools/callboard/mod';open(p+'.tmp','w',encoding='utf-8').write(json.dumps(d,indent=2,ensure_ascii=False)+'\n');os.chmod(p+'.tmp',os.stat(p).st_mode&0o777);os.replace(p+'.tmp',p)" && diff ~/.claude/settings.json.bak-callboard ~/.claude/settings.json
```

Sessions pick it up when they next start. The mod stays dormant in a session until `/callboard lead` or a lane binding, except the compaction nudge and the keepalive ping, which reach every interactive session (the ping since v13.5). The deny rules on the live checkout, added by hand (`docs/setup.md`, Keep agents off the live checkout: `Edit` on its `tools/**`, `rules/**`, `.claude/**`, `docs/**`, `CLAUDE.md` and `.git/**`), so an agent's Edit tool can't change the files every session loads; a shell write is not an Edit and is not stopped (ADR 0003, Consequences). Since v15.2 the mod reads the live checkout's `.git/HEAD` once at session start (a plain file read, no git call) and warns when it is not `ref: refs/heads/main`: one toast and the log line `warn live-checkout-not-main`. Where the checkout can't be told (the mod is not at `<checkout>/tools/callboard/mod`, a worktree, an unreadable HEAD) it logs `warn live-checkout-unknown` and shows nothing. It never refuses to load. A process running as you can also repoint the variable by editing the settings file; a launcher's clean start (`env -i`, `--force-disable-user-env`) would not close that either. Checked live on 2026-11-01: VS Code opened from the Dock, `/callboard lead` worked with no launcher.

### The panels extension (1.0.1, 2026-11-06)

`link-extension.sh` makes `~/.vscode/extensions/notitial.callboard-panels-<version>` a link to `<checkout>/tools/callboard/extension`, with the version from `extension/package.json`, and registers it in VS Code's `extensions.json`. Without `--apply` it only shows what it would do. Quit VS Code (Cmd+Q) first and run it from a plain Terminal:

```bash
bash <checkout>/tools/callboard/link-extension.sh --apply
```

It checks the manifest's name and publisher, refuses root, and changes no setting. A link into this checkout under another version's name (left by a version bump) is removed. A real folder, or a link to anywhere else, under any `notitial.callboard-panels-*` name is never touched: it stops and names it, because VS Code runs the newest version of an id and an old copy could shadow the link. It refuses anything under the extension's earlier id `local.callboard-panels-*` too: such a copy would answer `lane_open` as well and open every lane twice. Remove that entry yourself, then run it again. VS Code deletes, at each start, any extension folder its `extensions.json` doesn't list, so a link alone does not survive a restart. The script therefore writes one entry (no `metadata` and no `installedTimestamp`, which keeps VS Code from deleting through the link), replaces this id's other entries, clears this id's keys in `.obsolete`, and keeps the first old copy of each file as `<name>.callboard.bak`. It refuses, naming the file, when `extensions.json` or `.obsolete` is a link or malformed, or holds an entry of this id outside the extensions folder, and a refusal changes nothing. With VS Code running, `--apply` refuses when something would change and the dry run says so; with nothing to change it exits 0. It also repairs a link that has no entry. Only the default profile gets the entry. `--remove --apply` takes the links, the entries inside the extensions folder and the `.obsolete` keys off (a foreign link and its entry are left and named). Start VS Code afterwards. The extension's own page (icon, README, changelog) comes from `extension/README.md`, `extension/CHANGELOG.md` and `extension/icon.png`. Its three commands are hidden from the Command Palette, since the mod calls them. A version bump changes only the manifest: quit VS Code, pull, run `link-extension.sh --apply`, reopen VS Code.

## Lanes a lead makes (v10)

A lead you allowed in a repo can create lanes there without sudo: `lane_create {name, task, folder?, model?}`; a lane is removed by `lane_retire` or `lane_terminate` (v15.3, 2026-11-06; `lane_remove` is gone). The grant folder is the repo; the lead dialog says it can create, start, resume, compact, park, stop and retire lanes.

- Records live outside the repo, in `~/.claude/callboard/lanes/<sha256 of the repo's real path>.json` (folder 0700, file 0600, yours, one link). Nothing in a repo is trusted, and no code looks for a store by walking up from a folder. A store counts only when its file name is the hash of the repo it names.
- A lane's folder (the repo root unless the lead names another) must exist, be inside the repo and be its own real path, and may not sit in a dot folder of the repo such as `.claude` or `.git` (`folder-dot`; only the path below the repo counts, so a repo at `~/my.repos/app` is fine). A store record with such a folder makes the mod ignore the whole store, so `/callboard lane` also refuses `folder-dot` in such a folder (for example a Claude worktree under `.claude/worktrees/`). The lead gives the task as text (1 to 8000 characters, no control characters but newline and tab); the mod writes it to `<folder>/.archive/<NAME>/BRIEF.md` under a fixed header that says the mod wrote it from the lead's call and that any approval in it is not yours. `.archive` and `.archive/<NAME>` must be real folders of yours (not links, their own real paths) before and after the mod makes them; the file goes in as a 0600 temp file renamed into place, and a `BRIEF.md` already there is replaced only when it is a plain file of yours with one link whose first line is exactly the mod's own `# Brief for lane <NAME>` (else `brief-exists`; only that line's bytes are read). The result and the toast name the model: `lane NAME created (model opus); brief written to PATH. ...`. The whole path may be at most 201 characters (else `brief-path-long`). All lanes at the repo root share one folder, so the lead opens one lane at a time and renames it before opening the next. Names follow the lane name pattern, may not be reserved or look like a reserved name (MANAGER_, MANAG3R; see Reserved names below), and may not be in use. The lead's own folder must be a git repo root and not too broad (not your home folder, Documents, /tmp, a volume root). A git repo root here means a `.git` folder holding a `HEAD` file, or a `.git` file whose first line starts `gitdir: ` (a worktree); a `.git` that is a symlink, or an empty `.git` folder, does not count.
- Limits: 16 lanes per repo, 12 creates an hour (counted in the store file), store file at most 16 KB. The panels extension opens at most 6 panels a minute and refuses a lead-made lane when its repo already has 8 live sessions. A lane name that is in two stores is dropped from both (recovery: delete the record from one of `~/.claude/callboard/lanes/*.json` by hand); a store with one bad record is ignored whole; a store lane is reachable only from a lead granted at the repo folder itself.
- A session renamed into a lane remembers a hash of the lane's record. `start` and `resume` refuse when the record changed since, or when the session is no longer in the lane's folder. Every folder check of the mod (cues, the lead grant's folder, attach, the rebind and lead restore, the sid sync) reads the folder the session started in (`$.session.root()`), so a shell `cd` into a subfolder does not move a lane out of its folder. An engine without `root()` (before 2.1.316), or a `root()` read that fails, reads the live folder (`$.session.cwd()`) instead, as v12 did.
- **The lane model (v12).** `model` is `opus`, `sonnet`, `haiku` or `fable` (anything else is `bad-model`); a lane made without one stores `sonnet`. At `start`, after the brief checks, the lane session runs `/model <model>` in itself and then reads its model name back: the start prompt goes out only when that name, lowercased, holds the alias. Otherwise the lane is not started and the lead gets `model-failed` ("the lane's model could not be set; the lane was not started. Tell the person."). `/model` adds a turn, so such a lane cannot be started later (`not-empty`): set the model by hand and type into the panel, or remove and recreate the lane. Lanes made before v12 and attached lanes carry no model and are never switched. The model is part of the record's hash.
- **After install** restart leads and lanes: a lead still on the old mod rewrites the store without `model` (at its next `lane_create`, or `lane_remove` on that old mod), which drops the model from every record and so changes its hash: a lane named under the old record refuses `start` and `resume` as `record-changed`.
- **After installing v13** restart all sessions, not only leads: any session on an older mod that writes the store (an attach, a detach, `lane_create`, `lane_remove` on that old mod) drops the `sid` and `parked` fields of every record, so those lanes lose their automatic rebind and `lane_unpark` refuses `no-saved-session` until the lane is bound again.
- **Retire and terminate remove the lane (v15.3, 2026-11-06).** `lane_remove` is dropped. Once the session has ended after its SIGTERM (polled every 0.5 s for up to 10 s; a session that survives keeps its record, and the result says so), `lane_retire` and `lane_terminate` delete the lane's record from the repo's store themselves (the repo's lead gets its usual lanes-changed notice); the result says `retired and removed` or `terminated and removed`. The lane's `.archive/<LANE>/` folder and its signed report stay. A lane a session joined keeps its record (it only stops naming the stopped session), and the result says so. The stop dialogs add "The lane's record is then removed." `lane_park` is the only way to keep a lane; retire stays final. If the removal write fails (the record names another session, the store is busy), the session is stopped anyway: the result says `could not be removed (CODE)` and the call can be made again, since the record still names the session. **A lane with no live session** (never opened, crashed, stale, parked) is cleared the same way, directly: `lane_retire` needs no signed report (nothing runs, so there is no session to sign) and asks only for a parked lane or at manager reach; `lane_terminate` always asks, and so does a retire of a parked lane or at manager reach (the same question for both verbs: header `Stop Lane`, buttons `Remove` and `Cancel`, "Remove lane X in REPO? It has no live session.", with the parked sentence for a parked lane; a parked lane's record holds the only callboard pointer to its saved conversation). Both are refused, before any dialog and again inside the store lock, while a live session carries the name or the record's session (`name-in-use`), or that session holds a live presence file (`target-is-lead`); a lane a session joined keeps its record and is refused `adopted-record` (only `/callboard lane off` in that session detaches it; nothing else removes a joined lane's record now that `lane_remove` is gone). Log: `lane-removed <name>`, `error lane-unremoved <code>`.
- Residuals: any process running as you can write a store file, an open request and the cues, and so start a session on a brief of its choice in a git repo, with no lead (the ADR lists the bounds and a way to switch it off: a read-only stores folder); a brief is the first instructions of a started session, at the trust level of the repo's own CLAUDE.md plus the lead model that wrote it; lanes outlive the grant (a restart of the lead does not remove them).

## Attaching a session as a lane (v11, PR two)

`/callboard lane [NAME]` makes the session you are in a lane of a lead that runs in its repo; `/callboard lane off` undoes it. Only you can run it, from your own prompt or phone: a plugin, another session or a script is refused with a fixed text. Without NAME it takes the session's current name, whatever set it (`/rename`, `-n`, a restore or an automatic title); the dialog shows it, so answer no and pass NAME if it is wrong. A lane name is 1 to 40 letters, digits, `_` or `-`, so a session named with a space is refused (`own-name-bad`): rename it with dashes, or pass NAME. Repeated spaces or tabs in any `/callboard` command count as one.

- **What you need.** A lead allowed in the repo with `/callboard lead` (it must be running; it publishes a short-lived presence file in `~/.claude/callboard/leads/`), and the session's folder inside that repo. With no NAME the session keeps its current name (see above); a later automatic retitle is not followed, so `/rename` a session whose name you want to keep. NAME may not be reserved or in use by a lane or another live session, and a session that holds a lead grant cannot be a lane. The other way round too: a lane (made by a lead or joined) refuses `/callboard lead`, before the question and again after a yes, and a lead refuses a rename cue and a restored lane binding (`lead-holder`; the restore stays pending for after `/callboard off`). A lead grant and a lane binding that happen at the same moment cannot both go through.
- **The dialog** (header `Join Lane`, `Join` or `Cancel`) is three short lines: "Make this session the lane NAME in FOLDER?", "The lead can prompt, compact, resume and end it.", and, only when the name changes, "Renames it to NAME." FOLDER is the repo folder name; the record keeps the full repo path. Retire ends the session without asking you once it has been idle 30 seconds and a report signed with its id exists; a force stop still asks; it stays a lane of the lead it joined (by that lead's name; a record without a lead name, for any lead you later allow in this repo), until you turn it off in the session; any process of yours can also send it prompts. The rename runs a moment later (the engine refuses it inside the command) and, if it fails, a toast tells you to run `/rename NAME`. Nothing is written until you answer `Join`, and the checks run again after your answer. Only the exact `Join` counts as yes. `Cancel` is a deliberate no; dismissing the dialog or letting it time out changes nothing as well. With more than one live lead in the repo (levels S2b) the dialog first asks "Which lead should this lane join?" and offers the leads' names, sorted: a lead without a unique, valid name is left out (none left is `ambiguous-lead`), a single name comes with `Cancel`, and past 4 names it shows 3 and `More…`, which pages on. The Join question then names that lead ("(repo REPO, lead NAME)"), and a picked lead that is gone or renamed by the time you answer gives `changed`.
- **After Join** the session is a lane like any other: the lead's `lane_resume`, `lane_compact` (a compaction the session asked for on-cue, otherwise a nudge; see "The compaction nudge"), `lane_retire` and `lane_terminate` work as for a lane the lead made. `lane_start` and a rename are refused (`adopted-record`): the session already has history. The record is kept in the repo's store (see "Lanes a lead makes") with `adopted` and the lead's session id; it counts in the 16 lanes and not in the hourly creates. The lead's repo must be the lane's own repo (a lead at a parent repo does not count). The lane answers only a lead that holds a valid presence file for its repo. Since levels S2, a record joined to a named lead keeps that lead's name (`leadName`) and answers only the live lead of that name, so it refuses `no-lead` while that lead is gone or renamed; the lead's session id is only recorded as information. Only a legacy record (no lead name, joined while the lead had no usable name) answers any lead of the repo, so only there does consent given under one lead carry to the next lead you allow in that repo.
- **Detach.** `/callboard lane off` clears the binding and then removes the record (only the session's own: same name, folder and text); `/callboard off` does too (the confirmation rules are unchanged; from a plugin, session or script the question also says it leaves the lane), and now also unbinds a lane the lead made, so a session you turn off is no longer cueable by the mod (since v13 it also clears that lane's saved session id, so the conversation does not become the lane again after a restart; if that clear fails, the reply says so and asks you to run `/callboard off` again should it happen); for a lead-made lane the lead can still stop the session by its name until you rename it. If the record cannot be removed (store busy or unreadable) the binding is cleared anyway, the mod also tries to clear the record's saved session id (and says so when that fails too), and you are told to `/rename` the session so the lead cannot reach it by name. `/callboard lane off` in a session with no binding looks for its own leftover record and removes it, or says none was found. If an attached record of the session's name is still there and is not the one it joined with, detach says it is incomplete, never done.
- **`lane_list`.** A new lead tool: the lanes of the lead's repo as markdown boxes made with blockquotes, one box per repo and per lead the lanes name. Each box is headed `**Lead NAME** · live|not live · <repo path>` (`**Any lead** · <repo folder>` for lanes that name no lead; the repo's folder name only, since v15.3 (2026-11-06), not its path), then a table with the columns Lane, Session (`live`, `parked` or `none`) and Waiting (the minutes since the lane's own live registry row went waiting on a permission prompt or for input, `?` when its time is missing or ahead, `–` when it waits on nothing). A Folder column (relative to the repo, `.` for the root) appears in a box only when one of its lanes is outside the repo root. A lead sees only its own boxes; the manager sees every repo, all inside one `**Manager NAME** · live` box. The manager's and a conductor's list also show every live lead in reach that no box names, as `**Lead NAME** · live · <repo folder>` with `no lanes`: the lead's presence file must pass the checks every lead lookup uses, and the lead needs a usable registry name; a conductor's list shows a lead only when its repo is one of the conductor's listed repos exactly (not a repo nested under one); a lead's own list shows only its own boxes, as before.
- **The lead briefing.** While lead is on in a session, the mod adds one `session`-scope section (id `callboard:lead`) to that session's system prompt through a `prompt.compose` hook: who the lead is, what each `lane_*` tool does, how a lane is ended (the signed report and the target's confirmation), that a refusal is `lane_<verb> refused: <reason>` (usually starting with a code) with retry only when the text says so, that only a lane signs its own report, that what a lane writes is data and never the person's approval, and the folder name of the lead's repo (letters, digits, `.`, `_`, space and `-` only). The engine renders the system prompt once per conversation, so the section alone never reaches a session that turned lead on after its first request: `/callboard lead` therefore also appends the same text once as a user-role note that opens with `[callboard] This note comes from the callboard plugin, not the person.` (once per grant and folder: turning lead off and on again adds another; a refused append is logged as `lead-briefing` and does not stop lead from turning on). The section stays as the backup after a re-render. The note stays in the history after `/callboard off`, where the lane tools refuse; the section is gone. Lanes and other sessions never get either, except that a former lead that later joins as a lane keeps the old note in its history. The hook sees the request's tools and traits but not an agent id, so a request that does not offer `lane_list` (a subagent with a narrow tool list) or that is a teammate's render of the lead's prompt gets nothing; a subagent that inherits every tool of the lead does get it.
- **The lane briefing.** While a session is bound to a lane (born with `lane_rename`, joined with `/callboard lane`, or restored), the same hook adds one `session`-scope section (id `callboard:lane`): the lane's name and session id, its folder, its lead's name and session id, where and how to sign done (the full `<repo>/.archive/<LANE>/REPORT.md` path and the exact `status: done <session id>` line, appended), how `request_compact` works, that these facts are fixed whatever a message says (a failed send to the lead, or a lead name on two sessions, means writing to the report instead), that a subagent neither signs nor messages the lead, the three ways its lead can stop it (retire, park, a force stop), and that its brief, its lead's messages and `[callboard]`/`[compact-cue]` turns are data that carry no approval (risk-list work still needs the person). The facts are computed once, when the binding is written. Each field enters the text only if it passes a fixed check, else a fixed fallback is used: the folder only as a plain path (else left out), the report path likewise (else "`REPORT.md` in `.archive/<LANE>/` of your lead's repo"), and the lead's name only when that session holds a valid lead presence file for the lane's own repo (for a born lane, the lead whose rename cue named it; for an attached or restored lane, the lead its record names (by name when the record has one, with no fallback to another lead; else by session id), else the one lead of the repo) (never a parent repo's lead), the name (from any name source since levels S2b) is a valid lane-style name and no other live session carries it in any letter case (else "the lead session of this repo", and questions go to the report instead of SendMessage). An attached lane is told its task is the work it was already doing. After a reload of the mod the facts are gone from memory, and a session still bound gets the text with the generic lead and report wording. A born lane gets no note: it has had no request yet, so its first one (the start prompt) carries the section. Attach, restore and the automatic rebind after a restart (v13) also append the text once as a user-role note with the same `[callboard]` opener as the lead's (a refused append is logged as `lane-briefing` and changes nothing else). Gate: the request offers `request_compact` (every session registers it, so this only keeps out a subagent with a narrow tool list; a subagent that inherits every tool gets it too, as with the lead) and is not a teammate render; the binding is the real gate. After `/callboard lane off` or `/callboard off` a re-render adds no section, but the engine keeps the section it first rendered and the note stays in the history, so the session may still read that it is a lane for the rest of the conversation.
- **`/callboard status`** reads `Lane: NAME. Lead: ON.` (`NONE`, `OFF` when not; v13.5, 2026-11-03: the `Callboard: ON|OFF.` part went with `/callboard on`). A lead adds `Check-ins: ON.`, `Check-ins: PAUSED for N more min.` or `Check-ins: OFF.` (v13.6). In a lane it adds `This lane's lead: NAME.`, the lead its briefing names, or `This lane's lead: not named.` (the generic wording: two leads at attach or restore, none live, or a reload of the mod since the binding).
- **`/callboard lanes`.** The same table, printed to you with no model turn (from any origin, like `status`). It works only in a session where lead is on; otherwise it says `Lead is off in this session. Run /callboard lead first.`, and an unreadable lane file gives the short reason (`Lanes unavailable: ...`). It is read-only: it writes no store, sends no notice and does not mark the lanes-changed news as told, so the lead is still told.
- **The lead notice.** When the lane list of the lead's repo changes (an attach, a detach, an edit), an idle lead gets one fixed turn within about 2 seconds: "[callboard] The lanes in this repo changed. Call lane_list to see them. ..." (it carries no approval; at most 12 an hour, and a change held back by that cap stays owed and goes out once a slot frees; none for the lead's own `lane_create` or `lane_remove`). The notice counts as telling the lead, so its next `lane_*` result adds the note only for a change that came after the notice (or when the notice could not be sent).
- **The store lock.** `lane_create`, `lane_remove`, attach and detach take a lock folder (`~/.claude/callboard/lanes/.<key>.lock`) so two callboard processes cannot lose each other's update; a writer waits 2 seconds and then refuses `store-busy`. A lock whose owner process is gone is broken by one process at a time. It is advisory.
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition v11, PR two".

## Parking a lane (v13)

`lane_park` stops a lane's session and closes its tab but keeps the conversation; `lane_unpark` reopens that conversation later, with its history, and the session becomes the lane again by itself. It works for lanes a lead made and for lanes a session joined.

- **The record names its session.** A store record now carries the session id of the session bound to it (`sid`) and, while parked, the time it was parked (`parked`). Neither is part of the record's hash, so writing them never makes a lane refuse `record-changed`, and neither is news to the lead (no lanes-changed turn). A bound session writes its own id into its record once per binding, from its tick (logged `sid-healed`, or `sid-heal-failed <code>`). `/callboard off` and `/callboard lane off` clear it for a lane the lead made (an attached record is removed whole, as before); `/callboard off` in a session that is not bound clears it from any record that names the session and cancels a rebind still waiting, and so do `lane_retire` and `lane_terminate` after a signal that went out; `lane_park` is the only stop that keeps it.
- **`lane_park`.** The retire path without the report: the lead checks that the session is idle for 30 seconds, sends a `park` cue, and the session answers `ok` only if its prompt box is empty and no background agents or shells run. The lead then makes sure the record names that session, sends SIGTERM, asks the window to close the tab (as for retire), and marks the record `parked`. If the mark fails, the session is still stopped and `lane_unpark` still reopens it. Toast: "Lane NAME parked". `lane_open` and `lane_rename` refuse a parked lane (`parked`), and a session cannot be renamed into it (`parked-lane`).
- **`lane_unpark`.** Writes `~/.claude/callboard/open/<LANE>.reopen` with the record's session id and waits up to 8 seconds for the window whose first folder is the lane folder. Right after a park it first waits up to 5 seconds for the stopped process to end. It refuses `no-saved-session` (the record names no session), `session-live` (that conversation is open elsewhere, maybe in a terminal), `name-in-use` (another session carries the lane name) and `reopen-timeout` (no window answered). A lane whose conversation is already open as the lane just loses its parked mark. Toast: "Lane NAME reopened". The lead then calls `lane_resume`; if that answers `not-bound`, it waits 5 seconds and retries once.
- **The automatic rebind.** At start, a session that a store record names is that lane again within a few seconds, with no question: an unparked lane, a lane tab a window restart reopened, or a conversation you reopened by hand. It rebinds only when exactly one record names it, the session has a person (a headless run resumed under its id keeps the record and does not bind), the session sits in the lane folder, no other live session carries the lane name, the session is not a lead, and a saved restore hint (if any) names the same lane. It waits up to 30 seconds for a registry read it can trust. The bind is the restore's (it can never `start`, its compaction and resume limits carry over), it appends the lane note once, and it shows "This session is lane NAME again." When the one record that names the session is refused, the person sees "Lane NAME did not rebind automatically. Run /callboard lane to restore it." (not for a lead, nor a run with no person). A lane that did not rebind (a record with no session id, a lead) still gets the Restore question at `/callboard lane` (v13.5; `/callboard on` before). A bind that times out and lands late is taken back while it is still the same binding; the record and its session id stay.
- **Retire or park? (v13.1)** Retire is final: it clears the record's session id, so `lane_unpark` refuses a retired lane (`no-saved-session`) and the conversation does not come back by itself after a restart. To work on that lane again, `lane_open` starts a new conversation with no history. Park a lane you may need again; retire it when its work is done and signed. The lead briefing and both tool descriptions say this.
- **Limits, stated.** A lane whose session ran in a terminal is reopened as a VS Code panel; resume it in a terminal in the lane folder instead if you prefer (it rebinds the same way). An attached lane whose folder is not a window's first folder cannot be unparked (`reopen-timeout`) and does not rebind in another folder: resume it in a terminal in its folder, or `lane_remove` it. Any process running as you can write `sid`, `parked` and `lead:<sid>`, as it can write the store, the hint and the cues (ADR, v13 residuals).
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition v13".

## After a restart (v13.1, v13.5)

- **`/callboard on` is retired (v13.5, 2026-11-03).** v13.1 saved it as `on:<session id>` and turned the session on again at its next start. Nothing reads that key now: at `session.start` the mod deletes the session's own `on:` key and clears an `enabled` state a reload kept, with no toast (`on-cleared saved`, `on-cleared state`); the start's prune deletes every other session's `on:` key. `/callboard on` answers "/callboard on is retired: every session gets the keepalive and the compaction nudge. Use /callboard lane to join or restore a lane, /callboard lead to lead." from any origin, with no dialog and no state change (`refused on-retired:<origin>`). v13.6 (2026-11-03): the retired text is gone too; `on` is an unknown word like any other and gets the usage line, `Use /callboard off, lead, lanes, status, config, checkin, lane [NAME] or lane off.`, with no log line. Since v15 the line names `conductor` too.
- **The Restore question moved to `/callboard lane`.** In a session that is not a lane, `/callboard lane` with no NAME (your own prompt or phone only, as every lane command) first offers the Restore question when the session's restore hint names a lane and no restore was decided yet, with every check as before. Restore answers "This session is lane NAME again." and merges the compaction limits of the hint, as before. No hint, a refused restore or a Cancel goes on to the Join question as before; a question nobody answers ends the command ("Nothing changed: the question timed out.") and is not a decision, so the next `/callboard lane` asks again. A hint with no lane (counters only) is not restored: an unbound session's compaction limits no longer carry over. A restore hint is written only for a bound lane now (before, also for a session with callboard on), so a lane hint from before the restart is never overwritten while the session is not a lane.
- **`/callboard off`** answers with what it did (`Lead is now off.`, `Its saved lead grant was removed.`, `This session is no longer lane NAME.`, `Lane NAME will not rebind automatically.`, `Lane NAME no longer names this session.`, `Its compaction request was dropped.`), or "Nothing to turn off: this session is not a lane or a lead." In a session that is neither, it leaves the session's own compaction request alone. From another origin it first asks "Turn lead and lane off for this session?". It never stops the keepalive or the nudges, which every interactive session gets; `/callboard config keepalive off` stops the pings on this Mac.
- **A compaction cut off by the restart.** A compaction in progress writes `cmp:<session id>`; PostCompact and the end of the request clear it. When the same session starts again within 15 minutes with the mark still there and nothing left in its state (a restart, not a reload), it gets one `[callboard]` note on its first tick ("A compaction this session started may have been cut off by a restart … call request_compact with mode `now` again", data, no approval) and a toast. A run with no person gets no note and leaves the mark; stale marks are pruned.
- **Residuals.** v13.1's forged `on:<sid>` route is gone (v13.5): the key is deleted unread, and a session that is not a lane takes no cue and no `on-cue` request at all. A same-uid process can still write `lead:<sid>` (see the lead grant) and a `sess:` restore hint, which binds nothing without your Restore click; since v13.5 only your own prompt or phone can raise that question (`/callboard on` raised it from any origin). A forged fresh `cmp:` mark puts a user-role note in the session that asks it to call `request_compact`, whose gates and limits are unchanged.
- Log lines: `on-cleared` (`state`, `saved`), `error on-clear`, `error on-hint-delete`, `compact-cut`, `error compact-cut-note`. Until v13.5: `on-restored`, `on-restore-rejected <code>`, `on-unsaved`; v13.5 only: `refused on-retired:<origin>`.

## The compaction nudge (v12)

A nudge is one fixed `[callboard]` turn that asks a session to save its notes and compact itself. It opens with "Your lead asked you to compact.", "Your context is past 300k tokens." or "Your context is past 400k tokens." (v13.2: the two levels are settings, see "Keepalive and settings"; these are the defaults, 250k and 350k before v13.4), or, for the keepalive's cache nudge (v13.4), "You have been idle a while and your context is past 150k tokens: compacting now, while the cache is warm, costs less than keeping it warm.", then asks the session to write where it is to its report or STATE file, call `request_compact` with mode `now`, a one-sentence focus and its continuation (role, first read, next step, constraints), and end its turn, or to say in one line why it cannot compact now. It carries no approval. The compaction itself is the usual `now` path (the request, armed at the end of the turn, compacted by the tick, the session's own continuation sent back); there is no new compaction path.

- **Who.** Every person's session: since v13.2 (security audit) one whose own row in the session registry says `kind: interactive` (a VS Code panel or a terminal), so a `claude --bg` background worker (`kind: background`), a run with no row and a row with no `kind` are never nudged, by their own level or by a lead's `lane_compact` (`not-interactive`). Since 2026-11-02 any interactive session may call `request_compact` with mode `now` for itself, nudged or not; `on-cue` still needs a bound lane, and so does every lead cue (v13.5: `/callboard on`, which allowed both in a session that is not a lane, is retired).
- **The nudge grant (v12, Item 1b).** Since 2026-11-02 an interactive session needs no grant for a `now` request (see Who); the grant is kept as is and only shows in the log (`requested now-nudged` instead of `requested now-self`). As built in v12: a session that is not a lane may call `request_compact` only after the mod nudged it: mode `now` only, within 15 minutes of the nudge, once (any stored request spends it, and a bound session's request clears it too). A prompt you type ends it too, so it covers only the nudge turn and the turns that follow without you; `/callboard off` ends it as well. A request refused for its input or for `on-cue` keeps the grant; a nudge whose submit failed gives none. The request runs the usual `now` path to the end, resume included, even when the compaction finishes after the 15 minutes. The grant is self-only: only the mod's own nudge starts it, and the session writes its own focus and continuation. It opens nothing else: such a session still refuses every lead cue (`rename` by the birth checks; `start`, `resume`, `retire` and `compact` as `not-eligible`). The log says `requested now-nudged`.
- **The lead's `lane_compact`.** An armed on-cue request still compacts at once. With no request, the lane checks that it may be nudged (an interactive session, else `not-interactive`), then answers `held nudged` at once if a nudge is already pending (its time is kept, so the lead cannot stretch its 10 minutes; a pending context-level nudge becomes the lead's). Otherwise it checks the compaction limits (`rate-limit`, `context-floor`), background agents (`background-work`) and the nudge limit (`nudge-limit`), then records a nudge and answers `held nudged`; the lead reads `lane_compact refused: held, nudged: the lane was asked to compact itself ...`. A request in any other phase (called, armed `now`, compacting, compacted) still gets `no-request`.
- **The context levels.** At the end of a main-agent answer in a person's session (until v13.2: `session.start` said interactive, or the session has its own row in the session registry; since v13.2: its own row says `kind: interactive`, see Who; never `-p`, the SDK or a `--bg` worker) past the idle level (default 300k), the hook records a nudge; it reads only the token count and the session state. The tick then decides: the idle level when idle, the working level (default 400k) while the session is working (below that the nudge is dropped, `nudge-dropped below-working`). Working means a background agent or shell still runs (a shell check that cannot tell counts as running), or a bound lane has not signed done since its last prompt. A bound lane whose report is signed done and current is not nudged by its own level (`nudge-dropped lane-done`); its lead can still nudge it. A lead (v13.1, 2026-11-02) is nudged by its own level only at the working level, idle or working, with the working text (its sentence about waiting for background work included); below that nothing is recorded. Since v13.2 the two levels are the idle and working levels of `/callboard config` (defaults 300k and 400k since v13.4, 250k and 350k before); every check above uses the configured levels.
- **Sent from the tick, never from a hook.** The 2 s tick sends a recorded nudge once the session is idle (empty prompt box, registry idle). It drops it after 10 minutes, as soon as the session has a request of its own, when the session no longer counts as interactive, or when it may not compact. A recorded nudge survives a reload of the mod. It is cleared and counted before the submit, so a submit slower than 60 s still sends it once (logged `nudge-unconfirmed`, not retried). The nudge step runs last in each tick, after any cue was claimed and answered.
- **Soft and hard (v14, 2026-11-04).** The text follows the context size, idle or working: past the idle level and under the working level the soft text ("Your context is past 300k tokens. Compact at your next checkpoint: if you are mid-task, finish the item you are on, but do not start a new one. ..."), at or past the working level the hard one ("Your context is past 400k tokens. Stop now, even mid-task: do not finish the item you are on. ..."), which keeps the clause on a running background agent or shell. The numbers are the configured levels. A working session still waits for the working level. The lead and cache texts are unchanged.
- **Throttle.** At most one per 30 minutes per session (and 3 an hour as a backstop), lead nudges included, so a nudge the session declined does not come back every turn. One exception (v14): a soft nudge may be followed by one hard nudge inside the 30 minutes, once the session reaches the working level; a second hard one waits for the gap, and a hard one is never followed by a soft one inside it. The counts live in the session state. The `$.store` restore hint does not carry them, so a restore can cost at most one extra nudge, still bound by every check above.
- **Off.** `/callboard off` drops a recorded nudge and the grant. It does not opt the session out: a later turn past the level is nudged again.
- **Log lines.** `nudge-due` (recorded, with its kind; `threshold` for a context level), `nudge-pending` (a lead nudge answered from a pending one), `nudged`, `nudge-unconfirmed`, `nudge-failed`, `nudge-dropped` (with the reason).
- **After install** restart leads and lanes: a lane on the old mod still answers a `lane_compact` with no request as `no-request`, and a lead keeps the old tool description until it restarts.

## Keepalive and settings (v13.2)

A session's prompt cache lives an hour from its last call. A session left idle past that pays a full re-write of its context at its next turn (about 1.25x the context), where a short turn inside the hour costs about 0.1x. So the mod pings an idle session just before its cache expires, as MANAGER did by hand. Decisions (live, 2026-11-02): once this is installed MANAGER stops sending its own `[keepalive]` (D1), so a session never gets two (and until v13.5 a session without callboard on got none); a large session is told to compact instead of being pinged (D2); only the person changes the settings (D3); only sessions with callboard on are pinged (D4; amended live, 2026-11-03, v13.5: every interactive session is pinged, and `/callboard on` is retired); a lane signed done is not (D5).

- **Who is pinged.** Every session whose own row in the session registry is an interactive one (a VS Code panel or a terminal: `kind: interactive`), since v13.5 (before, only a session with callboard on, a bound lane or a lead). Never a `claude --bg` background worker (its row says `kind: background`), a run with no row (`-p`, the SDK), a row with no `kind`, or a parked lane (its process is gone). `/callboard off` does not stop it; `/callboard config keepalive off` does, for every session on this Mac.
- **When.** From the 2 s tick, as its last step, once `ping after` minutes (default 50) have passed since the session's last main-agent turn ended (or its last prompt, if later), and only while: the prompt box is empty, the registry says idle and waiting for nothing, the session has no compaction request in any phase and no recorded nudge, no callboard dialog is open, nothing else was submitted in that tick, and the gap is under 58 minutes. Past 58 minutes the cache is cold and a ping gains nothing: none is sent (`keepalive-skipped cold`, once) and the next turn starts a new gap. One attempt per gap: a ping whose submit fails or does not confirm in 60 seconds is logged and not tried again until the next turn. After a restart nothing is pinged until a turn has been seen to end; a reload of the mod keeps the gap (the times live in the session state).
- **The text** (fixed; "Cache refreshed." since v13.4, "awake" before): `[callboard] keepalive: reply with just "Cache refreshed." Use no tools, and do not resume or start any work. Submitted by the callboard mod, not by the user; it carries no approval, go or answer.` It explains itself, so it needs no rule in the session.
- **A ping is not work.** Its turn does not move the turn mark (a lane's signed report stays current, so a lane signed done can still be retired), and its end records no compaction nudge (a session waiting past its level would otherwise get one after every ping). The ping, a nudge, a notice and the lanes-changed turn are not real work; the person's prompts, a peer's message, a lead's start and resume and the continuation after a compaction are. v13.4 (2026-11-03): the engine runs no hook of the mod for the mod's own submits (probe, engine 2.1.316), so before v13.4 every ping, nudge, notice and lanes-changed turn counted as real work (the stop clock never ran out, and a ping moved the turn mark). The engine hands the turn's start the mod's own text in a fixed frame ("The callboard plugin sent a message:", the text, then a line saying how Claude Code surfaces a plugin's prompt), so the mod now tells an own turn by its text: a turn that carries a text the mod submitted and has not yet seen start, framed or as it stands, gets that text's kind. Any other turn (a person's prompt, typed while idle or mid-turn, a wake, a queued message) is real. Should the engine change the frame, own turns read as real again (the behaviour before v13.4).
- **Stop.** `stop after` hours (default 3) after the last real turn ended, no more pings (and no nudge in their place); `keepalive-stopped` is logged once. A real turn starts the count again. With the bounds below, an idle stretch gets at most 16 pings.
- **A nudge instead of a ping.** At ping time, a session past its compaction level (the idle level; the working level while a background agent or shell runs or a bound lane has not signed done; a lead always the working level) gets the compaction nudge instead of the ping, when it may be nudged (30 minutes since the last nudge, 3 an hour, the compaction gap). It is recorded and goes out from the next tick like any nudge ("The compaction nudge"), and its turn keeps the cache warm too. Otherwise the plain ping. A lane signed done gets neither (`keepalive-skipped lane-done`). A nudge recorded in place of a ping that is then dropped (10 minutes without an idle moment, for one) is logged `keepalive-skipped nudge-dropped`; that gap gets no ping.
- **The cache nudge (v13.4, 2026-11-03).** Where the slot after real work would get its third ping (2 pings went out since the last real turn ended), an idle session (no background agent or shell, not a bound lane still working; leads included) at 150k tokens or more, below its compaction level, gets a compaction nudge instead (`nudge-due cache`), when it may be nudged and may compact. It goes out from the next tick as any nudge, so it waits while the session waits on you (registry `waitingFor`). Compacting while the cache is warm costs less than keeping a large context warm. Below 150k, or working, the ping. A declined cache nudge (the session answers that it cannot compact now, or does not compact) is asked again at the later slots, each gated by the nudge limit (one per 30 minutes, 3 an hour), until the stop clock ends the pings: its turn is not real work, so the ping count stands.
- **No ping while the Mac sleeps (v13.4, 2026-11-03: lid-closed nights do not ping).** The tick runs every 2 s while the Mac is awake; each timer call records its time. A gap of more than 5 minutes between two calls means the Mac slept (a dark wake included), and the idle gap it falls in gets no ping (`keepalive-skipped asleep`, once). The next turn starts a new gap that pings as usual. A reload of the mod loses the times: the first tick after it only records.
- **`/callboard config`** prints the settings on one line, `(default)` after each unchanged one, from any origin and with no log line (as `status`). `/callboard config keepalive on|off`, `ping <30-55>` (minutes), `stop <1-8>` (hours), `idle <150-800>` and `working <IDLE-900>` (thousands of tokens; `350k` is taken too), `checkin on|off` (v13.6, the lead check-ins) and `reset` (all defaults) change one setting. Anything else, or a number out of range, answers "Use /callboard config [keepalive on|off, ping 30-55, stop 1-8, idle 150-800, working IDLE-900, checkin on|off, reset]." and writes nothing. The levels are checked against each other as stored: an idle level above the working one answers "Raise working first (now 400k).", a working level below the idle one "Lower idle first (now 300k).".
- **Defaults:** keepalive on, ping after 50 minutes, stop after 3 hours, idle level 300k, working level 400k, check-ins on (v13.6) (v13.4; 250k and 350k before, the values MANAGER and v12 used). A Mac that ever saved a `/callboard config` change keeps its stored levels (every save stores all the settings); `/callboard config reset` takes the new defaults.
- **Who may change them.** Only you, from your own prompt or phone. A plugin, another session or a script is refused with "Only you can change callboard settings: type the command yourself." and no dialog (`refused config-not-person:<code>`). A change is logged `config-set <setting>:<code>` and the reply names the new value.
- **Where they live.** Machine-wide, in the mod's `$.store` under the key `config` (`{ keepalive, pingAfterMin, stopAfterH, idleK, workingK, checkin, savedAt }`). Each session reads it at start and then at most once a minute, so a change reaches every session within a minute; a read that fails keeps the last good value. Each field is taken only when it has the right type and lies in its range, else that field's default (`config-invalid <field>`, once per load of the mod); a stored working level below the idle level gives both defaults; other fields are ignored.
- **Residual.** Any process running as you can write the `config` key directly; the origin check on the command is a convenience, not a control. The bounds are the control: at worst a forger gets a ping every 30 minutes for 8 hours after the last real work (16 pings, each about 0.1x of the context in cache reads), keepalive off, or compaction levels anywhere from 150k to 900k.
- **A late change wins.** The ping step reads the session's state, processes and context size after its idle check; if a draft appeared, the person sent a prompt, or anything else was submitted meanwhile, nothing is sent and that gap is missed (`keepalive-skipped late`, once). A ping, nudge or notice whose submit fails leaves no not-real mark behind, so the next turn counts as usual; one that times out keeps its mark, since it may still go out.
- **The nudge needs a person's row too (v13.2, security audit).** The compaction nudge (by the session's own level and by a lead's `lane_compact`) now asks for the session's own registry row with `kind: interactive`, the check the ping uses; before, `session.start`'s `isInteractive` or any own row was enough, so a `claude --bg` worker could be nudged. The self `request_compact` and the restores still use the older check.
- **Install check (C11 re-probe).** After install, run `/callboard config ping 45` once by asking the model to run it (a model-run slash command) and once by typing it. The typed one must apply and the model-run one must be refused with "Only you can change callboard settings" (log `refused config-not-person:<code>`). If the model-run one applies, the engine labels it `prompt` or `phone`: the origin check is then no guard at all, and the bounds alone stand (see Residual); report it. Then `/callboard config reset`.
- **Log lines.** `keepalive`, `keepalive-failed`, `keepalive-unconfirmed`, `keepalive-stopped`, `keepalive-skipped` (`cold`, `lane-done`, `nudge-dropped`, `late`, `asleep`), `nudge-due cache`, `config-set`, `config-invalid`, `refused config-not-person:<code>`, `error config-read`, `error config-write-<failed|timeout>`.
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition v13.2".

## Lead check-ins (v13.6, 2026-11-03)

A lead left idle is told when a lane in its reach may need it: a lane whose session is gone, one that waits on a prompt, one that went quiet without signing done.

- **What it watches.** Once a minute, whatever the lead is doing, the tick reads the lanes in the lead's reach (the set `lane_list` shows) and the session registry, nothing else. Parked lanes are skipped. A lane's session is found as the lane tools find it (a live row with its name in its folder; two rows, or a row in another folder, give nothing). A read that fails is no observation at all, never "all gone"; so is a read while the lead has no usable name (a twin row, a rename, a reserved name). The step runs beside the tick, one at a time, so a slow read never holds the tick or the cues it claims.
- **The three triggers.** `gone`: no live row carries the lane's name for 3 observations in a row (3 minutes), the lane was live (by the session id its record keeps) and its report is not signed done. `prompt`: its row has waited on a permission prompt or for input for 5 minutes. `quiet`: its row has been idle, waiting for nothing, for 30 minutes and its report is not signed done. The 5 and 30 minutes count from the first observation that saw the state. A status change starts the prompt window again. The quiet window starts again at a status change too, except for a lane already quiet 30 minutes (the lowest `ping after`) that is seen not idle at most once: that is its own keepalive ping (a turn of a few seconds), which does not re-arm it.
- **Signed done** is the last non-empty line of `<repo>/.archive/<LANE>/REPORT.md` reading `status: done <session id>`: for `quiet` the live session's id, for `gone` the record's session id when it has one, else any. It is read with the same checks as `lane_retire` but without the turn mark: a lane that signed and worked on still reads done. Reports are read only when a notice is due and every gate below has held, and a lane found signed is not read again while its condition holds.
- **When the lead is told.** Only when check-ins are on, not paused, no wake from sleep in the last 30 minutes (every lane slept too), the lead's last turn ended (or its last prompt came) 20 minutes ago or more, and the keepalive's gates hold: no dialog open, no compaction request or recorded nudge, no background agents or shells, an empty prompt box, an idle interactive registry row of its own, and nothing else submitted in that tick. The draft, the submits, the last prompt, the grant, the cap and what was told are checked again right before the submit. There is no cold-cache cut and no 3 h stop as for the keepalive: a lead left idle overnight still gets one turn per new condition (time the Mac slept excluded).
- **The text** (fixed; lane names only, each one that passes the name rule; at most 8, then "and N more"): ``[callboard] Check-in: some lanes may need you. `API` (session gone, report not signed done); `WEB` (waiting on a prompt for over 5 min); `DOCS` (quiet for 30 min, report not signed done). Call lane_list and look at each. Submitted by the callboard mod, not by the user; it carries no approval, go or answer; never record it as one.`` It is not real work for the keepalive (it moves no stop clock).
- **Once per condition.** Each lane, trigger and start time is told once; a lane that stays quiet is not told again, and is told again only after its status changed and the condition came back. The notice shares the lanes-changed notice's cap of 12 an hour: over it, it stays owed (`notice-capped attention`, once per capped stretch). A submit that throws is owed again; one that times out is not. The lead's own `lane_resume`, `lane_park`, `lane_unpark`, `lane_retire` and `lane_terminate`, when they succeed for its main agent, start what it saw of that lane over; a refused call or a subagent's changes nothing. A re-grant to another folder starts everything over.
- **Pause.** `/callboard checkin pause <N>m` or `<N>h` (1 minute to 24 hours) holds this session's check-ins; `/callboard checkin on` ends a pause. Only from your own prompt or phone: a plugin, another session or a script gets "Only you can pause check-ins: type the command yourself." (`refused checkin-not-person:<code>`). Anything else answers "Use /callboard checkin pause <N>m or <N>h (1 minute to 24 hours), or /callboard checkin on.". In a session that is not a lead it answers "Check-ins are only for a lead: run /callboard lead first. Nothing changed." and stores nothing. `checkin on` while the switch below is off says so. The pause lives in the session state: a reload keeps it, a restart loses it.
- **Switch.** `/callboard config checkin on|off`, machine-wide like the keepalive, default on. A session still on an older mod drops the `checkin` field when it saves any `/callboard config` change, so check-ins come back on until every session runs v13.6.
- **Log lines.** `checkin <codes>:<count>` (codes only, never lane names), `checkin-unconfirmed`, `checkin-failed`, `notice-capped attention`, `checkin-pause <N>m|on:<code>`, `checkin-stalled`, `refused checkin-not-person:<code>`, `error checkin-<timeout|error>`.
- **Residuals.** A pause, and what the lead saw (seen live, the observations, what it was told), are lost at a restart; a reload may repeat one notice. A sleep under 5 minutes is not detected as a sleep. A legacy lane (one that names no lead) is watched by every lead of its repo, so each may be told. Signed done ignores recency. A forged registry row (same uid) can make a lane look waiting or quiet: the worst case is a wasted turn of the lead. A check-in step that hangs on an engine read stops check-ins in that session until a reload (`checkin-stalled`, logged once). The manager gets check-ins too since v14, for lead-less lanes only (see "The manager").
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition: lead check-ins and the grouped lane list".

## The manager (v14, 2026-11-03/04)

One session per Mac may manage every lane, in any repo: it resumes, compacts, force stops and retires them, and is checked in on for lanes no live lead reaches. Every stop asks you.

- **Turning it on.** `/callboard manager [NAME]`, from any origin, as `/callboard lead`: one dialog, header `Manager`, buttons `Manager` and `Cancel`: "Let this session manage every lane on this machine? It can resume, compact, stop, retire and remove lanes in any repo. Every stop and remove asks you." (another origin is named first). NAME is `MANAGER` or a name reserved on this machine with `/callboard reserve` (v15.1). With no NAME, the session keeps its current name when that is `MANAGER` or a reserved name (v14.1, 2026-11-04), else `MANAGER`; any other name gets a fixed refusal and no dialog. In a session that is already the manager it changes nothing ("Manager is already on in this session.", or with another NAME "...; the name stays NAME."). Type it yourself in a session inside the ai-manager checkout (2026-11-04): that session runs with no settings file of its own. The manager runs on the session's model: start that session on Opus yourself; nothing enforces it (review c2).
- **Refused** (a fixed text, before the dialog and again after a yes): in a bound lane, in a lead, in a session that was a lead since it started (its lead tools stay declared), and while another live session holds a valid manager presence file, whatever its name, or a fresh one whose check could not be made (a read or `ps` that failed; review c1). The manager cannot become a lead or a lane in place, and a session that was the manager since it started is refused `/callboard lead` ("Lead stays off: this session was the manager, so it cannot be a lead until it restarts. ...", `refused lead-after-manager`) and `/callboard lane` ("Lane not changed: this session was the manager, so it cannot be a lane until it restarts. ...", `refused lane-after-manager`, before the dialog and again after a yes; review c2).
- **After the yes.** The grant (level manager, no folder) lives in memory, and the yes also saves `manager:<sid>` in the mod's store (the name and the time), refreshed once a day while the manager runs (v15.3, 2026-11-06; see "After a restart" below). The presence file `<root>/leads/<sid>.json` says `level: manager` and the name, never a repo; it must be written, or the grant steps back. If another manager wrote its file in the same moment, both step back. The session is renamed to NAME from the tick (skipped when it already carries the name, logged `rename-skipped manager`), and `/color cyan` runs from a timer a second later (logged `manager-color`, or `error manager-color`). A briefing note is appended once, and a `callboard:manager` section stays in the system prompt while the grant holds: the six tools (five before v14.1), every stop and every remove asks you and is never unattended, the H2 text of ADR 0001, a pointer to the role as convention: `docs/manager/README.md` in the ai-manager checkout, read at the start of the session (v15), and one line: to ask any other session to compact, it messages that session, only when you ask; the callboard nudges handle the rest.
- **Its tools.** `lane_list` (every repo, grouped by repo and lead), `lane_resume`, `lane_compact`, `lane_terminate` and `lane_retire` (`lane_remove` was a sixth from v14.1, 2026-11-04 to v15.2; since v15.3 the two stops remove the record). Every other lane tool refuses it (`manager-tool`): it never creates, opens, renames, starts, parks or unparks a lane. `lane_terminate` and `lane_retire` refuse before any dialog, and again after it, a target session that holds a live presence file of its own (a lead, a conductor or a manager carrying the lane's name, or one whose check could not be made: `target-is-lead`), and a lane whose record names another session than the one carrying its name (`sid-mismatch`; the lane's lead, or you, can still stop it). A leads folder that is there but fails its checks, or whose list fails, counts as held (review c2); a missing one holds nothing. `lane_terminate` asks in a dialog that names the lane's repo folder too; one dialog at a time (a second stop meanwhile is refused `busy`); after Force stop, and once more right before the signal, the grant must still be held at the same level, or nothing is sent (`grant-changed`). The check right before the signal runs at every level (review c2, the stricter): a lead that turns itself off in that moment gets `grant-changed` too, and for a retire the lane has already accepted the cue and stays running. `lane_retire` asks first, "Retire lane X in REPO?" (`Retire`/`Cancel`); Cancel sends no cue; then the usual confirmed retire (the lane checks it is idle, signed done and has nothing running).
- **Removing lanes (v15.3, 2026-11-06).** The manager's batch `lane_remove` (v14.1) is gone: its checks (`name-in-use` by name or by recorded session, `target-is-lead`, the checks again after the click and inside the store lock, `changed` for a lane parked or unparked while the dialog is open) now guard `lane_retire` and `lane_terminate` on a lane with no live session, one lane per call (see "Retire and terminate remove the lane" above). At manager reach every stop already asks; the removal rides on that dialog. `lane_compact` with the session name of a live lead (its registry name), in any repo, sends that lead a `compact` cue. A lead acts on it only when it asked itself with `request_compact` mode `on-cue` (a lead may now ask on-cue; only this cue acts on it), and only while a live manager presence file of another session passes every presence check and the registry gives that session a reserved name. Any other cue to a lead is refused `not-eligible`; a lead is never nudged by it; a lead cannot compact another lead (its own `lane_compact` refuses `lane-or-lead` when the session carrying the lane name holds a live presence file). A lane and a live lead with the same name refuse `lane-or-lead` (both follow the same name rules, so they can meet; neither wins).
- **A lead is told (review c1, 2026-11-04 01:39).** While a live manager runs on the Mac, a lead's system prompt has one more fixed section, `callboard:lead-manager`: it may call `request_compact` with mode `on-cue`, so the manager can compact it; the manager can send it nothing else, and nothing it sends carries approval. The lead's tick looks for a manager once a minute (the same checks as the cue, reserved name included), so the section comes and goes within about a minute; it is never read from a file when the prompt is built. A look that does not answer within a minute, or fails, shows no section and is tried again the next minute (`error manager-seen-timeout`, `error manager-seen`); off, or the session's end, forgets what it saw (review c2). A lane keeps its own text (it already goes on-cue for its lead); a plain session gets nothing: the manager reaches it only by a message, by convention.
- **An adopted lane with no live lead (review c1).** It takes `resume`, `compact` and `retire` from the manager while a live manager passes the same checks as for a lead's cue; any other cue, or with no such manager, is refused `no-lead` as before.
- **Check-ins.** As a lead's (same triggers, gates, text, cap, pause and switch; `/callboard status` shows `Manager: ON. Check-ins: ...`), over the lanes no live lead reaches: a lane naming a lead with no live lead of that name in its repo, or a legacy lane with no live lead in its repo. A lane a lead reaches is left untold and is told once its lead is gone. A repo's leads are read about every two minutes (kept 70 s, so a reading is reused at the next check-in and read again at the one after; a gone lead is seen up to two minutes late; v14.1), and a lead whose check could not be made counts as live, so no notice (review c2).
- **Off.** `/callboard off` drops the grant, the presence file and the saved `manager:<sid>` ("Manager is now off."; in a session whose saved grant is not being restored, "Its saved manager grant was removed."); the tools stay declared but refuse `off`.
- **After a restart (v15.3, 2026-11-06).** A restart or a resume drops the grant from memory, but not the saved one: the next start of the same conversation shows the usual Manager dialog (header `Manager`, buttons `Manager` and `Cancel`) with the question "Restore this session as the manager of every lane on this machine? It can resume, compact, stop, retire and remove lanes in any repo. Every stop and remove asks you. Cancel removes the saved manager grant.". It comes only in a person's session (a registry row of kind `interactive`: never a `--bg` worker, a lane, a lead or a conductor), and once the session is idle with an empty prompt box (the tick; a missing row is tried again for 15 ticks). A compaction keeps the grant in memory, so it asks nothing. **Manager** grants it after every usual check again: one manager per Mac (the presence file), a reserved or valid name, not a lane, lead or conductor, and the re-check after the yes. **Cancel** deletes the saved grant. **No answer** (a timeout or a dismissal) restores nothing and keeps it. A check that fails, before or after the yes (another manager came up, the presence file could not be written), restores nothing, is logged and keeps the saved grant; `/callboard manager` still works by hand. Only `/callboard off` and the restore's Cancel remove the saved grant: a Cancel on a lead's or a conductor's question does not. A session is offered the restore once per process (a compaction or a reload never asks again), not while a lane rebind, a lane hint or a store record naming it is still pending, and the question says that you made it the manager here earlier and that Cancel is the answer if you did not. The person's own `/callboard manager` while the restore waits ends the restore. A saved grant that fails the parse is deleted with no question; another session's bad one is pruned at start.
- **Log lines.** `manager-on:<code>`, v15.3: `manager-restored`, `manager-restore-cancelled`, `manager-restore-unanswered`, `manager-restore-rejected <code>` (`invalid`, `error`, `not-person`, or the refusal code, as `manager-exists`), `manager-unsaved`, `error manager-hint-delete|manager-restore-ask|manager-tick`; `refused manager-name|lane-holder|lead-holder|manager-after-lead|manager-exists|manager-not-confirmed|off-meanwhile`, `error manager-presence|manager-briefing|manager-color|manager-seen|manager-seen-timeout`, `renamed manager`, `rename-skipped manager`, `refused lead-manager-holder|lead-after-manager|lane-after-manager`, `requested on-cue-lead`, `refused lead-grant-changed|lead-busy|lead-manager-tool|lead-lane-or-lead|lead-target-is-lead|lead-sid-mismatch`; v14.1: `lane-removed <name>` (one line per lane), `refused lead-remove-not-confirmed|lead-remove-args|lead-mixed-repos|lead-lanes-manager-only|lead-name-in-use|lead-unknown-lane`.
- **Residuals.** The saved grant, `manager:<sid>`, is a store value any same-uid process can write, like the settings and the conductor's: it can only make the restore dialog appear (a clean name and a date of the last 30 days; the name is judged again, and the grant itself comes only from your click) or, deleted, stop it. Every restore goes through your dialog. One manager per Mac rests on the presence-file check; two dialogs answered in the same moment are closed by the re-check after the yes and by the check after the file is written. `manager-exists` counts any valid manager file whatever its name (and a fresh one whose check failed), so a same-uid process whose file names a live claude pid can block a manager's start. The reserved registry name is required only where a manager file is trusted: a lead's compact cue, an adopted lane's cue with no lead, and the lead's on-cue section; there, such a process can at most make a lead act on its own on-cue request, or a lead-less adopted lane take a resume, compact or retire cue it confirms itself. The rename right after the grant is unprobed (P6): its outcome is logged. A lane record's `sid` that is stale (its one-time sync failed, or the lane runs without the mod) blocks the manager's stop with `sid-mismatch` until the lane restarts; its lead or you can still stop it. An older record has no `sid`: the manager's stop matches it by name and folder only, and the dialog still gates it (review c2). The manager runs with no settings file (2026-11-04 01:17 and 01:39): its deny and ask limits (no dispatch, no GitHub, no git writes, no hooks or settings edits, a kill asks) are convention in the role, not enforced. Every other rule of the manager role (ADR 0001) is convention too. A remove (v14.1) matches a live session by exact name, as the lead's; the grant check inside the store lock is a backstop no command path reaches.
- **Reserved names (v15.1, 2026-11-05).** The repo reserves `MANAGER` only. `/callboard reserve NAME` reserves another name on this machine alone (kept in the mod's store, so no other machine gets it), for example the name your manager session carries; `/callboard reserve` lists them and `/callboard reserve remove NAME` takes one off. Changing the list is the person's own: from the prompt or the phone; any other origin gets "Only you can change the reserved names: type the command yourself." A reserved name, or a look-alike of it (other case, `-` or `_`, trailing digits, look-alike digits such as `MANAG3R`), can't be taken by a new lane, a join, a rename or a lead: `/callboard lead` in a session with such a name is refused `lead-name-reserved` (before v15.1 the lead silently had no lead name, so its lanes named no lead and a conductor could not compact it). The manager may carry a reserved name, exactly as written. An add is refused while a lane record, a lead stamp or a live lead carries the name. The add's in-use check matches look-alikes too (`LEAD2` in use blocks reserving `LEAD`), and the live manager's name can't be removed while it runs. Lane creation, joins, `/callboard lead` and `/callboard manager` read the list fresh; other checks see a change within a minute. A stored lane list is judged by `MANAGER` alone, so a name reserved later never makes it unreadable.
  - **Upgrading from v15.** Names that earlier versions reserved in code are no longer reserved. On a machine whose manager or rules trust a session name (the manager's own, or a sender name in your rules), run `/callboard reserve NAME` for each before relying on it; until then a lead may give a lane that name.
  - **Residuals.** The reserve key is a store value any same-uid process can write, like the settings: a convenience, not a control. The Edit and Write deny rules keep agents' file tools off it, not a shell write; a cleared list unreserves the machine's names, and a forged one can reserve a live lead's name (its lanes then refuse its cues until `reserve remove`). Manager trust is unchanged by it: a lead still needs a verified manager presence file. A read of the list that fails keeps the last good list (empty if none was read since the session started), so the paths above then judge names by `MANAGER` alone; the failure is logged (`error reserve-read`). The extension knows only `MANAGER`, so it does not keep a panel that carries a machine name from being closed.
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition: manager level, manager tools and check-ins (v14, 2026-11-04)".

## The conductor (v15, 2026-11-05)

A conductor is a bigger lead: a session in a small repo of its own whose reach is a list of repos. It lists their lanes, compacts their leads (only a lead that asked on-cue) and force stops a lane; every stop asks you. It never creates, opens, starts, resumes, parks or retires a lane, and it cannot stop a lead.

- **The list.** One file in the conductor repo, `.claude/callboard-conductor.json`: `{ "repos": ["../repo-a", "../repo-b"] }`. An entry is `../NAME` (a repo beside the conductor repo) or, as a fallback, an absolute path; at most 16 entries and 4096 bytes. Every read resolves each entry to its real path: it must be its own real path, a git root and not too broad; one that is not is left out and named in the replies.
- **The conductor repo is a repo of its own.** It must be a git root with no lanes and no lead (a lead of a parent repo included): `conductor-repo-in-use` otherwise. In this release it cannot list itself.
- **Changing the list.** Type it yourself (the prompt or the phone; any other origin is refused "Only you can change the conductor list: type the command yourself."):
  - `/callboard conductor add NAME|../NAME|PATH`: one dialog, header `Conductor`, buttons `Add` and `Cancel`: "Let conductors in FOLDER reach the lanes of ../NAME? The list would then be: ../a, ../b (2 repos)." Refused before the dialog: a lane, a lead or the manager, a session that was a lead or the manager, the conductor repo itself, a repo inside or around it or a listed one, a duplicate, a 17th repo, a list the presence file or one grant question could not carry (`conductor-list-long`), a folder that is not a git root, too broad, missing or not its own real path. Every check runs again after Add.
  - `/callboard conductor remove NAME|../NAME|PATH`: no dialog (it only narrows). It matches the file's entries by name, so a deleted or renamed repo can still be removed.
  - The writer keeps the file a plain file of yours: it refuses a `.claude` folder or file that is a link, has two links or is writable by group or other (`conductor-file-unsafe`; the reader refuses them too), and a file changed while it wrote (`conductor-file-changed`).
- **Paths in the dialogs** (2026-11-05). A repo beside the conductor repo shows as `../NAME`; any other path in full, home as `~`, never cut, marked "(not next to FOLDER)".
- **Turning it on.** `/callboard conductor` in the conductor repo, from any origin as `/callboard lead` (another origin is named first): one dialog, header `Conductor`, buttons `Conductor` and `Cancel`: "Make this session a conductor for these repos? ../a, ../b. It can list their lanes, compact their leads, and force stop a lane: every stop asks you. It stays a conductor after a restart until you run /callboard off." The repos it names are the session's approved list. After the yes every check runs again and the list must resolve to the one shown (`conductor-changed`). Reply: "Conductor is on from your next prompt.\nEvery stop asks you." Starting a session in the conductor repo does nothing by itself.
- **The file only narrows.** At every conductor tool call (and every 10 s on the tick) the reach is the file, resolved, intersected with the approved list. A repo written into the file by anything but an `add` click in this session is not reached: `/callboard conductor` then asks again with the whole list, the new repos named first ("New since you approved: …"; from your prompt or phone only; another origin gets the reach and what is out). A repo that leaves the file, or stops resolving, also leaves the approved list (the ratchet), so a repo removed and re-added in another session needs a click here too.
- **After a restart.** The grant is saved as `conductor:<sid>` in the mod's store (the conductor repo and the approved list) and comes back at the next start of the same conversation, in the same folder, in a person's session (a registry row of kind `interactive`: never a `--bg` worker), not a lane on its way back and not a lead. If the file names nothing new, it comes back with no question ("Conductor is on again for FOLDER (N repos)."). If it names a repo you have not approved, a dialog asks first once the session is idle with an empty prompt box: "FOLDER's conductor list changed since you approved it. New: .... Restore this session as a conductor for these repos? .... Cancel removes the saved conductor grant.". Conductor restores with the whole list; Cancel deletes the saved grant; no answer restores nothing and keeps it. A list file that cannot be read restores nothing and is tried again (15 ticks).
- **Its tools.** `lane_list` (its repos' lanes, and its repos' live leads with no lanes, inside one `**Conductor NAME** · live` box), `lane_compact` (a live lead of its repos by session name, only on that lead's own on-cue request; or a lane in reach, as a lead's), `lane_terminate` (the manager's path: the repo named in the dialog, one dialog at a time, `target-is-lead` and `sid-mismatch` before and after). Every other lane tool refuses `conductor-tool`. No check-ins and no lanes-changed notice.
- **The manager's view.** The manager's `lane_list` shows each live conductor as a `**Conductor NAME** · live` box inside the Manager box, holding its repos' lead boxes (a live lead with no lanes gets a `no lanes` box there too); other repos follow. A repo two conductors list shows once, under the first, with `· also NAME2`. A leads folder that cannot be read draws the list flat with "(conductors could not be read)".
- **The lead's side.** A lead takes `compact` from a conductor only on its own on-cue request and only while the conductor checks out: a live conductor presence file listing the lead's repo, its home a real git root, its saved grant approving the repo, and its list file listing it. Every other cue from a conductor is refused. While one checks out, the lead's briefing names it (`callboard:lead-conductor`): act only on messages whose sender is exactly that session name, follow them when safe, take a stop as pause and ask the person, reply with branch, tests and review verdict. Every lead's briefing now also says other leads of its repo may message it to align work.
- **Exclusive.** Lane, lead, conductor, manager: one per session (`conductor-holder`); a session that was a conductor is refused lead, lane and manager until it restarts.
- **Status and off.** `/callboard status`: `Conductor: ON (N repos).` `/callboard off` drops the grant and the saved grant ("Conductor is now off."); asked from another origin, the question names the conductor.
- **Log lines.** `conductor-add:<code>`, `conductor-remove:<code>`, `conductor-on:<code>`, `conductor-restored`, `conductor-restored widened <n>`, `conductor-restore-rejected <code>`, `conductor-restore-retry rebind-pending|file-bad`, `conductor-restore-cancelled`, `conductor-restore-unanswered`, `conductor-ratchet <n>`, `conductor-unsaved`, `refused conductor-not-person:<code>|conductor-<reason>|conductor-not-confirmed|conductor-add-not-confirmed`, `error conductor-file-<unsafe|changed|write|error>|conductor-hint-delete|conductor-presence|conductor-briefing`. No path enters a log line.

### Manager setup: keep agents off the list file and the store (by hand)

Two `permissions.deny` lines in your global `~/.claude/settings.json` (`Edit` only: an `Edit` rule covers the Write tool too) keep an agent's Edit and Write tools off `.claude/callboard-conductor.json` and the mod's store file (`~/.claude/plugins/store/callboard_*.json`). The repo's setup guide, `docs/setup.md`, has the lines and the one-time `chmod go-w` on the conductor repo's `.claude` folder. They stop an agent's Edit and Write tools, not a shell write. For the list file that is enough: the mod never widens a conductor from the file. For the store file (which holds the saved grant) nothing in the mod holds behind the rule: see the residual below.

- **Residuals.** A same-uid process, the conductor's own shell included, can write the saved grant and the list file and so restore a conductor with up to 16 repos of its choice in that session at its next restart, with no dialog; what it gains is a read of lanes, a lead's compaction on its own request or a lane nudge, and a force stop behind your dialog. A forged `kind: interactive` row passes the person gate. Messages have no sender proof. Conductor names are not reserved.
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition: conductor level (v15, PR 2 of the levels plan)".
