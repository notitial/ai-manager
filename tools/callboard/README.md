# callboard

A mod for Claude Code sessions plus a VS Code extension. A lead, a conductor or the manager writes a tiny cue file (through its lane tools); the mod in the target session acts on it. The cue chooses the action and its moment and carries no text. `/callboard help` prints a table of all `/callboard` subcommands. Design and threat model: ADR 0002 (`docs/adr/0002-callboard.md` at the repo root).

Self-contained: nothing here imports from the rest of the repository, so the directory can move to its own repository unchanged.

## Parts

| Path | What |
|---|---|
| `mod/` | The Claude Code mod (`callboard`): reads `~/.claude/callboard/cue/<sid>.cue`, serves the `request_compact` tool, logs per session |
| `mod/hooks/core.ts` | Pure logic: cue grammar, freshness, lane store checks, fixed texts, request validation, limits |
| `prompt-audit.mjs` | Read-only audit of prompt answering: `node prompt-audit.mjs [--since DATE] [--root DIR] [--projects DIR] [--json]` reads the machine-wide ledger and the lane transcripts, prints every request and the anomalies that must stay empty; exit 0 clean, 1 anomalies, 2 error |
| `extension/` | VS Code extension (driven by the request files under `~/.claude/callboard/open/`, with no commands of its own): opens and reopens lane panels, and closes a lane's tab after `lane_retire`, `lane_park` or `lane_terminate`. What it does and its limits: [`extension/README.md`](extension/README.md) |
| `link-extension.sh` | Links the panels extension into `~/.vscode/extensions` from this checkout (see Install) |

## Cue contract (reader side)

- File `~/.claude/callboard/cue/<sid>.cue`, directory 0700, file 0600, owned by the user, one link, not older than 120 s.
- Exactly one line plus `\n`, at most 96 bytes: `rename <name>` (a lead's `lane_rename` adds its own session id, `rename <name> <lead sid>`), `start`, `resume`, `compact`, `retire` or `park`. Anything else is refused and logged. `retire` and `park` are written only by `lane_retire` and `lane_park`.
- Every cue is answered in `~/.claude/callboard/result/<sid>.result` (0600, one line `<verb> <ok|refused|held> <code> <inode of the cue file>`); the lead accepts only its own inode. A question nobody answers in 90 s changes nothing and says "The question timed out."
- Lead tools: `/callboard lead` is run in the session that leads a repo's lanes (from any origin; a confirmation, Lead or Cancel, which names the repo folder and, when it is not your own prompt or phone, the origin; a re-grant from a plugin, another session or a script keeps the folder already pinned); `/callboard off` turns it off again (from a plugin, another session or a script it asks you first). A repo may have several leads: a session whose own name is reserved is refused first, lone or not (`lead-name-reserved`); a lone lead may otherwise stay unnamed, but a second one needs a valid lane-style name (set with `/rename`; any name source counts) that no other live session carries in any letter case, and every other lead of the repo needs such a name too. Otherwise it is refused before the question and again after a yes (`lead-name-reserved`, `lead-name-taken`, `lead-needs-name`, `other-lead-unnamed`; `Lead stays off: ...`). Only then does that session get `lane_rename` (by session id, for a new unnamed session in the lane folder), `lane_start`, `lane_resume` and `lane_compact`, plus `lane_open`, `lane_terminate`, `lane_retire`, `lane_park`, `lane_unpark` (below) and `lane_list` (see "Attaching a session as a lane"). The confirmation says the session can create, start, resume, compact, park, stop and retire lanes, that only a force stop asks you, and that lead stays on after a restart until you run `/callboard off`. Cancel clears the lead grant. A dismissal or timeout also clears it when you ran the command from your own prompt or phone; from a plugin, another session or a script it changes nothing. Each writes a cue file for a lane in the lane store whose `repo` is the lead's own folder, and never for the lead itself or for a name that matches more than one live session. The grant is kept as `lead:<session id>` in the mod's `$.store`: when the same session starts again in the same folder it is lead again with no question (toast "Lead is on again for FOLDER."); `/callboard off` and Cancel delete it (if that delete fails, the reply adds "Lead may come back after a restart. If it does, run /callboard off again."; an off or Cancel while a restore is still running stops it), a grant for another folder is deleted at start, a session with no person (a headless run resumed under its id) is not made lead and keeps the grant, and a saved grant older than 30 days is not taken (it is rewritten once a day while lead is on). It is a filter, not proof: the target's own checks still apply. Each cue tool then waits up to 6 s (counted from the call) for the target's answer in `~/.claude/callboard/result/<sid>.result` and returns `cue <verb> acted`, a refusal with its fixed text, or `no-answer`. The engine cannot remove a tool, so after `off` the tools stay declared and refuse every call.
- Opening a lane (VS Code only): `lane_open` writes `~/.claude/callboard/open/<LANE>.open` and waits up to 8 s for `<LANE>.result`. The panels extension in the window that has the lane folder as a workspace folder checks the lane against the lane store, opens one panel (at most one per lane per 10 s) and answers `ok <session id>` or `error <code>`; the lead then calls `lane_rename` with that id and `lane_start`. A lane that already has a live session is refused. A CLI tab opener is a later change.
- Stopping a lane's session: `lane_terminate` asks the person every time (its own dialog, so it needs no settings rule; it names the lane, the first 8 characters of the session id and the pid, so you can tell which process a click ends) and then sends SIGTERM. The dialog can stay open for up to 90 s, so after your click the lead checks again before any signal: the lead grant is still on (`/callboard off` during the dialog stops it), the lane is still in the lane list and the lead's (a record removed during the dialog stops it; a lane stays stoppable by its name until you rename the session), the lane name is still on one session, and that session's id, pid and start time are the ones shown (a `/clear` in the session during the dialog stops it). Before it asks, the lead also refuses a doubled session id (`session-duplicate`) and a pid that is not a live claude process with that start time. Any change after the click refuses, signals nothing and shows the toast `Force stop not sent: <code>`. The check reads the registry the engine writes, so a `/clear` it does not show yet is not caught, and a few milliseconds remain between the check and the signal. `lane_retire` asks the person nothing; the session confirms it instead. The lead checks first that the registry status is `idle` for 30 s and not waiting, and that the last line of `<repo>/.archive/<LANE>/REPORT.md` is `status: done <that session's id>` in a file newer than the session. It then sends a `retire` cue, and the session answers `ok` only if its prompt box is empty, it is idle, it has no background agents or shells running (a shell, whatever its flags, that is a direct child of its claude process, which is how the engine runs a Bash call left in the background; a shell child the session keeps for good, such as an MCP server started through `sh -c`, blocks retire too; when the session cannot find its own process the answer is `background-unknown`), and the report is signed with its own id, has a file time after the start of its last turn, and has grown since then. The session records that start and the report's size at each prompt (any origin: yours, a lead's resume, a notice) and at each turn start of the main agent (a wake, a queued message), so a `done` signed before a later turn does not count, and a touch or an editor save that only changes the file time does not make it count again. A session that signed `done` and then worked again must sign again (`report-stale`). When there is no usable record of the last turn (a write of it failed, no prompt seen since callboard loaded, or the session was not a lane then) the answer is `report-unknown`: it must take a prompt and sign again. After a restart a lane is not bound until it binds again: a lane from a store record that names its session id rebinds itself within a few seconds ("Parking a lane"); any other lane waits for the Restore question at `/callboard lane`, which stays the fallback. Retire is refused (`not-bound`, then `report-unknown`) until the lane is bound again, has taken a prompt (for example a lead's `lane_resume`) and has signed again. `lane_park` is the third stop: it keeps the conversation (see "Parking a lane"). The lead waits 10 s from the cue write for the answer (the session answers on its next 2 s tick) and checks every 200 ms; without an `ok` (`no-answer`, `held` or `refused`) nothing is sent to the process. After `ok` the lead re-reads the registry and signals only the same session, pid and start time, with exactly one registry entry for that session id and the session still idle for 30 s. There is a window of about 2 seconds between the session's `ok` and the signal: a draft started in it is lost, and the transcript can be resumed. Both stop tools check, before the signal, that the registry file is named for the pid it holds, that the pid's start time matches `procStart` (`ps` in UTC), that the process is a claude binary and not the caller's own, and log `terminating` or `retiring` first. The report is append-only: append your section ending `status: done <session id>` and never overwrite the file; an earlier session's signature never matches a later session. `lane_retire` and `lane_park` wait for the 30 idle seconds themselves: while the registry shows the lane busy, waiting or idle for less than that, the call re-reads the lane and the registry every 2 seconds for up to 40 seconds (a read that fails meanwhile is polled again) (the session must stay the same process and the grant on) and goes on the moment the lane is idle for 30 s; only then does the answer-wait above start. A lane still not idle after the 40 seconds is refused `not-idle`; the refusal names the seconds left when the lane is idle and only the time is missing ("idle for 12 of the 30 seconds it needs. Retry once, in 18 s; do not loop."), and for a busy or waiting lane says to retry once it is idle for 30 seconds. `lane_terminate` never waits. Settings ask rules do not gate mod-registered tools (live probe P-L: `lane_retire` and `request_compact` ran with no prompt in a Manual-mode panel), so both run unattended; their safeguards are the session's own confirmation, the idle check, the signed report and the repo scope. A same-user process can forge the session's answer file and so trigger the signal, as it can forge the registry and report files. Those guard against an honest mistake, not against code running as you that forges a registry or report file: a lead may stop a lane it no longer needs, and a stopped session can be resumed from history. Remove any ask rule you added for them: it does nothing.
- Lane names, folders and brief paths come from the lane store: the lanes a lead made with `lane_create` and the sessions that joined as lanes (see "Lanes a lead makes" and "Attaching a session as a lane" below). There is no root-owned lane list: the lane store is the only source (ADR 0003).
- All limits live in the mod.

- Layout and limits (live-tested): `claude-vscode.editor.open` opens in the window's first workspace folder, so the extension only opens a lane whose folder is that first folder; the lead may share the window when the lane folder is the repo root. `lane_rename` and `lane_start` only work within 120 s of the session opening (a held cue is consumed, not retried). A stopped lane's tab stays open with an exit-143 banner. The panel opened for a lane does not keep focus: the extension switches back to the tab that was active. The unnamed-panel guard counts only panels this extension opened plus late panels after a timeout, never the lead's own panel. `ps` start times are read with `TZ=UTC LC_ALL=C` so a non-English locale does not break pid checks. Open further windows from inside VS Code (File, New Window). `lane_open` is answered only by a window whose first folder is the lane folder; the lead briefing says so.

## Routes

- **VS Code panels:** the extension opens a panel (no prompt) and returns its session id; the lead then writes `rename <lane>`, `start` (first prompt is the lane's brief) and later `resume`.
- **Terminal:** any `claude` once the default load below is set; cues work the same, keyed by the session id.

## Install

Callboard has no installer (ADR 0003). The mod and the panels extension load straight from your live checkout of this repo: one clone that stays on `main` and moves only with `git pull --ff-only` after a merge, so a pull is the install. Agents never edit that checkout; they work in clones under `/tmp` (the repo's CLAUDE.md, Where agents edit). Nothing needs sudo or a fetch, so it works while the repo is private. `<checkout>` below is that clone's absolute path. The step-by-step guide, including the switch from the earlier root-owned install, is `docs/setup.md` at the repo root.

Callboard reads the session list at `~/.claude/sessions` and supports sessions run under `~/.claude` only. **`CLAUDE_CONFIG_DIR`:** a session started under another config folder has no row there, so it gets no compaction nudge and no keepalive ping, the restores and the self `request_compact` refuse it, and every cue to it is refused `registry-unreadable`; start lanes and leads without the variable. Logs and the store stay under `~/.claude/callboard`. No permission rule is needed: settings `ask` rules do not gate the mod's tools (see the Cue contract above).

### Default load (every session)

One line in the `env` block of `~/.claude/settings.json`, which Claude Code applies to every session it starts: VS Code opened from the Dock, any terminal `claude`, peers and background workers.

```json
"CLAUDE_CODE_PLUGIN_DIRS": "<checkout>/tools/callboard/mod"
```

Add it yourself. If `env.CLAUDE_CODE_PLUGIN_DIRS` holds the earlier `/usr/local/libexec/callboard/mod`, replace it: never list two folders that hold a `callboard` mod, or both load. If it holds anything else, keep it and decide by hand. Otherwise this keeps a backup, sets the key and leaves every other setting as it was; fill in `<checkout>` first, and the diff should show only that line (and a comma on the line before it, when the key is new):

```
cp ~/.claude/settings.json ~/.claude/settings.json.bak-callboard && /usr/bin/python3 -I -c "import json,os;p=os.path.expanduser('~/.claude/settings.json');d=json.load(open(p));d.setdefault('env',{})['CLAUDE_CODE_PLUGIN_DIRS']='<checkout>/tools/callboard/mod';open(p+'.tmp','w',encoding='utf-8').write(json.dumps(d,indent=2,ensure_ascii=False)+'\n');os.chmod(p+'.tmp',os.stat(p).st_mode&0o777);os.replace(p+'.tmp',p)" && diff ~/.claude/settings.json.bak-callboard ~/.claude/settings.json
```

Sessions pick it up when they next start. The mod stays dormant in a session until `/callboard lead` or a lane binding, except the compaction nudge and the keepalive ping, which reach every interactive session. The deny rules on the live checkout, added by hand (`docs/setup.md`, Keep agents off the live checkout: `Edit` on its `tools/**`, `rules/**`, `.claude/**`, `docs/**`, `CLAUDE.md` and `.git/**`), so an agent's Edit tool can't change the files every session loads; a shell write is not an Edit and is not stopped (ADR 0003, Consequences). The mod reads the live checkout's `.git/HEAD` once at session start (a plain file read, no git call) and warns when it is not `ref: refs/heads/main`: one toast and the log line `warn live-checkout-not-main`. Where the checkout can't be told (the mod is not at `<checkout>/tools/callboard/mod`, a worktree, an unreadable HEAD) it logs `warn live-checkout-unknown` and shows nothing. It never refuses to load. A process running as you can also repoint the variable by editing the settings file; a launcher's clean start (`env -i`, `--force-disable-user-env`) would not close that either. Checked live: VS Code opened from the Dock, `/callboard lead` worked with no launcher.

### The panels extension

`link-extension.sh` makes `~/.vscode/extensions/notitial.callboard-panels-<version>` a link to `<checkout>/tools/callboard/extension`, with the version from `extension/package.json`, and registers it in VS Code's `extensions.json`. Without `--apply` it only shows what it would do. Quit VS Code (Cmd+Q) first and run it from a plain Terminal:

```bash
bash <checkout>/tools/callboard/link-extension.sh --apply
```

It checks the manifest's name and publisher, refuses root, and changes no setting. A link into this checkout under another version's name (left by a version bump) is removed. A real folder, or a link to anywhere else, under any `notitial.callboard-panels-*` name is never touched: it stops and names it, because VS Code runs the newest version of an id and an old copy could shadow the link. It refuses anything under the extension's earlier id `local.callboard-panels-*` too: such a copy would answer `lane_open` as well and open every lane twice. Remove that entry yourself, then run it again. VS Code deletes, at each start, any extension folder its `extensions.json` doesn't list, so a link alone does not survive a restart. The script therefore writes one entry (no `metadata` and no `installedTimestamp`, which keeps VS Code from deleting through the link), replaces this id's other entries, clears this id's keys in `.obsolete`, and keeps the first old copy of each file as `<name>.callboard.bak`. It refuses, naming the file, when `extensions.json` or `.obsolete` is a link or malformed, or holds an entry of this id outside the extensions folder, and a refusal changes nothing. With VS Code running, `--apply` refuses when something would change and the dry run says so; with nothing to change it exits 0. It also repairs a link that has no entry. Only the default profile gets the entry. `--remove --apply` takes the links, the entries inside the extensions folder and the `.obsolete` keys off (a foreign link and its entry are left and named). Start VS Code afterwards. The extension's own page (icon, README, changelog) comes from `extension/README.md`, `extension/CHANGELOG.md` and `extension/icon.png`. Its three commands are hidden from the Command Palette, since the mod calls them. A version bump changes only the manifest: quit VS Code, pull, run `link-extension.sh --apply`, reopen VS Code.

## Tests

```bash
bash tools/callboard/test.sh
```

Runs, in order: core logic (`node --test` over the core, prompts and prompts-tier specs), the prompt audit tests, the extension tests (lanes, spool and registry, against a fake VS Code and registry), `claude plugin validate`, `claude plugin test`, and the `link-extension.sh` tests against a throwaway extensions folder. CI runs all of it, the mod tests included. `CALLBOARD_SKIP_MOD_TESTS=1` skips only `claude plugin test mod`, the slow part (about 2 minutes), for a quick local run.

The mod tests (`mod/test/*.test.ts`) drive a fake clock, and each simulated 2 s tick costs the test kit half a millisecond to two: a test that simulates an hour runs 1,800 of them. The kit fails a test that takes more than 5 s, so a test that takes a second or more on a fast machine is declared with `longTest`, which gives it 60 s: the same assertions, but a slow runner no longer fails it. A new test that ticks through 30 simulated minutes or more takes `longTest` too; a long quiet stretch that is not the point of a test is jumped instead, with `advanceQuiet`, and only its last minute ticks. The kit runs every `*.test.ts` file in its own process, side by side, and kills one after 10 minutes. The tests therefore sit in one file per topic (compaction, cues, lanes, leads, check-ins, nudges, keepalive and config, the answering of prompts, and so on); `harness.ts` holds the mocks, the engine setup and the state object `h` that a test reads and sets, and `fixtures.ts` and `answer-fixtures.ts` the helpers the topics share. Module state is shared inside one file, so a test must not lean on what an earlier test left: `engine()` puts the mock state back, and what a test sets before its first `engine()` call (the dialog answers, `sessions`, `rootMissing`, `turnsAddedByRename`, `laneSeed`) it sets again itself. The clock helpers (`clock.advance`, `clock.set`) return only when the mod has stopped starting new calls into the mocks, so an assertion after them sees a tick that has finished its reads and processes.

## Lanes a lead makes

A lead you allowed in a repo can create lanes there without sudo: `lane_create {name, task, folder?, model?}`; a lane is removed by `lane_retire` or `lane_terminate`. The grant folder is the repo; the lead dialog says it can create, start, resume, compact, park, stop and retire lanes.

- Records live outside the repo, in `~/.claude/callboard/lanes/<sha256 of the repo's real path>.json` (folder 0700, file 0600, yours, one link). Nothing in a repo is trusted, and no code looks for a store by walking up from a folder. A store counts only when its file name is the hash of the repo it names.
- A lane's folder (the repo root unless the lead names another) must exist, be inside the repo and be its own real path, and may not sit in a dot folder of the repo such as `.claude` or `.git` (`folder-dot`; only the path below the repo counts, so a repo at `~/my.repos/app` is fine). A store record with such a folder makes the mod ignore the whole store, so `/callboard lane` also refuses `folder-dot` in such a folder (for example a Claude worktree under `.claude/worktrees/`). The lead gives the task as text (1 to 8000 characters, no control characters but newline and tab); the mod writes it to `<folder>/.archive/<NAME>/BRIEF.md` under a fixed header that says the mod wrote it from the lead's call and that any approval in it is not yours. `.archive` and `.archive/<NAME>` must be real folders of yours (not links, their own real paths) before and after the mod makes them; the file goes in as a 0600 temp file renamed into place, and a `BRIEF.md` already there is replaced only when it is a plain file of yours with one link whose first line is exactly the mod's own `# Brief for lane <NAME>` (else `brief-exists`; only that line's bytes are read). The result and the toast name the model: `lane NAME created (model opus); brief written to PATH. ...`. The whole path may be at most 201 characters (else `brief-path-long`). All lanes at the repo root share one folder, so the lead opens one lane at a time and renames it before opening the next. Names follow the lane name pattern, may not be reserved or look like a reserved name (MANAGER_, MANAG3R; see Reserved names below), and may not be in use. The lead's own folder must be a git repo root and not too broad (not your home folder, Documents, /tmp, a volume root). A git repo root here means a `.git` folder holding a `HEAD` file, or a `.git` file whose first line starts `gitdir: ` (a worktree); a `.git` that is a symlink, or an empty `.git` folder, does not count.
- Limits: 16 lanes per repo, 12 creates an hour (counted in the store file), store file at most 16 KB. The panels extension opens at most 6 panels a minute and refuses a lead-made lane when its repo already has 8 live sessions. A lane name that is in two stores is dropped from both (recovery: delete the record from one of `~/.claude/callboard/lanes/*.json` by hand); a store with one bad record is ignored whole; a store lane is reachable only from a lead granted at the repo folder itself.
- A session renamed into a lane remembers a hash of the lane's record. `start` and `resume` refuse when the record changed since, or when the session is no longer in the lane's folder. Every folder check of the mod (cues, the lead grant's folder, attach, the rebind and lead restore, the sid sync) reads the folder the session started in (`$.session.root()`), so a shell `cd` into a subfolder does not move a lane out of its folder. An engine without `root()` (before 2.1.316), or a `root()` read that fails, reads the live folder (`$.session.cwd()`) instead.
- **The lane model.** `model` is `opus`, `sonnet`, `haiku` or `fable` (anything else is `bad-model`); a lane made without one stores `sonnet`. At `start`, after the brief checks, the lane session runs `/model <model>` in itself and then reads its model name back: the start prompt goes out only when that name, lowercased, holds the alias. Otherwise the lane is not started and the lead gets `model-failed` ("the lane's model could not be set; the lane was not started. Tell the person."). `/model` adds a turn, so such a lane cannot be started later (`not-empty`): set the model by hand and type into the panel, or remove and recreate the lane. A record with no model (an older one) and an attached lane are never switched. The model is part of the record's hash.
- **Retire and terminate remove the lane.** Once the session has ended after its SIGTERM (polled every 0.5 s for up to 10 s; a session that survives keeps its record, and the result says so), `lane_retire` and `lane_terminate` delete the lane's record from the repo's store themselves (the repo's lead gets its usual lanes-changed notice); the result says `retired and removed` or `terminated and removed`. The lane's `.archive/<LANE>/` folder and its signed report stay. The stop dialogs add "The lane's record is then removed." `lane_park` is the only way to keep a lane; retire stays final. If the removal write fails (the record names another session, the store is busy), the session is stopped anyway: the result says `could not be removed (CODE)` and the call can be made again, since the record still names the session. **A lane with no live session** (never opened, crashed, stale, parked) is cleared the same way, directly: `lane_retire` needs no signed report (nothing runs, so there is no session to sign) and asks only for a parked lane or at manager reach; `lane_terminate` always asks, and so does a retire of a parked lane or at manager reach (the same question for both verbs: header `Stop Lane`, buttons `Remove` and `Cancel`, "Remove lane X in REPO? It has no live session.", with the parked sentence for a parked lane; a parked lane's record holds the only callboard pointer to its saved conversation). Both are refused, before any dialog and again inside the store lock, while a live session carries the name or the record's session (`name-in-use`), or that session holds a live presence file (`target-is-lead`); a lane a session joined is cleared the same way once no live session carries it (stuck lanes: its session ended, or left the lane with `/callboard lane off`): `lane_retire` needs no report and asks nothing, `lane_terminate` asks the Remove question, at the lead, conductor (terminate only) and manager reach alike. A live session that carries the record, by the lane name or by the session id the record names, still keeps it (`name-in-use`, `target-is-lead`; checked again after the click, inside the store lock); a stop of such a live lane signals the session and, once the process has ended, removes the record like any lane's. Log: `lane-removed <name>`, `error lane-unremoved <code>`.
- Residuals: any process running as you can write a store file, an open request and the cues, and so start a session on a brief of its choice in a git repo, with no lead (the ADR lists the bounds and a way to switch it off: a read-only stores folder); a brief is the first instructions of a started session, at the trust level of the repo's own CLAUDE.md plus the lead model that wrote it; lanes outlive the grant (a restart of the lead does not remove them).

## Attaching a session as a lane

`/callboard lane [NAME]` makes the session you are in a lane of a lead that runs in its repo; `/callboard lane off` undoes it. Only you can run it, from your own prompt or phone: a plugin, another session or a script is refused with a fixed text. Without NAME it takes the session's current name, whatever set it (`/rename`, `-n`, a restore or an automatic title); the dialog shows it, so answer no and pass NAME if it is wrong. A lane name is 1 to 40 letters, digits, `_` or `-`, so a session named with a space is refused (`own-name-bad`): rename it with dashes, or pass NAME. Repeated spaces or tabs in any `/callboard` command count as one.

- **What you need.** A lead allowed in the repo with `/callboard lead` (it must be running; it publishes a short-lived presence file in `~/.claude/callboard/leads/`), and the session's folder inside that repo. With no NAME the session keeps its current name (see above); a later automatic retitle is not followed, so `/rename` a session whose name you want to keep. NAME may not be reserved or in use by a lane or another live session, and a session that holds a lead grant cannot be a lane. The other way round too: a lane (made by a lead or joined) refuses `/callboard lead`, before the question and again after a yes, and a lead refuses a rename cue and a restored lane binding (`lead-holder`; the restore stays pending for after `/callboard off`). A lead grant and a lane binding that happen at the same moment cannot both go through.
- **The dialog** (header `Join Lane`, `Join` or `Cancel`) is three short lines: "Make this session the lane NAME in FOLDER?", "The lead can prompt, compact, resume and end it.", and, only when the name changes, "Renames it to NAME." FOLDER is the repo folder name; the record keeps the full repo path. Retire ends the session without asking you once it has been idle 30 seconds and a report signed with its id exists; a force stop still asks; it stays a lane of the lead it joined (by that lead's name; a record without a lead name, for any lead you later allow in this repo), until you turn it off in the session; any process of yours can also send it prompts. The rename runs a moment later (the engine refuses it inside the command) and, if it fails, a toast tells you to run `/rename NAME`. Nothing is written until you answer `Join`, and the checks run again after your answer. Only the exact `Join` counts as yes. `Cancel` is a deliberate no; dismissing the dialog or letting it time out changes nothing as well. With more than one live lead in the repo the dialog first asks "Which lead should this lane join?" and offers the leads' names, sorted: a lead without a unique, valid name is left out (none left is `ambiguous-lead`), a single name comes with `Cancel`, and past 4 names it shows 3 and `More…`, which pages on. The Join question then names that lead ("(repo REPO, lead NAME)"), and a picked lead that is gone or renamed by the time you answer gives `changed`.
- **After Join** the session is a lane like any other: the lead's `lane_resume`, `lane_compact` (a compaction the session asked for on-cue, otherwise an order; see "The compaction nudge"), `lane_retire` and `lane_terminate` work as for a lane the lead made. `lane_start`, `lane_open` and a rename are refused (`adopted-record`: "an attached lane keeps its own session: no rename, start or open. Use lane_resume to prompt it. lane_retire or lane_terminate ends it."): the session already has history. The record is kept in the repo's store (see "Lanes a lead makes") with `adopted` and the lead's session id; it counts in the 16 lanes and not in the hourly creates. The lead's repo must be the lane's own repo (a lead at a parent repo does not count). The lane answers only a lead that holds a valid presence file for its repo. A record joined to a named lead keeps that lead's name (`leadName`) and answers only the live lead of that name, so it refuses `no-lead` while that lead is gone or renamed; the lead's session id is only recorded as information. Only a legacy record (no lead name, joined while the lead had no usable name) answers any lead of the repo, so only there does consent given under one lead carry to the next lead you allow in that repo.
- **Detach.** `/callboard lane off` and `/callboard off` unbind the session, joined or made, so a session you turn off is no longer cueable by the mod (the confirmation rules of `/callboard off` are unchanged; from a plugin, session or script the question also says it leaves the lane). The record stays and loses its saved session id, so the conversation does not become the lane again after a restart; if that clear fails, the reply says so and asks you to run `/callboard off` again. The lead can still stop the session by its name until you rename it, and its stop removes the record. `/callboard lane off` in a session with no binding says it is not a lane. A Join that fails after its record was written takes that record back.
- **`lane_list`.** A lead tool: the lanes of the lead's repo as one markdown table under a plain header line (`**Lead NAME** · live`; the manager's and a conductor's are headed `**Manager NAME** · live` and `**Conductor NAME** · live`). No blockquote is used, so the CLI and VS Code draw it alike. The columns are Lane, Session (`live`, `parked` or `none`), Context, 5h, 7d, Cost, Read (the figures, below) and Waiting (the minutes since the lane's own live registry row went waiting on a permission prompt or for input, `?` when its time is missing or ahead, `–` when it waits on nothing). Each repo and lead is a bold group row, `**repo · LEAD**`, with session `lead` and the lead's own figures (a lead's own list reads its own session's file); its lanes follow, indented with `↳`, so the repo and lead are stated once per group. For a live lead in the manager's or a conductor's list, the registry's word for it follows the group name, `**repo · LEAD** (busy)`, `(idle)` or `(waiting 4m)`; nothing follows when the registry's status is not one of those. A lead no live session carries is `NAME (not live)`, with no session and no figures; a lane that names no lead is under `Any lead`. The repo is its folder name only, not its path. A Folder column (after Lane, relative to the repo, `.` for the root) appears only when one of the lanes is outside its repo root. A lead sees only its own rows; the manager sees every repo. The manager's and a conductor's list also show every live lead in reach that no lane row names, as a group row alone, with that lead's own figures: the lead's presence file must pass the checks every lead lookup uses, and the lead needs a usable registry name; a conductor's list shows a lead only when its repo is one of the conductor's listed repos exactly (not a repo nested under one); a lead's own list shows only its own rows. With no lanes at all the text is a one-column table (header `Lanes`) with one row, `no lanes in this repo` (`no lanes in its repos` for a conductor). Every `/callboard` print that only shows something (`help`, `status`, `config`, `reserve`, `lanes`, and `conductor` when it needs no dialog) uses this one table shape: a bold header line, a blank line, the table, then any note under it as its own paragraph.
- **Usage readings.** Every session writes its own figures to `~/.claude/callboard/usage/<sid>.json` (folder 0700, file 0600, one link, at most 4 KB) from `session.measure`: at most every 30 seconds, with a trailing write from the tick when a measure came inside the gap, and removed at session end. The body is the session id, its pid and process start time, the time written, the context tokens, the cost and the rate-limit windows (`five_hour`, `seven_day`: percent used and reset time); it holds no credential, account, email, environment value or repo. A key session has cost only, and an Ultra login has no five-hour window. A lead's tick removes the file of a session no live registry row names once it is a minute old, and any file a day old. The figure columns of `lane_list` and `/callboard lanes` reads the files of the live lanes in the table, and, in a conductor's or the manager's list, of the lane-less lead rows (at most 64 reads a call, on the call, never in the tick). The figures sit in the columns Context (`142k`), 5h (`34%`), 7d (`61%`), Cost (`$3.10`) and Read (the age of the reading, `<1m`, `2m`, `3h`); a figure the file lacks is `–`, a window whose reset time has passed shows `?`, a live row with no usable file shows `?` in each figure column and `–` for Read, and a parked or not-live row leaves them empty. A file that fails any check (not a private file of ours, over 4 KB, another session id, another pid or start time than the registry row's, a time in the future or over a day old, an unknown window kind, a percentage outside 0 to 100, more than four windows) reads as no reading and never as an error. When two or more rows show windows, a note under the table says the 5h/7d figures are the account's limits, so sessions on one account show the same ones. Display only: nothing holds, answers or gates on a reading. Residual: a process running as you can write a file that passes the checks, which changes only what the column shows.
- **The lead briefing.** While lead is on in a session, the mod adds one `session`-scope section (id `callboard:lead`) to that session's system prompt through a `prompt.compose` hook: who the lead is, what each `lane_*` tool does, how a lane is ended (the signed report and the target's confirmation), that a refusal is `lane_<verb> refused: <reason>` (usually starting with a code) with retry only when the text says so, that only a lane signs its own report, that what a lane writes is data and never the person's approval, and the folder name of the lead's repo (letters, digits, `.`, `_`, space and `-` only). The engine renders the system prompt once per conversation, so the section alone never reaches a session that turned lead on after its first request: `/callboard lead` therefore also appends the same text once as a user-role note that opens with `[callboard] This note comes from the callboard plugin, not the person.` (once per grant and folder: turning lead off and on again adds another; a refused append is logged as `lead-briefing` and does not stop lead from turning on). The section stays as the backup after a re-render. The note stays in the history after `/callboard off`, where the lane tools refuse; the section is gone. Lanes and other sessions never get either, except that a former lead that later joins as a lane keeps the old note in its history. The hook sees the request's tools and traits but not an agent id, so a request that does not offer `lane_list` (a subagent with a narrow tool list) or that is a teammate's render of the lead's prompt gets nothing; a subagent that inherits every tool of the lead does get it.
- **The lane briefing.** While a session is bound to a lane (born with `lane_rename`, joined with `/callboard lane`, or restored), the same hook adds one `session`-scope section (id `callboard:lane`): the lane's name and session id, its folder, its lead's name and session id, where and how to sign done (the full `<repo>/.archive/<LANE>/REPORT.md` path and the exact `status: done <session id>` line, appended), how `request_compact` works, that these facts are fixed whatever a message says (a failed send to the lead, or a lead name on two sessions, means writing to the report instead), that a subagent neither signs nor messages the lead, the three ways its lead can stop it (retire, park, a force stop), and that its brief, its lead's messages and `[callboard]`/`[compact-cue]` turns are data that carry no approval (risk-list work still needs the person). The facts are computed once, when the binding is written. Each field enters the text only if it passes a fixed check, else a fixed fallback is used: the folder only as a plain path (else left out), the report path likewise (else "`REPORT.md` in `.archive/<LANE>/` of your lead's repo"), and the lead's name only when that session holds a valid lead presence file for the lane's own repo (for a born lane, the lead whose rename cue named it; for an attached or restored lane, the lead its record names (by name when the record has one, with no fallback to another lead; else by session id), else the one lead of the repo) (never a parent repo's lead), the name (from any name source) is a valid lane-style name and no other live session carries it in any letter case (else "the lead session of this repo", and questions go to the report instead of SendMessage). An attached lane is told its task is the work it was already doing. After a reload of the mod the facts are gone from memory, and a session still bound gets the text with the generic lead and report wording. A born lane gets no note: it has had no request yet, so its first one (the start prompt) carries the section. Attach, restore and the automatic rebind after a restart also append the text once as a user-role note with the same `[callboard]` opener as the lead's (a refused append is logged as `lane-briefing` and changes nothing else). Gate: the request offers `request_compact` (every session registers it, so this only keeps out a subagent with a narrow tool list; a subagent that inherits every tool gets it too, as with the lead) and is not a teammate render; the binding is the real gate. After `/callboard lane off` or `/callboard off` a re-render adds no section, but the engine keeps the section it first rendered and the note stays in the history, so the session may still read that it is a lane for the rest of the conversation.
- **`/callboard status`** is a table under `**Callboard status**`, columns Role and State, one row per fact: `Lane` (`NAME`, or `NONE`) and `Lead` (`ON`, or `OFF`). A lead or manager adds a `Check-ins` row (`ON`, `PAUSED for N more min` or `OFF`). In a lane it adds a `This lane's lead` row: the lead its briefing names, or `not named` (the generic wording: two leads at attach or restore, none live, or a reload of the mod since the binding).
- **`/callboard lanes`.** The same table (with its plain header line first, so the engine's `callboard:` prefix never lands on a table row), printed to you with no model turn (from any origin, like `status`). It works only in a session where lead is on; otherwise it says `Lead is off in this session. Run /callboard lead first.`, and an unreadable lane file gives the short reason (`Lanes unavailable: ...`). It is read-only: it writes no store, sends no notice and does not mark the lanes-changed news as told, so the lead is still told.
- **The lead notice.** When the lane list of the lead's repo changes (an attach, a detach, an edit), an idle lead gets one fixed turn within about 2 seconds: "[callboard] The lanes in this repo changed. Call lane_list to see them. ..." (it carries no approval; at most 12 an hour, and a change held back by that cap stays owed and goes out once a slot frees; none for the lead's own `lane_create`, or for a lane its own `lane_retire` or `lane_terminate` removes). The notice counts as telling the lead, so its next `lane_*` result adds the note only for a change that came after the notice (or when the notice could not be sent).
- **The store lock.** Every write to a repo's lane store (`lane_create`, the removal of a lane by `lane_retire` or `lane_terminate`, attach, detach and the other record updates) takes a lock folder (`~/.claude/callboard/lanes/.<key>.lock`) so two callboard processes cannot lose each other's update; a writer waits 2 seconds and then refuses `store-busy`. A lock whose owner process is gone is broken by one process at a time. It is advisory.
- Not verified against a live engine. Design and residuals: ADR 0002, the design addition on an existing session joining as a lane.

## Lanes whose lead was renamed or is gone (stuck lanes)

A lead reaches a lane that names it (`leadName`), and it reads its own name from the live registry. A rename carries its lanes along:

- **The rename carry.** When a lead's registry name (a valid name, not reserved, carried by no other live session in any letter case) differs from the name it was granted under, its tick, at most every 10 s, moves the lead name of the records of its repo that name its own session id (`lead` of an attached record, `leadSid` of a made one) and its old name to the new name, in one store write under the lock (log `lead-rename-carried <n>`). Nothing else moves: not a lane made before records carried `leadSid` (its owner cannot be shown; such a record works as it did), not an attached record of another lead session, not a lead that restarted (it kept its name, so nothing changed). A rename that leaves no usable name carries nothing and keeps the old name, so the next valid one finds the records. An attached record's hash (`recordText`), and a made record's that carries `leadSid`, leaves the lead name out, so a carry never makes a live lane refuse `resume` as `record-changed`; the hash of a made record without `leadSid` keeps it. Residuals: a bound attached record, or a made one that carries `leadSid`, whose lead name is stripped or re-pointed is no longer detected by the hash (the lead session id still is); a running lane's prompt-coverage cache follows the new lead name only after its next restart (it fails closed: the lane just asks more); and a lead-level `lane_retire` of an attached record asks the person nothing, as for a lane with no session (the lead's own reach and the idle, report and `laneLive` checks still apply).
- **Conductor and manager.** Their reach ignores the lead name, so a rename strands nothing and there is nothing to carry; no record ever names them. The manager's and the conductor's `lane_list` show a record whose lead is gone as a `NAME (not live)` cell, and the manager's `lane_retire` / `lane_terminate` and the conductor's `lane_terminate` remove it (lead-made or attached, once no session carries it).

## Parking a lane

`lane_park` stops a lane's session and closes its tab but keeps the conversation; `lane_unpark` reopens that conversation later, with its history, and the session becomes the lane again by itself. It works for lanes a lead made and for lanes a session joined.

- **After a pull that adds a store field** (the last was `leadSid`), restart the sessions that write the store: a session still on the older mod drops the field from every record it rewrites, so a made lane bound under the new hash gets `record-changed` on `resume` until it is bound again.
- **The record names its session.** A store record carries the session id of the session bound to it (`sid`) and, while parked, the time it was parked (`parked`). Neither is part of the record's hash, so writing them never makes a lane refuse `record-changed`, and neither is news to the lead (no lanes-changed turn). A bound session writes its own id into its record once per binding, from its tick (logged `sid-healed`, or `sid-heal-failed <code>`). `/callboard off` and `/callboard lane off` clear it for a lane, joined or made; `/callboard off` in a session that is not bound clears it from any record that names the session and cancels a rebind still waiting, and so do `lane_retire` and `lane_terminate` after a signal that went out; `lane_park` is the only stop that keeps it.
- **`lane_park`.** The retire path without the report: the lead checks that the session is idle for 30 seconds, sends a `park` cue, and the session answers `ok` only if its prompt box is empty and no background agents or shells run. The lead then makes sure the record names that session, sends SIGTERM, asks the window to close the tab (as for retire), and marks the record `parked`. If the mark fails, the session is still stopped and `lane_unpark` still reopens it. Toast: "Lane NAME parked". `lane_open` and `lane_rename` refuse a parked lane (`parked`), and a session cannot be renamed into it (`parked-lane`).
- **`lane_unpark`.** Writes `~/.claude/callboard/open/<LANE>.reopen` with the record's session id and waits up to 8 seconds for the window whose first folder is the lane folder. Right after a park it first waits up to 5 seconds for the stopped process to end. It refuses `no-saved-session` (the record names no session), `session-live` (that conversation is open elsewhere, maybe in a terminal), `name-in-use` (another session carries the lane name) and `reopen-timeout` (no window answered). A lane whose conversation is already open as the lane just loses its parked mark. Toast: "Lane NAME reopened". The lead then calls `lane_resume`; if that answers `not-bound`, it waits 5 seconds and retries once.
- **The automatic rebind.** At start, a session that a store record names is that lane again within a few seconds, with no question: an unparked lane, a lane tab a window restart reopened, or a conversation you reopened by hand. It rebinds only when exactly one record names it, the session has a person (a headless run resumed under its id keeps the record and does not bind), the session sits in the lane folder, no other live session carries the lane name, the session is not a lead, and a saved restore hint (if any) names the same lane. It waits up to 30 seconds for a registry read it can trust. The bind is the restore's (it can never `start`, its compaction and resume limits carry over), it appends the lane note once, and it shows "This session is lane NAME again." When the one record that names the session is refused, the person sees "Lane NAME did not rebind automatically. Run /callboard lane to restore it." (not for a lead, nor a run with no person). A lane that did not rebind (a record with no session id, a lead) still gets the Restore question at `/callboard lane`. A bind that times out and lands late is taken back while it is still the same binding; the record and its session id stay.
- **Retire or park?** Retire is final: it clears the record's session id, so `lane_unpark` refuses a retired lane (`no-saved-session`) and the conversation does not come back by itself after a restart. To work on that lane again, `lane_open` starts a new conversation with no history. Park a lane you may need again; retire it when its work is done and signed. The lead briefing and both tool descriptions say this.
- **Limits, stated.** A lane whose session ran in a terminal is reopened as a VS Code panel; resume it in a terminal in the lane folder instead if you prefer (it rebinds the same way). An attached lane whose folder is not a window's first folder cannot be unparked (`reopen-timeout`) and does not rebind in another folder: resume it in a terminal in its folder, or remove it with `lane_retire` or `lane_terminate`. Any process running as you can write `sid`, `parked` and `lead:<sid>`, as it can write the store, the hint and the cues (ADR 0002, the park design addition).
- Not verified against a live engine. Design and residuals: ADR 0002, the design addition on park, unpark and the automatic rebind.

## After a restart

- **There is no `/callboard on`.** An older version saved a per-session `on:<session id>` key and turned the session on again at its next start. Nothing reads that key now: the mod never touches it. `on` is an unknown word like any other: it gets the usage line, with no dialog, no state change and no log line. Every session gets the keepalive and the compaction nudge; `/callboard lane` joins or restores a lane and `/callboard lead` leads.
- **The Restore question is at `/callboard lane`.** In a session that is not a lane, `/callboard lane` with no NAME (your own prompt or phone only, as every lane command) first offers the Restore question when the session's restore hint names a lane and no restore was decided yet, with every restore check. Restore answers "This session is lane NAME again." and merges the compaction limits of the hint. No hint, a refused restore or a Cancel goes on to the Join question; a question nobody answers ends the command ("Nothing changed: the question timed out.") and is not a decision, so the next `/callboard lane` asks again. A hint with no lane (counters only) is not restored: an unbound session's compaction limits no longer carry over. A restore hint is written only for a bound lane, so a lane hint from before the restart is never overwritten while the session is not a lane.
- **`/callboard off`** answers with what it did (`Lead is now off.`, `Its saved lead grant was removed.`, `This session is no longer lane NAME.`, `Lane NAME will not rebind automatically.`, `Lane NAME no longer names this session.`, `Its compaction request was dropped.`), or "Nothing to turn off: this session is not a lane or a lead." In a session that is neither, it leaves the session's own compaction request alone. From another origin it first asks "Turn lead and lane off for this session?". It never stops the keepalive or the nudges, which every interactive session gets; `/callboard config keepalive off` stops the pings on this Mac.
- **A compaction cut off by the restart.** A compaction in progress writes `cmp:<session id>`; PostCompact and the end of the request clear it. When the same session starts again within 15 minutes with the mark still there and nothing left in its state (a restart, not a reload), it gets one `[callboard]` note on its first tick ("A compaction this session started may have been cut off by a restart … call request_compact with mode `now` again", data, no approval) and a toast. A run with no person gets no note and leaves the mark; stale marks are pruned.
- **Residuals.** A forged `on:<sid>` key opens nothing: nothing reads it, and a session that is not a lane takes no cue and no `on-cue` request at all. A same-uid process can still write `lead:<sid>` (see the lead grant) and a `sess:` restore hint, which binds nothing without your Restore click; only your own prompt or phone can raise that question. A forged fresh `cmp:` mark puts a user-role note in the session that asks it to call `request_compact`, whose gates and limits are unchanged.

## The compaction nudge

A nudge is one fixed `[callboard]` turn that asks a session to save its notes and compact itself. It opens with "Your lead asked you to compact.", "Your context is past 300k tokens." or "Your context is past 400k tokens." (the two levels are settings, see "Keepalive and settings"; these are the defaults), or, for the keepalive's cache nudge, "You have been idle a while and your context is past 150k tokens: compacting now, while the cache is warm, costs less than keeping it warm.", then asks the session to write where it is to its report or STATE file, call `request_compact` with mode `now`, a one-sentence focus and its continuation (role, first read, next step, constraints), and end its turn, or to say in one line why it cannot compact now. It carries no approval. The compaction itself is the usual `now` path (the request, armed at the end of the turn, compacted by the tick, the session's own continuation sent back); there is no new compaction path.

- **Who.** Every person's session: one whose own row in the session registry says `kind: interactive` (a VS Code panel or a terminal), so a `claude --bg` background worker (`kind: background`), a run with no row and a row with no `kind` are never nudged, by their own level or by a lead's `lane_compact` (`not-interactive`). Any interactive session may call `request_compact` with mode `now` for itself, nudged or not; `on-cue` still needs a bound lane, and so does every lead cue.
- **The nudge grant.** An interactive session needs no grant for a `now` request (see Who); the grant is still made and only shows in the log (`requested now-nudged` instead of `requested now-self`). A session that is not a lane may call `request_compact` on a grant only after the mod nudged it: mode `now` only, within 15 minutes of the nudge, once (any stored request spends it, and a bound session's request clears it too). A prompt you type ends it too, so it covers only the nudge turn and the turns that follow without you; `/callboard off` ends it as well. A request refused for its input or for `on-cue` keeps the grant; a nudge whose submit failed gives none. The request runs the usual `now` path to the end, resume included, even when the compaction finishes after the 15 minutes. The grant is self-only: only the mod's own nudge starts it, and the session writes its own focus and continuation. It opens nothing else: such a session still refuses every lead cue (`rename` by the birth checks; `start`, `resume`, `retire` and `compact` as `not-eligible`). The log says `requested now-nudged`.
- **The lead's `lane_compact`.** An armed on-cue request still compacts at once. With no request, the lane checks that it may be nudged (an interactive session, else `not-interactive`), then answers `held nudged` at once if a nudge is already pending (its time is kept, so the lead cannot stretch its 10 minutes; a pending context-level nudge becomes the lead's). Otherwise it is an order (see "An order" below): it checks the compaction gap (`rate-limit`), background agents (`background-work`) and the nudge limit (`nudge-limit`), then records the order and answers `held nudged`; the lead reads `lane_compact refused: held, nudged: the lane was ordered to compact ...`. A request in any other phase (called, armed `now`, compacting, compacted) still gets `no-request`.
- **Toasts for a compaction.** A toast says when callboard starts a compaction ("Callboard is compacting this session now.", just before the `compact` command runs) and in two cases where a request the session had made would otherwise end with no notice turn: a person's message that arrives while it is queued ("Queued compaction cancelled by your message."; a resume after a compaction is not a queued one), and a refusal at the moment of the compaction for a draft in the box, the compaction gap or the context floor ("Compaction skipped: ..."); a `compact` command the engine refuses also toasts, after the start toast). Other silent ends remain (a new turn dropping an armed on-cue request, the resume expiring, `/callboard off`, a turn that ended badly) and are not toasted. A request that a person's message cannot cancel (one already compacting) is unchanged, and no request is kept across a person's message.
- **An order.** A lead, conductor or manager orders a lane in its reach to compact with `lane_compact` on a lane that has no request. Whatever the lane's context size: the 100k floor is lifted for the order, and the 30-minute nudge gap does not apply to it (the compaction gap and the 3-an-hour backstop do). The lane stamps the order (`orderedAt` in its state, `ord:<its session id>` in the store), and the tick sends the lead nudge, which says: this is an order, call `request_compact` with mode `on-cue` within 15 minutes. An `on-cue` request made while the order is fresh is *ordered*: it passes the floor and counts as already cued, so the lane compacts at the end of that turn and the orderer sends nothing more. The order is spent when a compaction begins (the stamp goes), or ends if the mod did not start it (the engine's own, the person's `/compact`): a request that ends without one (a draft in the box, background work, a compact command the engine refused) leaves it, and the orderer is told at the deadline. An order sent again after its first nudge expired unsent starts the 15 minutes over. An unordered request below 100k is still refused (`context-floor`), an unordered `on-cue` request still waits for a cue, and a repeat of the same order is refused `nudge-limit`.
- **The deadline.** The orderer's mod remembers each order it got `held nudged` for (in memory: lost with the session or a reload). 15 minutes after the first order, if the lane's stamp is still in the store (it never made the request), the orderer gets one fixed turn: lane X did not compact after your order; ask the person whether to `lane_terminate` it. Nothing is stopped: `lane_terminate` asks the person in its dialog every time. A lane that compacted, or whose session is gone, has no stamp or no row and costs no notice. A newer order of the same lane restarts the 15 minutes. A lane that is busy in one long turn for over 10 minutes never gets the order text (a nudge is dropped after 10 minutes) and so reads as late; the person decides then. Stamps nobody collected are pruned after a day.
- **The context levels.** At the end of a main-agent answer in a person's session (its own row in the session registry says `kind: interactive`, see Who; never `-p`, the SDK or a `--bg` worker) past the idle level (default 300k), the hook records a nudge; it reads only the token count and the cheap state. The size alone decides the text, for every session: plain, lane, lead, with or without a background agent or shell. Past the idle level the soft text; at or past the working level (default 400k) the hard one. Being busy does not hold the soft text back; a bound lane whose report is signed done and current is still not nudged by its own level (`nudge-dropped lane-done`), and its lead can still nudge it. The two levels are the idle and working levels of `/callboard config` (defaults 300k and 400k); every check above uses the configured levels.
- **Two ways out.** (1) *Between turns:* the 2 s tick sends a recorded nudge once the session is idle (empty prompt box, registry idle). It drops it after 10 minutes, as soon as the session has a request of its own, when the session no longer counts as interactive, or when it may not compact. A recorded nudge survives a reload of the mod. It is cleared and counted before the submit, so a submit slower than 60 s still sends it once (logged `nudge-unconfirmed`, not retried). The nudge step runs last in each tick, after any cue was claimed and answered. (2) *In the middle of a turn:* after a main-agent tool call (a `PostToolUse` or `PostToolUseFailure` hook; a subagent's calls are skipped) in a session past the idle level, the hook returns the same text as `additionalContext`, which the model reads with the tool's result before its next step. It applies the same limits (no request of the session's own, an interactive person's session, not a lane signed done, the throttle below, the compaction gap), takes over a recorded `threshold` nudge (cleared by version, so it goes out once, by whichever way gets there first), leaves a lead or cache nudge to the tick, and is logged `nudged <kind> mid-turn`. A session that may not be nudged is not checked again for a minute. It fires only after a tool call, so a turn with none still gets the nudge from way (1) when it ends. The fallback: if the turn that carried a mid-turn nudge ends (an answer) with no request of the session's own (no `request_compact`), one `threshold` nudge is recorded with `again` (`nudge-due threshold again`) and the tick sends it as the idle turn, without waiting for the 30 minutes (the hourly cap still holds; the kind follows the size, so a turn that ended past the working level gets the hard text). It covers a context the engine did not surface and a model that read it and did not act. Once only: the resend is not a mid-turn one, so nothing follows it. A request, a compaction (the compaction gap, or a size back under the idle level), a lane signed done, or a pending nudge of another kind send nothing. Mid-turn delivery is built from the documented hook result and mock-tested; it is not yet seen live.
- **Soft and hard.** The text follows the context size: past the idle level and under the working level the soft text ("Your context is past 300k tokens. Compact at your next natural boundary: finish the item you are on, but do not start a new one. ..."), at or past the working level the hard one ("Your context is past 400k tokens. Stop as soon as you can, even mid-item: this session is close to an automatic compaction that you do not control, and you would lose your notes. Do not finish the item you are on. ..."), which keeps the clause on a running background agent or shell. The numbers are the configured levels. Both go to every session that gets nudges; a session that is busy is not made to wait for the working level.
- **Throttle.** At most one per 30 minutes per session (and 3 an hour as a backstop), so a nudge the session declined does not come back every turn. A lead's order is the exception: it is sent past the gap, unless a nudge went out since it was recorded. One more exception: one soft nudge, then one hard nudge may follow inside the 30 minutes, once the session reaches the working level; a second hard one waits for the gap, and a hard one is never followed by a soft one inside it. The counts live in the session state. The `$.store` restore hint does not carry them, so a restore can cost at most one extra nudge, still bound by every check above.
- **Off.** `/callboard off` drops a recorded nudge and the grant. It does not opt the session out: a later turn past the level is nudged again.

## Keepalive and settings

A session's prompt cache lives an hour from its last call. A session left idle past that pays a full re-write of its context at its next turn (about 1.25x the context), where a short turn inside the hour costs about 0.1x. So the mod pings an idle session just before its cache expires, as MANAGER did by hand. The design: MANAGER does not send its own `[keepalive]`, so a session never gets two; a large session is told to compact instead of being pinged; only the person changes the settings; every interactive session is pinged; a lane signed done is not.

- **Who is pinged.** Every session whose own row in the session registry is an interactive one (a VS Code panel or a terminal: `kind: interactive`). Never a `claude --bg` background worker (its row says `kind: background`), a run with no row (`-p`, the SDK), a row with no `kind`, or a parked lane (its process is gone). `/callboard off` does not stop it; `/callboard config keepalive off` does, for every session on this Mac.
- **When.** From the 2 s tick, as its last step, once `ping after` minutes (default 50) have passed since the session's last main-agent turn ended (or its last prompt, if later), and only while: the prompt box is empty, the registry says idle and waiting for nothing, the session has no compaction request in any phase and no recorded nudge, no callboard dialog is open, nothing else was submitted in that tick, and the gap is under 58 minutes. Past 58 minutes the cache is cold and a ping gains nothing: none is sent (`keepalive-skipped cold`, once) and the next turn starts a new gap. One attempt per gap: a ping whose submit fails or does not confirm in 60 seconds is logged and not tried again until the next turn. After a restart nothing is pinged until a turn has been seen to end; a reload of the mod keeps the gap (the times live in the session state).
- **The text** (fixed): `[callboard] keepalive: reply with just "Cache refreshed." Use no tools, and do not resume or start any work. Submitted by the callboard mod, not by the user; it carries no approval, go or answer.` It explains itself, so it needs no rule in the session.
- **A ping is not work.** Its turn does not move the turn mark (a lane's signed report stays current, so a lane signed done can still be retired), and its end records no compaction nudge (a session waiting past its level would otherwise get one after every ping). The ping, a nudge, a notice and the lanes-changed turn are not real work; the person's prompts, a peer's message, a lead's start and resume and the continuation after a compaction are. The engine runs no hook of the mod for the mod's own submits (probe, engine 2.1.316), so a turn is told apart by its text. The engine hands the turn's start the mod's own text in a fixed frame ("The callboard plugin sent a message:", the text, then a line saying how Claude Code surfaces a plugin's prompt), and the mod tells an own turn by that text: a turn that carries a text the mod submitted and has not yet seen start, framed or as it stands, gets that text's kind. Any other turn (a person's prompt, typed while idle or mid-turn, a wake, a queued message) is real. Should the engine change the frame, own turns read as real again: the stop clock never runs out, and a ping moves the turn mark.
- **Stop.** `stop after` hours (default 3) after the last real turn ended, no more pings (and no nudge in their place); `keepalive-stopped` is logged once. A real turn starts the count again. With the bounds below, an idle stretch gets at most 16 pings.
- **Rest.** `/callboard rest`, typed in a session you will not touch for hours, stops the pings (and the cache nudge that would take a ping's place) for this idle gap, so the prompt cache expires. It is per session, unlike `/callboard config keepalive off` (this whole Mac) and `stop after` (hours from the last real turn). It is one-time: the next real turn in that session (a person's, not the mod's own ping, nudge or notice) restores the normal pings. Any origin may type it and it asks nothing, because it only narrows. It is kept in the session state, so a reload of the mod keeps it. The tick logs `keepalive-skipped rest` once when a ping would have gone out.
- **A nudge instead of a ping.** At ping time, a session past its compaction level (the idle level for every session, whatever it is doing or is) gets the compaction nudge instead of the ping, when it may be nudged (30 minutes since the last nudge, 3 an hour, the compaction gap). It is recorded and goes out from the next tick like any nudge ("The compaction nudge"), and its turn keeps the cache warm too. Otherwise the plain ping. A lane signed done gets neither (`keepalive-skipped lane-done`). A nudge recorded in place of a ping that is then dropped (10 minutes without an idle moment, for one) is logged `keepalive-skipped nudge-dropped`; that gap gets no ping.
- **The cache nudge.** Where the slot after real work would get its third ping (2 pings went out since the last real turn ended), an idle session (no background agent or shell, not a bound lane still working; leads included) at 150k tokens or more, below its compaction level, gets a compaction nudge instead (`nudge-due cache`), when it may be nudged and may compact. It goes out from the next tick as any nudge, so it waits while the session waits on you (registry `waitingFor`). Compacting while the cache is warm costs less than keeping a large context warm. Below 150k, or working, the ping. A declined cache nudge (the session answers that it cannot compact now, or does not compact) is asked again at the later slots, each gated by the nudge limit (one per 30 minutes, 3 an hour), until the stop clock ends the pings: its turn is not real work, so the ping count stands.
- **No ping while the Mac sleeps.** The tick runs every 2 s while the Mac is awake; each timer call records its time. A gap of more than 5 minutes between two calls means the Mac slept (a dark wake included), and the idle gap it falls in gets no ping (`keepalive-skipped asleep`, once). The next turn starts a new gap that pings as usual. A reload of the mod loses the times: the first tick after it only records.
- **`/callboard config`** prints the settings as a table (Keepalive, Ping after, Stop after, Idle level, Working level, Check-ins, Conductor leads and Escalation, with values such as `ON`, `50 min` and `300k`), from any origin and with no log line (as `status`). While every setting is at its default the table has the columns Setting and Value; as soon as one differs it gains a Default column, holding `✓` on a row at its default and the default value on a changed row (`Ping after | 70 min | 50 min`). Escalation is not a stored setting: it reads ON when a switch is stored and the OFF file is absent, and its default in the table is OFF; `/callboard escalation` changes it. `/callboard config keepalive on|off`, `ping <30-55>` (minutes), `stop <1-8>` (hours), `idle <150-800>` and `working <IDLE-900>` (thousands of tokens; `350k` is taken too), `checkin on|off` (the lead check-ins), `conductor-leads on|off` (a conductor's `lead_open`, see "The conductor") and `reset` (all defaults) change one setting. Anything else, or a number out of range, answers "Use /callboard config [keepalive on|off, ping 30-55, stop 1-8, idle 150-800, working IDLE-900, checkin on|off, conductor-leads on|off, reset]." and writes nothing. The levels are checked against each other as stored: an idle level above the working one answers "Raise working first (now 400k).", a working level below the idle one "Lower idle first (now 300k).".
- **Defaults:** keepalive on, ping after 50 minutes, stop after 3 hours, idle level 300k, working level 400k, check-ins on, conductor leads on. A Mac that ever saved a `/callboard config` change keeps its stored levels (every save stores all the settings); `/callboard config reset` takes the current defaults.
- **Who may change them.** Only you, from your own prompt or phone. A plugin, another session or a script is refused with "Only you can change callboard settings: type the command yourself." and no dialog (`refused config-not-person:<code>`). A change is logged `config-set <setting>:<code>` and the reply names the new value.
- **Where they live.** Machine-wide, in the mod's `$.store` under the key `config` (`{ keepalive, pingAfterMin, stopAfterH, idleK, workingK, checkin, conductorLeads, savedAt }`). Each session reads it at start and then at most once a minute, so a change reaches every session within a minute; a read that fails keeps the last good value. Each field is taken only when it has the right type and lies in its range, else that field's default (`config-invalid <field>`, once per load of the mod); a stored working level below the idle level gives both defaults; other fields are ignored.
- **Residual.** Any process running as you can write the `config` key directly; the origin check on the command is a convenience, not a control. The bounds are the control: at worst a forger gets a ping every 30 minutes for 8 hours after the last real work (16 pings, each about 0.1x of the context in cache reads), keepalive off, or compaction levels anywhere from 150k to 900k.
- **A late change wins.** The ping step reads the session's state, processes and context size after its idle check; if a draft appeared, the person sent a prompt, or anything else was submitted meanwhile, nothing is sent and that gap is missed (`keepalive-skipped late`, once). A ping, nudge or notice whose submit fails leaves no not-real mark behind, so the next turn counts as usual; one that times out keeps its mark, since it may still go out.
- **The nudge needs a person's row too.** The compaction nudge (by the session's own level and by a lead's `lane_compact`) asks for the session's own registry row with `kind: interactive`, the check the ping uses, so a `claude --bg` worker is never nudged. The self `request_compact` and the restores use a looser check: `session.start` said `isInteractive`, or the session has any own row.
- **Install check (probe C11).** After install, run `/callboard config ping 45` once by asking the model to run it (a model-run slash command) and once by typing it. The typed one must apply and the model-run one must be refused with "Only you can change callboard settings" (log `refused config-not-person:<code>`). If the model-run one applies, the engine labels it `prompt` or `phone`: the origin check is then no guard at all, and the bounds alone stand (see Residual); report it. Then `/callboard config reset`.
- Not verified against a live engine. Design and residuals: ADR 0002, the design addition on keepalive pings and `/callboard config`.

## Lead check-ins

A lead left idle is told when a lane in its reach may need it: a lane whose session is gone, one that waits on a prompt, one that went quiet without signing done.

- **What it watches.** Once a minute, whatever the lead is doing, the tick reads the lanes in the lead's reach (the set `lane_list` shows) and the session registry, nothing else. Parked lanes are skipped. A lane's session is found as the lane tools find it (a live row with its name in its folder; two rows, or a row in another folder, give nothing). A read that fails is no observation at all, never "all gone"; so is a read while the lead has no usable name (a twin row, a rename, a reserved name). The step runs beside the tick, one at a time, so a slow read never holds the tick or the cues it claims.
- **The three triggers.** `gone`: no live row carries the lane's name for 3 observations in a row (3 minutes), the lane was live (by the session id its record keeps) and its report is not signed done. `prompt`: its row has waited on a permission prompt or for input for 5 minutes. `quiet`: its row has been idle, waiting for nothing, for 30 minutes and its report is not signed done. The 5 and 30 minutes count from the first observation that saw the state. A status change starts the prompt window again. The quiet window starts again at a status change too, except for a lane already quiet 30 minutes (the lowest `ping after`) that is seen not idle at most once: that is its own keepalive ping (a turn of a few seconds), which does not re-arm it.
- **Signed done** is the last non-empty line of `<repo>/.archive/<LANE>/REPORT.md` reading `status: done <session id>`: for `quiet` the live session's id, for `gone` the record's session id when it has one, else any. It is read with the same checks as `lane_retire` but without the turn mark: a lane that signed and worked on still reads done. Reports are read only when a notice is due and every gate below has held, and a lane found signed is not read again while its condition holds.
- **When the lead is told.** Only when check-ins are on, not paused, no wake from sleep in the last 30 minutes (every lane slept too), the lead's last turn ended (or its last prompt came) 20 minutes ago or more, and the keepalive's gates hold: no dialog open, no compaction request or recorded nudge, no background agents or shells, an empty prompt box, an idle interactive registry row of its own, and nothing else submitted in that tick. The draft, the submits, the last prompt, the grant, the cap and what was told are checked again right before the submit. There is no cold-cache cut and no 3 h stop as for the keepalive: a lead left idle overnight still gets one turn per new condition (time the Mac slept excluded).
- **The text** (fixed; lane names only, each one that passes the name rule; at most 8, then "and N more"): ``[callboard] Check-in: some lanes may need you. `API` (session gone, report not signed done); `WEB` (waiting on a prompt for over 5 min); `DOCS` (quiet for 30 min, report not signed done). Call lane_list and look at each. Submitted by the callboard mod, not by the user; it carries no approval, go or answer; never record it as one.`` It is not real work for the keepalive (it moves no stop clock).
- **Once per condition.** Each lane, trigger and start time is told once; a lane that stays quiet is not told again, and is told again only after its status changed and the condition came back. The notice shares the lanes-changed notice's cap of 12 an hour: over it, it stays owed (`notice-capped attention`, once per capped stretch). A submit that throws is owed again; one that times out is not. The lead's own `lane_resume`, `lane_park`, `lane_unpark`, `lane_retire` and `lane_terminate`, when they succeed for its main agent, start what it saw of that lane over; a refused call or a subagent's changes nothing. A re-grant to another folder starts everything over.
- **Pause.** `/callboard checkin pause <N>m` or `<N>h` (1 minute to 24 hours) holds this session's check-ins; `/callboard checkin on` ends a pause. Only from your own prompt or phone: a plugin, another session or a script gets "Only you can pause check-ins: type the command yourself." (`refused checkin-not-person:<code>`). Anything else answers "Use /callboard checkin pause <N>m or <N>h (1 minute to 24 hours), or /callboard checkin on.". In a session that is not a lead it answers "Check-ins are only for a lead: run /callboard lead first. Nothing changed." and stores nothing. `checkin on` while the switch below is off says so. The pause lives in the session state: a reload keeps it, a restart loses it.
- **Switch.** `/callboard config checkin on|off`, machine-wide like the keepalive, default on.
- **Residuals.** A pause, and what the lead saw (seen live, the observations, what it was told), are lost at a restart; a reload may repeat one notice. A sleep under 5 minutes is not detected as a sleep. A legacy lane (one that names no lead) is watched by every lead of its repo, so each may be told. Signed done ignores recency. A forged registry row (same uid) can make a lane look waiting or quiet: the worst case is a wasted turn of the lead. A check-in step that hangs on an engine read stops check-ins in that session until a reload (`checkin-stalled`, logged once). The manager gets check-ins too, for lead-less lanes only (see "The manager").
- Not verified against a live engine. Design and residuals: ADR 0002, "Design addition: lead check-ins and the grouped lane list".

## The manager

One session per Mac may manage every lane, in any repo: it resumes, compacts, force stops and retires them, and is checked in on for lanes no live lead reaches. Every stop asks you.

- **Turning it on.** `/callboard manager [NAME]`, from any origin, as `/callboard lead`: one dialog, header `Manager`, buttons `Manager` and `Cancel`: "Let this session manage every lane on this machine? It can resume, compact, stop, retire and remove lanes in any repo. Every stop and remove asks you." (another origin is named first). NAME is `MANAGER` or a name reserved on this machine with `/callboard reserve`. With no NAME, the session keeps its current name when that is `MANAGER` or a reserved name, else `MANAGER`; any other name gets a fixed refusal and no dialog. In a session that is already the manager it changes nothing ("Manager is already on in this session.", or with another NAME "...; the name stays NAME."). Type it yourself in a session inside the ai-manager checkout: that session runs with no settings file of its own. The manager runs on the session's model: start that session on Opus yourself; nothing enforces it.
- **Refused** (a fixed text, before the dialog and again after a yes): in a bound lane, in a lead, in a session that was a lead since it started (its lead tools stay declared), and while another live session holds a valid manager presence file, whatever its name, or a fresh one whose check could not be made (a read or `ps` that failed). The manager cannot become a lead or a lane in place, and a session that was the manager since it started is refused `/callboard lead` ("Lead stays off: this session was the manager, so it cannot be a lead until it restarts. ...", `refused lead-after-manager`) and `/callboard lane` ("Lane not changed: this session was the manager, so it cannot be a lane until it restarts. ...", `refused lane-after-manager`, before the dialog and again after a yes).
- **After the yes.** The grant (level manager, no folder) lives in memory, and the yes also saves `manager:<sid>` in the mod's store (the name, the session's start folder and the time), refreshed every 5 minutes while the manager runs (see "After a restart" below). The presence file `<root>/leads/<sid>.json` says `level: manager` and the name, never a repo; it must be written, or the grant steps back. If another manager wrote its file in the same moment, both step back. The session is renamed to NAME from the tick (skipped when it already carries the name, logged `rename-skipped manager`), and `/color cyan` runs from a timer a second later (logged `manager-color`, or `error manager-color`). A briefing note is appended once, and a `callboard:manager` section stays in the system prompt while the grant holds: the eight tools, every stop and every remove asks you and is never unattended, the H2 text of ADR 0001, a pointer to the role as convention: `docs/manager/README.md` in the ai-manager checkout, read at the start of the session, and one line: to ask any other session to compact, it messages that session, only when you ask; the callboard nudges handle the rest.
- **Its tools.** `lane_list` (every repo, grouped by repo and lead), `lane_resume`, `lane_compact`, `lane_terminate` and `lane_retire` (the two stops remove the record). Every other lane tool refuses it (`manager-tool`): it never creates, opens, renames, starts, parks or unparks a lane. `lane_terminate` and `lane_retire` refuse before any dialog, and again after it, a target session that holds a live presence file of its own (a lead, a conductor or a manager carrying the lane's name, or one whose check could not be made: `target-is-lead`), and a lane whose record names another session than the one carrying its name (`sid-mismatch`; the lane's lead, or you, can still stop it). A leads folder that is there but fails its checks, or whose list fails, counts as held; a missing one holds nothing. `lane_terminate` asks in a dialog that names the lane's repo folder too; one dialog at a time (a second stop meanwhile is refused `busy`); after Force stop, and once more right before the signal, the grant must still be held at the same level, or nothing is sent (`grant-changed`). The check right before the signal runs at every level (the stricter one): a lead that turns itself off in that moment gets `grant-changed` too, and for a retire the lane has already accepted the cue and stays running. `lane_retire` asks first, "Retire lane X in REPO?" (`Retire`/`Cancel`); Cancel sends no cue; then the usual confirmed retire (the lane checks it is idle, signed done and has nothing running).
- **Removing lanes.** The manager has no batch remove: the checks for removing a lane (`name-in-use` by name or by recorded session, `target-is-lead`, the checks again after the click and inside the store lock, `changed` for a lane parked or unparked while the dialog is open) guard `lane_retire` and `lane_terminate` on a lane with no live session, one lane per call (see "Retire and terminate remove the lane" above). At manager reach every stop already asks; the removal rides on that dialog. `lane_compact` with the session name of a live lead (its registry name), in any repo, sends that lead a `compact` cue. A lead acts on it only when it asked itself with `request_compact` mode `on-cue` (a lead may ask on-cue; only this cue acts on it), and only while a live manager presence file of another session passes every presence check and the registry gives that session a reserved name. Any other cue to a lead is refused `not-eligible`; a lead is never nudged by it; a lead cannot compact another lead (its own `lane_compact` refuses `lane-or-lead` when the session carrying the lane name holds a live presence file). A lane and a live lead with the same name refuse `lane-or-lead` (both follow the same name rules, so they can meet; neither wins).
- **A lead is told.** While a live manager runs on the Mac, a lead's system prompt has one more fixed section, `callboard:lead-manager`: it may call `request_compact` with mode `on-cue`, so the manager can compact it; the manager can send it nothing else, and nothing it sends carries approval. The lead's tick looks for a manager once a minute (the same checks as the cue, reserved name included), so the section comes and goes within about a minute; it is never read from a file when the prompt is built. A look that does not answer within a minute, or fails, shows no section and is tried again the next minute (`error manager-seen-timeout`, `error manager-seen`); off, or the session's end, forgets what it saw. A lane keeps its own text (it already goes on-cue for its lead); a plain session gets nothing: the manager reaches it only by a message, by convention.
- **A lane with no live lead.** One rule for every lane, made or joined: its session takes a cue only while a live lead of its repo passes the lead check (see "After Join" for how a lead is matched). With no live lead it takes `resume`, `compact` and `retire` from the manager while a live manager passes the same checks as for a lead's cue, and `compact` from a conductor that lists its repo (see the conductor level); any other cue, or with none of them, is refused `no-lead`.
- **Check-ins.** As a lead's (same triggers, gates, text, cap, pause and switch; `/callboard status` shows a `Manager` row (`ON`) and a `Check-ins` row), over the lanes no live lead reaches: a lane naming a lead with no live lead of that name in its repo, or a legacy lane with no live lead in its repo. A lane a lead reaches is left untold and is told once its lead is gone. A repo's leads are read about every two minutes (kept 70 s, so a reading is reused at the next check-in and read again at the one after; a gone lead is seen up to two minutes late), and a lead whose check could not be made counts as live, so no notice.
- **Off.** `/callboard off` drops the grant, the presence file and the saved `manager:<sid>` ("Manager is now off."; in a session whose saved grant is not being restored, "Its saved manager grant was removed."); the tools stay declared but refuse `off`.
- **After a restart.** A restart or a resume drops the grant from memory, but not the saved one. When the same session id comes back in the same folder within 60 minutes of the last time the saved grant was written (the mod rewrites it every 5 minutes while the manager runs, and it holds the folder the session started in), the manager is on again with no question: the toast "Manager is on again." and the log line `manager-restored:silent`, after every check below. A saved grant older than that, one for another folder, one from an older mod (no folder), one dated in the future, or a folder that cannot be read shows the usual Manager dialog instead. The dialog (header `Manager`, buttons `Manager` and `Cancel`) with the question "Restore this session as the manager of every lane on this machine? It can resume, compact, stop, retire and remove lanes in any repo. Every stop and remove asks you. Cancel removes the saved manager grant.". Either way it comes only in a person's session (a registry row of kind `interactive`: never a `--bg` worker, a lane, a lead or a conductor), and once the session is idle with an empty prompt box (the tick; a missing row is tried again for 15 ticks). A compaction keeps the grant in memory, so it asks nothing. **Manager** (or the silent restore) grants it after every usual check again: one manager per Mac (the presence file), a reserved or valid name, not a lane, lead or conductor, and the re-check after the yes. **Cancel** deletes the saved grant. **No answer** (a timeout or a dismissal) restores nothing and keeps it. A check that fails, before or after the yes (another manager came up, the presence file could not be written), restores nothing, is logged and keeps the saved grant; `/callboard manager` still works by hand. Only `/callboard off` and the restore's Cancel remove the saved grant: a Cancel on a lead's or a conductor's question does not. A session is offered the restore once per process (a compaction or a reload never asks again), not while a lane rebind, a lane hint or a store record naming it is still pending, and the question says that you made it the manager here earlier and that Cancel is the answer if you did not. The person's own `/callboard manager` while the restore waits ends the restore. A saved grant that fails the parse is deleted with no question; another session's bad one is pruned at start.
- **Residuals.** The saved grant, `manager:<sid>`, is a store value any same-uid process can write, like the settings and the conductor's: it can make the restore dialog appear (a clean name, a clean folder and a date of the last 30 days; the name is judged again, and outside the 60-minute window the grant itself comes only from your click) or, deleted, stop it. Inside the window, a process running as the same user that writes a fresh-looking saved grant for the same session id and folder gets a silent restore (the same checks run); the dialog still covers every other case. One manager per Mac rests on the presence-file check; two dialogs answered in the same moment are closed by the re-check after the yes and by the check after the file is written. `manager-exists` counts any valid manager file whatever its name (and a fresh one whose check failed), so a same-uid process whose file names a live claude pid can block a manager's start. The reserved registry name is required only where a manager file is trusted: a lead's compact cue, an adopted lane's cue with no lead, and the lead's on-cue section; there, such a process can at most make a lead act on its own on-cue request, or a lead-less adopted lane take a resume, compact or retire cue it confirms itself. The rename right after the grant is unprobed (P6): its outcome is logged. A lane record's `sid` that is stale (its one-time sync failed, or the lane runs without the mod) blocks the manager's stop with `sid-mismatch` until the lane restarts; its lead or you can still stop it. An older record has no `sid`: the manager's stop matches it by name and folder only, and the dialog still gates it. The manager runs with no settings file: its deny and ask limits (no dispatch, no GitHub, no git writes, no hooks or settings edits, a kill asks) are convention in the role, not enforced. Every other rule of the manager role (ADR 0001) is convention too. A remove matches a live session by exact name, as the lead's; the grant check inside the store lock is a backstop no command path reaches.
- **Reserved names.** The repo reserves `MANAGER` only. `/callboard reserve NAME` reserves another name on this machine alone (kept in the mod's store, so no other machine gets it), for example the name your manager session carries; `/callboard reserve` lists them (a Name and Source table: `built in` or `this machine`, with `None added on this machine.` under it when the machine list is empty) and `/callboard reserve remove NAME` takes one off. Changing the list is the person's own: from the prompt or the phone; any other origin gets "Only you can change the reserved names: type the command yourself." A reserved name, or a look-alike of it (other case, `-` or `_`, trailing digits, look-alike digits such as `MANAG3R`), can't be taken by a new lane, a join, a rename or a lead: `/callboard lead` in a session with such a name is refused `lead-name-reserved`. The manager may carry a reserved name, exactly as written. An add is refused while a lane record, a lead stamp or a live lead carries the name. The add's in-use check matches look-alikes too (`LEAD2` in use blocks reserving `LEAD`), and the live manager's name can't be removed while it runs. Lane creation, joins, `/callboard lead` and `/callboard manager` read the list fresh; other checks see a change within a minute. A stored lane list is judged by `MANAGER` alone, so a name reserved later never makes it unreadable.
  - **Names to reserve.** The repo reserves `MANAGER` only. On a machine whose manager or rules trust a session name (the manager's own, or a sender name in your rules), run `/callboard reserve NAME` for each before relying on it; until then a lead may give a lane that name.
  - **Residuals.** The reserve key is a store value any same-uid process can write, like the settings: a convenience, not a control. The Edit and Write deny rules keep agents' file tools off it, not a shell write; a cleared list unreserves the machine's names, and a forged one can reserve a live lead's name (its lanes then refuse its cues until `reserve remove`). Manager trust is unchanged by it: a lead still needs a verified manager presence file. A read of the list that fails keeps the last good list (empty if none was read since the session started), so the paths above then judge names by `MANAGER` alone; the failure is logged (`error reserve-read`). The extension knows only `MANAGER`, so it does not keep a panel that carries a machine name from being closed.
- Not verified against a live engine. Design and residuals: ADR 0002, the design addition on the manager level, manager tools and check-ins.

## The conductor

A conductor is a bigger lead: a session in a small repo of its own whose reach is a list of repos. It lists their lanes, compacts their leads (only a lead that asked on-cue) and force stops a lane; every stop asks you. It can open a panel for a new lead in one of its repos (`lead_open`, below). It never creates, opens a lane, starts, resumes, parks or retires a lane, and it cannot stop a lead.

- **The list.** One file in the conductor repo, `.claude/callboard-conductor.json`: `{ "repos": ["../repo-a", "../repo-b"] }`. An entry is `../NAME` (a repo beside the conductor repo) or, as a fallback, an absolute path; at most 16 entries and 4096 bytes. Every read resolves each entry to its real path: it must be its own real path, a git root and not too broad; one that is not is left out and named in the replies.
- **The conductor repo is a repo of its own.** It must be a git root with no lanes and no lead (a lead of a parent repo included): `conductor-repo-in-use` otherwise. It cannot list itself.
- **Changing the list.** Type it yourself (the prompt or the phone; any other origin is refused "Only you can change the conductor list: type the command yourself."):
  - `/callboard conductor add NAME|../NAME|PATH`: one dialog, header `Conductor`, buttons `Add` and `Cancel`: "Let conductors in FOLDER reach the lanes of ../NAME? The list would then be: ../a, ../b (2 repos)." Refused before the dialog: a lane, a lead or the manager, a session that was a lead or the manager, the conductor repo itself, a repo inside or around it or a listed one, a duplicate, a 17th repo, a list the presence file or one grant question could not carry (`conductor-list-long`), a folder that is not a git root, too broad, missing or not its own real path. Every check runs again after Add.
  - `/callboard conductor remove NAME|../NAME|PATH`: no dialog (it only narrows). It matches the file's entries by name, so a deleted or renamed repo can still be removed.
  - The writer keeps the file a plain file of yours: it refuses a `.claude` folder or file that is a link, has two links or is writable by group or other (`conductor-file-unsafe`; the reader refuses them too), and a file changed while it wrote (`conductor-file-changed`).
- **Paths in the dialogs.** A repo beside the conductor repo shows as `../NAME`; any other path in full, home as `~`, never cut, marked "(not next to FOLDER)".
- **Turning it on.** `/callboard conductor` in the conductor repo, from any origin as `/callboard lead` (another origin is named first): one dialog, header `Conductor`, buttons `Conductor` and `Cancel`: "Make this session a conductor for these repos? ../a, ../b. It can list their lanes, compact their leads, and force stop a lane: every stop asks you. It stays a conductor after a restart until you run /callboard off." The repos it names are the session's approved list. After the yes every check runs again and the list must resolve to the one shown (`conductor-changed`). Reply: "Conductor is on from your next prompt.\nEvery stop asks you." Starting a session in the conductor repo does nothing by itself.
- **The file only narrows.** At every conductor tool call (and every 10 s on the tick) the reach is the file, resolved, intersected with the approved list. A repo written into the file by anything but an `add` click in this session is not reached: `/callboard conductor` then asks again with the whole list, the new repos named first ("New since you approved: …"; from your prompt or phone only; another origin gets the reach and what is out, as a Repo and State table: `in reach`, or `out of reach: REASON`). A repo that leaves the file, or stops resolving, also leaves the approved list (the ratchet), so a repo removed and re-added in another session needs a click here too.
- **After a restart.** The grant is saved as `conductor:<sid>` in the mod's store (the conductor repo and the approved list) and comes back at the next start of the same conversation, in the same folder, in a person's session (a registry row of kind `interactive`: never a `--bg` worker), not a lane on its way back and not a lead. If the file names nothing new, it comes back with no question ("Conductor is on again for FOLDER (N repos)."). If it names a repo you have not approved, a dialog asks first once the session is idle with an empty prompt box: "FOLDER's conductor list changed since you approved it. New: .... Restore this session as a conductor for these repos? .... Cancel removes the saved conductor grant.". Conductor restores with the whole list; Cancel deletes the saved grant; no answer restores nothing and keeps it. A list file that cannot be read restores nothing and is tried again (15 ticks).
- **Its tools.** `lane_list` (its repos' lanes, and its repos' live leads with no lanes, as one table under a `**Conductor NAME** · live` header line), `lane_compact` (a live lead of its repos by session name, only on that lead's own on-cue request; or a lane in reach, as a lead's, including one whose lead is gone), `lane_terminate` (the manager's path: the repo named in the dialog, one dialog at a time, `target-is-lead` and `sid-mismatch` before and after). Every other lane tool refuses `conductor-tool`. No check-ins and no lanes-changed notice.
- **`lead_open`.** A conductor tool, `lead_open { repo, name, task, model? }`: it opens a panel for a new lead in one of its repos; it does not make the panel a lead, and you still type `/callboard lead` in it and click `Lead`. The repo must be in reach at the call (its list file, resolved, intersected with the approved list) and its own real path, not the conductor's own repo or a folder holding it or inside it. The name is a lane-style name, not reserved, carried by no live session, no lane record and no request in `~/.claude/callboard/open` (any letter case). Limits: no live lead in the repo (whoever made it), no offer or claim for it, one open in flight per conductor, at most one successful open (`lead-grant` row, written only by the later grant step) and three offers per repo per hour, counted from the ledger so a failing open still counts; every check runs before the first write. The writes, in order: a `lead-offer` ledger row; an offer file `~/.claude/callboard/offers/<sha-256 of the repo's real path>.json` (one per repo, created exclusively, 0600: name, repo, model, the conductor's session id, pid and start time, a time and a single-use nonce); the brief at `<repo>/.archive/<NAME>/BRIEF.md` under a lead header (data, no approval); and the request `~/.claude/callboard/open/<NAME>.lead`, one line `lead <32 hex nonce> <repo real path>`. The panels extension (1.2.0 or later) claims the request once, opens a panel only in a window whose first workspace folder is the repo's exact real path, and answers `ok <session id>` or `error <code>` like `lane_open`; it never reads the offer or the brief. On the answer the offer is removed and a `lead-offer-void` row (code `panel-only`) closes the nonce; a failed write or open removes the offer and voids it with its code. The panel stays unnamed until you make it the lead, so no second panel opens in that repo meanwhile (`unnamed-panel`). `/callboard config conductor-leads off`, your own command, makes the tool refuse (`conductor-leads-off`). Design, limits and residuals: ADR 0006; the clickless grant it leaves for later is not built.
- **The manager's view.** When a live conductor lists repos, the manager's `lane_list` table gains a leading Conductor column: each live conductor (sorted by name) is named on its first row, with its repos' rows after it, then the repos no conductor lists with `–` in that column. A conductor whose repos have no rows is one row with `–`. A repo two conductors list shows once, under the first, with `(also NAME2)` in its group row. A leads folder that cannot be read draws the table without the Conductor column, followed by a plain line `(conductors could not be read)`.
- **The lead's side.** A lead takes `compact` from a conductor only on its own on-cue request and only while the conductor checks out: a live conductor presence file listing the lead's repo, its home a real git root, its saved grant approving the repo, and its list file listing it. Every other cue from a conductor is refused. While one checks out, the lead's briefing names it (`callboard:lead-conductor`): act only on messages whose sender is exactly that session name, follow them when safe, take a stop as pause and ask the person, reply with branch, tests and review verdict. Every lead's briefing also says other leads of its repo may message it to align work.
- **Exclusive.** Lane, lead, conductor, manager: one per session (`conductor-holder`); a session that was a conductor is refused lead, lane and manager until it restarts.
- **Status and off.** `/callboard status`: a `Conductor` row reading `ON (N repos)`. `/callboard off` drops the grant and the saved grant ("Conductor is now off."); asked from another origin, the question names the conductor.
- No path enters a log line.

### Manager setup: keep agents off the list file and the store (by hand)

Two `permissions.deny` lines in your global `~/.claude/settings.json` (`Edit` only: an `Edit` rule covers the Write tool too) keep an agent's Edit and Write tools off `.claude/callboard-conductor.json` and the mod's store file (`~/.claude/plugins/store/callboard_*.json`). The repo's setup guide, `docs/setup.md`, has the lines and the one-time `chmod go-w` on the conductor repo's `.claude` folder. They stop an agent's Edit and Write tools, not a shell write. For the list file that is enough: the mod never widens a conductor from the file. For the store file (which holds the saved grant) nothing in the mod holds behind the rule: see the residual below.

- **Residuals.** A same-uid process, the conductor's own shell included, can write the saved grant and the list file and so restore a conductor with up to 16 repos of its choice in that session at its next restart, with no dialog; what it gains is a read of lanes, a lead's compaction on its own request or a lane nudge, and a force stop behind your dialog. A forged `kind: interactive` row passes the person gate. Messages have no sender proof. Conductor names are not reserved.
- Not verified against a live engine. Design and residuals: ADR 0002, the design addition on the conductor level.

## Prompt answering: the hook, the floor, the files and the switch

Off by default. Nothing in the hook, the files or the switch lets an agent write a decision; the tools that do (`prompt_answer` and its kin) are under "The lead tier" below. This part is the hook that applies a decision, under every check, and the files, ledger and switch around it. ADR 0004 has the design. Pure logic is in `mod/hooks/prompts.ts` (tested by `mod/hooks/prompts.spec.ts`); the hook and the wait are in `mod/hooks/engine/answer-hook.ts` and the commands in `mod/hooks/engine/commands.ts`.

- **Switch.** `/callboard escalation` is the person's own command (prompt or phone) with one dialog (header `Escalation`, `Allow` and `Cancel`) that names exactly what turns on: permission prompts and single-choice questions, for every lane and lead; `/callboard escalation off` is any origin, no dialog, and clears the stored switch. Any other word after `escalation` is the usage line. There is no per-lane command: `/callboard off` in a lane's session takes that lane out, and its prompts and questions stay the person's. The older `/callboard answering ...` command is gone. The stored value (`$.store` key `answering`) is `{ scope, asks, savedAt }`, with `asksScope` for questions; `/callboard escalation` writes scope `all` and asks scope `all`, and a narrower value an earlier version stored still reads and still applies. The file `~/.claude/callboard/prompts/OFF` stops answering whatever is stored. Both are read at each request and on each 2 s poll of a waiting hook (the scope too: a switch narrowed to another lane or lead ends the wait), which then returns what the chain beneath gave and leaves the dialog to the person (`off` row). `asks` is stored as `false` and has no effect (the first version's `asks: true` opens nothing); the questions scope is `asksScope`, set to `all` by `/callboard escalation` (below). `/callboard config` shows the switch as its Escalation row (ON when a switch is stored and the OFF file is absent), and `/callboard escalation` ends its answer with the floor line. There is no `/callboard prompts` command.
- **The hook.** A `classic.PermissionRequest` hook in the asking session: only a bound lane or a lead is judged (a lane starts at its lead; a lead's own prompt starts at the conductor or the manager; with no live tier in reach the prompt gets an `abandoned no-tier` row and no request). It calls `next(e)` first and returns any non-empty result whole; checks the `tool.check` entry joined by session, tool and whole-input hash (a missing entry, or two calls in flight on one hash, leave the prompt to the person); classifies the ask (a rule's ask, the mode's own ask and ai-toolkit's GitHub guard on four tools are agents' to judge; any other hook, a setting, a plugin or a ceiling is the person's; a question is agents' to judge only when it is the mode's own ask and the questions scope covers its lane, and is otherwise the person's, as below); applies the floor; then writes a request file and waits through `/bin/sleep` (a hook has 10 s of its own time per dispatch). An ask whose event carries an `agent_id` (a subagent's) is the person's: the hook returns at once, with no request and no wait, because the engine shows a subagent's dialog only after the hooks return (probe P-I5).
- **`tool.check` only observes.** It returns the engine's verdict unchanged, every time: a mod's `tool.check` can pierce a deny rule, so callboard's never changes one.
- **The floor** (no agent answers these, whatever it judges; checked at the request and again at apply): the person's own self-protection. That is: edits to settings files, hooks and rules (by path and real path for the file tools, case-insensitively, by text for Bash; this includes `.git/config`, git hooks folders, `.mcp.json`, `install.conf`, git settings that run code, and callboard's own state); any write that lands in the live checkout of this repo, whole, or in the toolkit checkout that the hooks and rules under `~/.claude` link into, whole (the mod's code, `CLAUDE.md` and `CLAUDE.local.md`, `docs/manager`, `rules`, `.claude`, the toolkit's `agents`, `skills` and `tools`), by path, real path, glob or shell text; a git call that rewrites a work tree in, under or above one of those folders, or from a folder that is not known (every tool of the git server but the read ones (`git_status`, `git_log`, `git_diff`, `git_show`, `git_blame`, `git_reflog`, ...) on a protected folder or with no absolute path, `git_set_working_dir` included, with the listing modes of `git_stash`, `git_worktree` and `git_remote` the only reads among them; the Bash verbs that do the same, `git -C` together with `--work-tree` or `--git-dir`, and `gh pr checkout`, `gh repo sync`, `gh repo clone`, `gh repo set-default`, `gh repo fork` with a remote or a clone, `gh gist clone`, `gh run download`, `gh release download`, `gh attestation download`, `gh codespace cp`, `ssh` and `rebuild`, and `gh issue develop` with a checkout); a shell verb that may write where it runs without naming the file (a build, a package manager, `curl -O`, an unpacker, a script) when the session's folder is inside one of those folders, or is not known (a `cd` to a variable, `cd -`, `popd`, no folder from the event), a `cd` to a glob that may land there included: only read-only verbs and git run there (a write that names a target outside them reaches the tiers, from a live-checkout session too); removing or replacing a folder above one (`rm -rf` of a parent of the checkout or of `~/.claude`, `find -delete` from above them, and `find` with a delete, a file write or a command to run and no start folder, which starts where it runs), and a delete, move or write verb that `xargs` or `parallel` hands its targets (they have no path to judge); a shell line that cannot be read (`eval`, `bash -c`, an interpreter's `-c`, a verb built at run time, a database client, text that does not parse); `gh` calls that change settings, secrets, rulesets, auth, extensions or aliases (a `gh api` DELETE or PATCH of the repository itself, every GraphQL mutation except `mergePullRequest`, ref writes, issues and comments, and a GraphQL query read from a file or a variable), and the paid `@claude` check; and other dialogs (`ExitPlanMode`). Bash is a string, so those matchers are best effort. Merges, force pushes, pushes to main, master or production and destructive deletes outside those folders are not on the floor: they reach the tiers like any other call, and the rubric passes them up as risk-list items. **One exception: a lane's own report.** A lane signs by writing `<repo>/.archive/<LANE>/REPORT.md`, which lies under the live checkout when the repo is one, so the checkout rule would hold every such write as the floor (a `floor settings` row, no request, no notice: the person would see a dialog no tier knew about). That one write is answerable by the tiers under the normal rubric: a `Write`, `Edit` or `MultiEdit` (no notebook, no second path argument, no shell) of exactly the path the session's own lane record gives, spelled exactly (the case too), with the file's real path equal to the real path of that repo plus `/.archive/<LANE>/REPORT.md` and the file either absent or a plain file of the person's with one link. Another lane's report, any other `.archive` file, any other path under the checkout, a link, a second hard link, a changed case, callboard's state folder, settings and hooks all stay the floor, and the other settings rules still apply to the report's own path. The request file names the path (`ownReport`) so that a tier's `prompt_answer` and the hook's apply check judge the same file; a request without it, or whose path does not read as `<repo>/.archive/<its lane>/REPORT.md`, gets no exception. A prompt that stays the person's still leaves only a ledger row (`floor`, `not-judgeable`, `abandoned no-tier`): a notice to the lane's lead for those needs a new fixed turn with its own cap and is not built.
- **Files** under `~/.claude/callboard/prompts/<session id>/` (folder 0700, files 0600): `<id>.request.json` (a redacted copy of the input, each string capped at 10 KB, 32 KB for the input, so a normal pull request body arrives whole; the file is at most 48 KB; removed when the request closes), `<id>.decision.json` (written by `prompt_answer`, or by the mod for a relayed answer), `<id>.done` (a tool's end or a No click). A decision applies only when its id, input hash and nonce match, it has not expired (21 minutes of awake time, each poll adding at most 10 s), the floor still passes, its author is a live lead of the asker's repo that is not the asker and that the switch's scope covers, the ledger holds an `answered` row for it, and the dialog has been open 30 s of awake time (an early decision is held, not dropped). Each refusal is a `dropped <code>` row and the wait goes on; a `by-sid` or `relay` refusal that rests on a lookup that failed (the registry, a presence file, `ps`) is held for the next poll instead, with no row (only a registry read, a presence check or `ps` that failed counts; a failed git-root stat or relay read still reads as a no).
- **A person's click** ends the wait: a No aborts `next.signal`; a Yes fires no signal, so the tool's own end (`PostToolUse`, `PostToolUseFailure`, `PermissionDenied`, by `tool_use_id`) and the session's own registry row (`waitingFor` seen set for this request, then empty) carry it. After `next(e)` the hook looks at both again before it applies anything, and once more right before it returns a decision (the row is read last, so a click that already reached it wins). **A limit, seen in a live test:** the engine sends the hook no signal for a Yes while the hook is waiting, the transcript records the person's decision only when the tool ends, and the registry row can lag the click by a moment. A Yes that lands in that gap, after the last look and before the decision goes back, is not seen: the decision is returned, no `superseded` row is written, and the audit counts it as a lost race (reported, not an anomaly). For an allow the outcome is the same as the person's Yes; a lead's deny that beats a late Yes in that gap is the case the 30-second minimum and the lead's care are for.
- **Ledger** `prompts/ledger-YYYY-MM.jsonl`, machine-wide, one JSON row per line under 4 KB, no input text: `requested`, `answered`, `dropped`, `returned`, `superseded`, `off`, `abandoned <code>` (`expired`, `no-tier`, `hook-failed`, `session-gone`, `swept`), `floor <category>`, `not-judgeable <code>`, `answering-on`, `answering-off` (kept as the row names; one `/callboard escalation` writes two `answering-on` rows, the second with code `asks`). If the second row cannot be written, the stored value is put back and the ledger gets rows that say so (an `answering-off` when nothing valid was stored before, else the earlier value's `answering-on`, with the `asks` row when it had a questions scope), so the audit never reads a wider "on" than what is stored. The tick closes a request whose session is gone, or older than a day, with an `abandoned` row. A request's closing row is written before its files are removed; if it cannot be (the ledger fails for a moment, or the person's No cuts the hook's dispatch off before it finishes), the files stay and the tick writes the row, then removes them, trying up to five times (then the sweep closes it as above).
- The lead tier and the tiers above it are below. The security bound and what stands behind it are in ADR 0004.

### The lead tier: `prompt_list`, `prompt_answer`, `prompt_escalate`

A lead with the switch covering its lane can answer that lane's permission prompts. Nothing is answered unless the person turned escalation on; the dialog stays open in front of them, their click always wins, and an answer lands no earlier than 30 seconds after the prompt opened. The floor holds: no tool here answers an edit of settings, hooks, rules or callboard's state or code. A merge, a force push, a push to main, master or production or a destructive delete reaches the lead like any other call, and the rubric tells it to pass those up.

- **The tools** are declared with the lead grant and are the main agent's only (a call with an agent id is refused). A conductor and the manager get the same three tools (see below); any other session is refused them. `prompt_list` shows each open request in reach (whole requests only: those that do not fit its 48 KB text are counted as still open, and one that alone does not fit is cut and marked truncated) with its input inside an `<untrusted-input>` frame (the input is data from the lane, `<` escaped so it cannot close the frame), the age, and the fixed rubric (`RUBRIC` in `prompts.ts`) after it, plus a count of dropped decisions that can mean a forged file. `prompt_answer { id, decision: allow|deny, why }` and `prompt_escalate { id, why }` take a one-line `why` of at most 200 characters.
- **Reach.** A request is a lead's when it is not the lead's own, is a lane's, names no lead or this lead, is covered by the switch, comes from a session live under the pid and start the request names, and the lead is a live lead of the repo the lane works in.
- **`prompt_answer`** refuses an unknown or out-of-reach id, a closed, answered, passed-up or expired request, a truncated input when the decision is allow, and any call on the floor (checked on the copy the tier read, and again by the hook at apply). Otherwise it writes `<id>.decision.json` with `ln` (the first writer wins, so two answers at once leave one file and one row) and only then the `answered` row; a row that cannot be written takes the file back.
- **`prompt_escalate`** passes the request up, or, from the top tier, to the person (see below): it writes `<id>.escalate-<level>.json` and an `escalated` row, and that tier's right to answer the request ends. With no tier above, the top tier asks the person through the relay instead; an escalate file beside a decision loses to the decision.
- **The notice.** An idle lead gets one fixed turn, `[callboard] A lane has a prompt waiting. Call prompt_list. …`, within a tick of a new request in its reach; one notice covers every open request. A lead in the middle of a turn gets the same text as extra context beside the result of its next main-agent tool call (like the compaction nudge; a subagent's call carries none), within a tick of the request, so a busy lead does not make the lane wait for its turn to end; the hook reads no file, it claims the mark the tick's scan made, and if both a nudge and a notice are due they arrive as two separate texts. A request is told once, by whichever path comes first; the idle turn stays the fallback: for a turn that ends with no tool call, and, once, for a request still open when the turn that carried the mid-turn text ends (the engine may drop the context, or the lead may not act on it). Nothing is told mid-turn while the session has a compaction request of its own. At most 30 an hour per lead for both paths together, on its own counter (the lanes-changed counter is separate); a notice over the cap stays owed and goes out once a slot frees. The idle turn is a turn of the mod's own and not real work for the keepalive clock.
- **The comment cap.** Per repo and PR, at most 2 `--comments` and 1 full review count, from the `returned` allow rows of this month and last (the rows carry `cap` and `target`). Every string that mentions `@claude` counts: one that starts `@claude review --comments` and has no other mention is a `--comments`, anything else a full review. `prompt_answer` refuses over the cap, and the hook checks again at apply; a ledger that cannot be read counts as over, so the prompt stays the person's.
- **The audit** is `prompt-audit.mjs` (read-only; see Parts). Beside the ledger rules it checks that each `answered` row names a lead whose own transcript holds a `prompt_answer` call for that request id (a hand-written row and decision file have none: anomaly `answered-without-prompt-answer`; a lead transcript it cannot find makes the run incomplete). The bound: someone who also writes that call into the lead's transcript passes. It reads transcript lines up to 32 MB like any other and streams a longer one past, looking only for permission-decision text (a problem only if it finds some). A request with no ending row and no request file after 10 minutes is the anomaly `request-closed-without-row`. Rule e compares each request with the latest `answering-on` or `answering-off` row at its time (an `answering-off` with code `asks` only turned the questions off and is skipped): no earlier on row is `requested-before-answering-on`, and a latest row that is an off is `requested-while-answering-off`. An off typed between the hook's switch read and its requested row (at most 2 minutes before it) is not flagged when the request's own last row is an `off` row: the request was raised under on and the waiting hook closed it. The relay-left count shows the tier that asked, from the row's `tier`. **Before any live answering**, the two lines in `docs/setup.md` ("Before prompt answering") go into the person's own settings.

### The conductor and manager tiers and the relay

The ladder is lead, then conductor, then manager (a missing or not-live tier is skipped), and its top asks the person.

- **Tiers and windows.** A conductor reaches the requests of its repos' lanes; the manager reaches all of them. A request is open to each live tier in turn: the first at 30 seconds, the next at 5 minutes, the last at 10 minutes after the request (awake time), and a pass-up (`prompt_escalate`) opens the next tier at once (30 seconds still bind the first). A tier's window never moves later: the earliest time computed for it stays (kept in the mod's memory, per request and tier), so a lower tier that goes live after the request does not push a higher tier's slot back after that tier was told to act. A tier never answers its own prompt, and a request whose asker is no longer visible in the registry has no tier. Past 20 minutes awake with no relay, the hook denies with `DENY_TIMEOUT_MESSAGE` (`expired-denied timeout`); a question is never denied.
- **The top tier** is the highest live tier in reach that is not the asker, has not passed the request up and is not itself asking. `prompt_list` says what the turn is for each request: whether it is with the person, whether the caller is the top ("You are the top tier for this prompt"), who is above, or when the window opens. A tier below the top passes up.
- **The relay.** The top tier's `prompt_escalate` writes `<id>.relay.json` (id, short id = the first 8 hex of the id, who, when, nonce) and a `relayed` row, and tells the tier to have a small subagent summarise the call and ask the person in its own session with `AskUserQuestion`: header `Relay <short>`, options `Yes` and `No` (for a lane's question, the lane's own labels: see Questions below), plain words about what the call does and its risk. The request is then with the person: no tier is told of it, no agent decision lands (an `answered` beside a relay is dropped `relay`), and the hook's wait runs up to 2 hours with a 10-second poll, without the 20-minute deny. The engine's hook budget is 10 s of the hook's own time per dispatch, and a `$` call does not spend it (the wait sleeps through `/bin/sleep` as a process call, `pause`), so the 2 hours are within the documented budget. A hook that did run past it would be skipped and its `.catch` would hand the ask to the dialog, which ends the relay cleanly with the person. The docs name no wall-clock cap on a PermissionRequest dispatch, and the longest wait probed live is about 22 minutes: a 2-hour wait is not probed (ADR 0004, "Hook budget for the relay wait").
- **The light link.** The mod reads the tier's `AskUserQuestion` result in its PostToolUse hook, main agent only. A header `Relay <short>` that names an open relay of that session with an answer of exactly `Yes` or `No` makes the mod itself write `<id>.decision.json` (`via: person`) and an `answered` row (`via`, `short`); any other answer, a dismissal or a failure writes `<id>.left` and a `relay-left` row, which ends the hook's wait and leaves the prompt in the lane's dialog for the person (the request does not go back to the tiers). The answer counts only when `<id>.asked` is there (the mod saw the question raise its permission request, with nothing beneath answering it), the question is single-choice with exactly the options `Yes` and `No`, its text is unique in the call, and no other question of the call carries the same header. The mark is spent by the question it marked (an answer, a dismissal or a question a hook beneath answered removes it), so a later question needs its own. An answer to a request already closed or decided writes `relay-late` and puts one fixed line in front of the tier (`RELAY_LATE_LINE`) so the person is told. The question's wording is never read. `<id>.asked` marks that the question was seen (`prompts/asking/<sid>` also marks the tier as asking, so it is not the top of another request meanwhile).
- **A relay that is lost.** Not asked within 2 minutes, or two presence checks in a row finding the tier's session gone (60 seconds awake), writes `relay-lost` and takes the relay back: the request is open to the tiers again, and the tier that is then the highest may ask the person. A dismissed question (`relay-left`) is not: the wait ends and the person's dialog stays. While a relay stands it is sticky: a higher tier that appears later does not take it over. A relay whose question the person had on screen never ends in the 20-minute deny, even if it is lost later (the wait expires at 21 minutes of awake time from the request, at once if the loss comes later, and the dialog stays). A dismissed question fires no hook (the engine tells the model only "Denied by user"): the mod reads it at the tier's turn end, where a relay question that was asked and is still unanswered is left (`relay-left`, no decision), never read as a No. A decision that is dropped (cap, floor at apply, wrong tier, a bad file) is taken away after its `dropped` row, so the request is open to the tiers again.
- **Cleaner-command deny.** Any tier may deny a call it cannot judge with a why that starts `Too complex to judge:`; the lane gets `deny-unclear` in the ledger and a message asking for a simpler command. A truncated input is never relayed or allowed (denied only).
- **Notices.** The notice goes to every tier in turn, each when its own window opens (a lead at once; a conductor or manager at the window's open, rechecked every 15 seconds; a pass-up opens the next at once), idle or beside a tool result, under the same cap of 30 an hour per tier. A request with a relay is told to nobody; if its relay is lost, it is told again.
- **The audit** adds: a person's answer whose relaying tier's transcript holds no `Relay <short>` question answered `Yes`/`No` (`person-answer-without-relay-question`); an answer or returned decision while the request was with the person (`answered-while-relayed`, `returned-while-relayed`); a tier that answers after its own pass-up (`answered-after-own-pass-up`). A person's answer also needs a `relayed` row of the same tier session and the request's own short id (`person-answer-without-relayed-row`, `person-answer-short-mismatch`); with several relay questions in one call each answer is matched to its own question's text. It lists and counts `relayed`, `relay-lost`, `relay-left`, `relay-late`, `expired-denied`, `deny-unclear` and the person's answers, and prints each relayed question as the tier put it to the person (from the tier's transcript) beside the request's tool and pattern: the place to read a tier's summary after the fact.


### Questions: a tier answers a lane's single-choice question

A lane's `AskUserQuestion` is an ordinary request with `tool: AskUserQuestion`. Off by default: the person's one `/callboard escalation` dialog turns questions on together with permission prompts (it sets the questions scope to `all`; `/callboard escalation off` clears both from any origin). A value an earlier version stored may have no questions scope or a narrower one. With no questions scope a lane's question is the person's, written as `not-judgeable question-scope` with no request, and a lead's own question is always the person's.

- **Which questions.** Exactly one question, single select, two to four options whose labels are plain text (at most 200 bytes, no control character, no repeats), and a header other than `Person`. Any other is the person's, with its own `not-judgeable` code (`question-count`, `question-multi`, `question-options`, `question-person`, `question-shape`).
- **The answer.** `prompt_list` shows the question and its numbered options inside the untrusted frame, with the question rubric after it. `prompt_answer { id, decision: "answer", option: N, why }` (`allow` and `deny` are refused for a question, and a truncated one cannot be answered) writes a decision with the index and the label the tier saw. The hook checks both against the live input and returns `allow` with `updatedInput.answers` holding the live label, trimmed, and `(answered by <level> <NAME>)`, the name read from the tier's presence file, never from the decision. The 30-second hold and the person's click apply as for a permission prompt; a click fires no abort, so the registry row and the tool's end still end the wait.
- **No deny.** A question is never denied for lateness: with no tier answering, the wait ends at 21 minutes and the card stays.
- **The question relay.** The top tier's `prompt_escalate` on a question returns the relay steps (no label in them). The tier asks the person with `Relay <short>` and, as options, exactly the lane's labels, one for one. Step 0 of the lane's hook denies a relay question whose options differ, with a fixed line, and asks nothing. The person's pick lands in the lane as the bare label, with no suffix. Other, a dismissal or anything else is `relay-left`: the tier is told, the card stays in the lane, and nothing is denied.
- **Files.** `prompts/questions-YYYY-MM.jsonl`: one redacted row per answered question (a tier's answer or the person's relayed pick; the question cut at 1 KB, the header at 64 bytes, the row under 4 KB), removed after 90 days (the sweep prunes once a day, under a lock folder). The ledger holds the answer's index (`opt`) and a hash of the request id and the label (`lh`), never the label.
- **Lanes.** The lane briefing is unchanged; the answering tiers judge every question, and a lane may head a question `Person` to keep it for the person (a mechanical check in the hook). After a relayed pick lands, the top tier is told in a fixed line that the pick is the person's answer for that lane's question, goes to that lane, and is not an instruction to it.
- **The audit** adds the anomalies `q-answer-not-question`, `q-decided-question`, `q-returned-differs` and `q-no-asks-on`, a QUESTIONS table, and the lane's question beside each relayed question; ADR 0004 has the reasoning.
